# Journal 渐进媒体加载安全发布顺序

状态：待执行  
日期：2026-07-23  
范围：本轮占位瀑布流、图片预览生成、历史图片补齐以及对应前后端代码的生产发布  
原则：不建立额外测试环境，不修改现有部署架构，不让 Journal 与 bot 在同一轮发布

## 1. 结论

本轮不是“发布后无法回头”。数据库迁移只增加一个可空字段和唯一索引，预览图也是原资产旁边的派生文件；旧 Journal 镜像不会读取这些新字段和文件，因此即使新版本已经完成迁移或只完成了部分历史预览补齐，仍可切回旧镜像继续运行。

真正需要控制的是发布过程，而不是迁移本身：当前 GitHub Actions 在 `main` 收到非文档推送后立即自动发布，而本轮修改了根依赖、锁文件和共享协议，路径判断会同时选中 Journal 与 bot。直接普通 push 会把 Journal 数据升级和 bwgdc01 bot 重启绑在同一轮中，不适合本次大改。

推荐采用以下主路径：

```text
冻结本轮代码
  → 建立发布前数据备份和旧镜像回退点
  → 用 skip 指令把代码推到 main，但不触发 push 发布
  → 手动只发布 Journal
  → 用真实公开页、私有页和 Telegram 新记录完成使用验收
  → bot 保持现状，本轮不单独发布
```

不增加新的预发布环境、双数据库、灰度系统、影子服务或第二套 workflow。

## 3. 发布顺序

### 阶段 0：冻结发布范围

在本轮代码进入 `main` 前停止继续叠加无关功能，只保留：

- 方案文档；
- `sharp` 依赖、锁文件和允许构建声明；
- Journal 数据迁移、预览服务、历史补齐和媒体路由；
- 占位瀑布流、渐进图片和卡片视频展示；
- 已经存在于本地但尚未部署的深色文字画报提交。

不把新的交互优化、样式微调或其他功能顺手带入本次发布。

阶段完成条件：本轮形成一个边界明确的 release commit，当前所有未提交文件都能归入上述范围。

### 阶段 1：建立发布前回退基线

在推送代码之前、手动发布 Journal 之前完成一次新的 Journal 异地备份。备份必须包含现有 SQLite、WAL 相关数据、全部媒体、环境配置、Compose 配置和当前部署 SHA；沿用已经存在的 `journal-backup` 主路径，不另建备份工具。

同时记录并保留：

- 当前生产 SHA `0c028f84c90fc2632c13dd5b6bfa35396704b375`；
- 当前生产镜像；
- 已有前一镜像 `384970e17215b744a460ed8832ac6ae1f4043715`；
- 新备份在异地存储中的文件名和时间。

首选应用回退点是当前生产 SHA，而不是更老的前一镜像。备份恢复只作为数据异常时的最后手段，正常的前端或启动问题不应恢复数据库。

阶段完成条件：新的备份成功结束，当前生产镜像仍然 healthy，两个旧镜像没有被清理。

### 阶段 2：推送代码但禁止自动发布

release commit 继续使用项目现有的英文 Conventional Commit 格式，并在提交信息中加入 `[skip actions]`。GitHub 官方说明该指令会跳过由 `push` 触发的 workflow，但不会阻止之后通过 `workflow_dispatch` 手动运行。

这样做的目的不是绕过 CI，而是把“代码进入默认分支”和“生产环境切换”拆成两个可控动作：

- `main` 先获得完整、可定位的 release SHA；
- push 不自动启动 Journal 或 bot job；
- 后续由同一个现有 `deploy.yml` 手动选择部署目标；
- 不修改 workflow，也不引入临时代理或部署脚本。

参考：[GitHub Actions 跳过 push workflow 的官方说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs)。

阶段完成条件：远端 `main` 已指向 release SHA，push 没有触发生产发布，线上仍是 `0c028f8`。

### 阶段 3：只发布 Journal

从 GitHub Actions 手动触发现有 `Deploy To Servers` workflow，并明确选择：

- `deploy_journal = true`；
- `deploy_bot = false`。

前端不是独立站点，它已经构建在同一个 Journal 镜像里，因此不需要第二次前端发布。该 job 会依次完成不可变镜像构建、上传和 Journal 容器切换；新容器启动时依次发生：

1. SQLite 执行 v3 增量迁移；
2. 逐张生成历史图片的 64px WebP；
3. 写入预览路径并补齐缺失宽高；
4. 历史资产全部处理完成后注册 HTTP 服务；
5. health 成功后，workflow 才把新 SHA 记为当前版本。

如果失败发生在镜像构建或上传阶段，生产容器没有变化。如果失败发生在容器切换或历史补齐阶段，旧镜像仍保留，但旧容器可能已经被新容器替换，需要立即执行阶段 5 的应用回退。

阶段完成条件：Journal job 成功，新容器为 release SHA 且进入 healthy；bot job 明确 skipped。

### 阶段 4：真实使用验收

不创建测试数据体系，直接使用现有个人项目的真实主路径验收，顺序为：

1. 以访客视角打开公开信息流，确认首帧是静态瀑布流占位，随后整体自然接管；
2. 查看既有单图、多图、文章封面和文字记录，确认图片由模糊预览过渡到清晰原图，卡片高度稳定；
3. 登录“我的资产”，确认私有信息流与公开信息流保持相同接管效果；
4. 打开已有多媒体详情，确认主媒体布局未改变，底部图片缩略导航使用低清预览；
5. 从 Telegram 新发布一条带图片记录，确认新资产不依赖历史补齐也能立即生成预览；
6. 新增或替换一张文章图片，确认文章上传链路生成预览并保存正确比例；
7. 继续加载下一页，确认新增卡片只在 Masonry 排版完成后出现，不覆盖已有信息流。

发现纯前端展示问题时优先回退应用镜像，不恢复数据；发现新图片入库失败或历史补齐错误时保留具体资产和日志现场，再决定修复还是回退。

阶段完成条件：公开页、私有页、既有图片、新增 Telegram 图片、文章图片和追加分页的主路径均符合预期。

### 阶段 5：回退路径

#### 5.1 应用回退

首选回退到发布前的生产 SHA：

```text
0c028f84c90fc2632c13dd5b6bfa35396704b375
```

v3 迁移是向后兼容的增量：旧应用会忽略 `preview_relative_path`，也会忽略已经生成的 `.preview.webp` 文件。因此以下情况只需要切回旧镜像：

- 新前端交互或样式不可接受；
- 新服务无法在启动窗口内进入 healthy；
- sharp 在生产镜像内无法正常处理某张历史图片；
- 新媒体路由或图片加载存在功能错误。

回退应用后保留 v3 字段和预览文件，不执行逆向迁移，不删除派生文件。后续修复版本可以继续复用已经成功补齐的部分。

#### 5.2 数据恢复

只有确认 SQLite 或原始媒体发生数据破坏时，才停止 Journal 并恢复阶段 1 的完整备份。数据恢复会覆盖发布后的新增记录，因此属于最后手段，必须另行确认，不能与普通应用回退混用。

### 阶段 6：bot 处理

本功能不修改 bot 交互逻辑，Journal API 只是给资产对象增加 `previewUrl`，现有字段保持不变。Journal 验收通过后无需为了“版本一致”立即重启 bwgdc01 bot。

bot 保持当前版本，等下一次真实 bot 功能变更时再按原流程发布。届时 Journal 已经先完成协议升级，不会出现新 bot 先于新 Journal 的顺序倒置。

## 4. 明确禁止的发布方式

- 不使用普通提交信息直接 push `main`，避免 Journal 与 bot 自动连续发布；
- 不在没有新备份和明确旧 SHA 的情况下触发 Journal job；
- 不同时选择 `deploy_journal = true` 和 `deploy_bot = true`；
- 不因为前端问题恢复数据库；
- 不删除旧镜像后再尝试新版本；
- 不为本轮临时增加第二套服务器、数据库、OpenResty 站点或发布 workflow；
- 不绕过 GitHub Actions 直接覆盖生产应用源码。

## 5. 最短执行清单

```text
1. 冻结本轮代码并形成带 [skip actions] 的 release commit
2. 生成新的 Journal 异地备份并记录备份文件
3. 保留并记录生产 SHA 0c028f8 和两个旧镜像
4. push main，确认没有自动发布
5. 手动 dispatch：Journal=true，Bot=false
6. Journal healthy 后按真实主路径验收
7. 通过则结束；失败则先切回 0c028f8，数据不回滚
8. 本轮不发布 bot
```

这套顺序只复用已有不可变镜像、Compose health、GitHub 手动发布和 rclone 备份能力，没有引入新的长期组件。
