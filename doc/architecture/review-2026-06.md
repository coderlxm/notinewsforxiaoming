# 项目架构评估与改进方向

> 时间：2026-06-23
> 背景：对 NotiNewsForXiaoming 项目当前 src/ 结构的全面审阅，评估架构合理性并记录待优化点。

## 整体评价

整体架构合理，是一个典型的个人 Telegram bot 单体应用，分层职责清晰，单向依赖无循环引用。

## 合理的部分

1. **分层职责清晰**：`fetchers`（数据获取）→ `ai`（AI 处理）→ `formatters`（消息格式化）→ `publishers`（发送）→ `scheduled`（调度），单向依赖，无循环引用。
2. **`utils/` 纯工具、`calendar/` 独立无外部依赖**，边界干净。
3. **`reminders/` 作为独立模块自包含**（db + repository + parser + scheduler + formatter），是项目最成熟的部分。
4. **start.gg 已完成拆分**：从单文件 `startggTracker.ts`（981 行）拆为 `startgg/{client,queries,tracker}.ts` + barrel `index.ts`，结构合理。

## 值得关注的问题

### 1. `reminders/db.ts` 是全局 DB 狗骨头

所有 repository（`reminders/`、`services/startggRepository`、`services/v2exBufferRepository`、`services/avRepository`、`services/vitaminReminder`）都直接 `import { getDb } from '../reminders/db.js'`。

问题：
- `db.ts` 放在 `reminders/` 目录里，但它实际是全局基础设施，不该属于 reminders 模块。
- 所有 service 对 DB 的依赖隐式耦合在模块加载时，难以单独测试或替换。

建议：将 `db.ts` 提升为 `src/db.ts` 或 `src/infrastructure/db.ts`，语义上归位基础设施层。

### 2. `scheduled/runMode.ts` 是上帝函数

`runMode()` 一个函数 191 行，包含 12+ 种模式的完整编排逻辑，import 了几乎所有目录的内容。这是全项目耦合度最高的节点。

问题：
- 每新增一个 push 模式就要改这个函数和 `index.ts` 的调度表。
- 模式间逻辑差异大（有的需要 AI、有的需要 fetcher + formatter、有的需要 service），堆在一起难以看清主路径。

建议：可以按模式将各分支抽为独立 handler（如 `modes/sleep.ts`、`modes/news.ts`），`runMode` 只做分发。但如果模式数量已趋于稳定，保持现状也不影响使用。

### 3. `bot/interactive.ts` 882 行——另一个上帝文件

所有交互命令（remind、startgg watch、av fetch、vitamin）的 handler 都注册在这一个文件里。它和 `runMode.ts` 一样是全局编排点。

问题与 `runMode` 类似：命令越多越臃肿。

建议：可按功能域拆为 `bot/handlers/reminders.ts`、`bot/handlers/startgg.ts` 等，`interactive.ts` 只做注册入口。同样，如果不频繁新增命令，现状可接受。

### 4. `services/` 内部层次扁平，服务粒度不均

`services/` 同时容纳了：
- 重型业务（`avTracker` 451 行、`startggTracker` 483 行）
- 轻量配置（`startggPresetConfig` 48 行、`fitness` 144 行）
- 纯 repository（`avRepository`、`v2exBufferRepository`、`startggRepository`）

start.gg 已经拆出子目录，但 av 相关的 `avTracker.ts` + `avContentParser.ts` + `avRepository.ts` 仍是平铺的三文件，没有像 start.gg 那样收进 `av/` 子目录。如果 av 模块继续增长，可以考虑同样收进 `services/av/`。

### 5. 根目录散落测试文件

`test_rss.ts`（项目根）和 `src/test_v2ex.ts` 是临时调试脚本，不属于正式代码，但混在源码目录里。

建议：移到 `scripts/` 或删除。

### 6. `formatters/index.ts` 228 行，承担了大部分模式的格式化

和 `runMode.ts` 一一对应地膨胀。10 种 push 消息的格式化函数都在一个文件里。

这个可以接受（格式化函数间无共享逻辑，放一起问题不大），但如果后续模式继续增加，同样可按域拆分。

## 总结

| 维度 | 评价 |
|------|------|
| 分层架构 | 合理，单向依赖无环 |
| 模块内聚 | `reminders/`、`startgg/` 好；`services/` 粒度不均 |
| 耦合度 | `db.ts` 全局隐式耦合、`runMode.ts`/`interactive.ts` 是高耦合中心 |
| 可维护性 | 中等——当前规模可接受，但两个上帝文件是主要风险点 |
| 一致性 | start.gg 已子目录化，av 尚未跟进 |

**当前规模下架构是合理的**。如果业务不再大幅扩张，最大的改善点是把 `db.ts` 从 `reminders/` 提到顶层，以及清理根目录测试脚本。如果后续要继续加 push 模式或交互命令，优先拆 `runMode.ts` 和 `interactive.ts`。

## 各目录职责一览

| 目录 | 职责 | 主要依赖 |
|------|------|----------|
| `ai/` | DeepSeek AI 客户端 + 8 个 AI 辅助函数 | config, fetchers(types), services/fitness(type) |
| `bot/` | Telegram bot 创建、鉴权、回调解析、交互命令注册 | reminders/*, services/*, formatters, scheduled, utils |
| `calendar/` | 中国节假日判定 + 倒计时 | 无外部依赖 |
| `config/` | dotenv 环境变量加载 | — |
| `fetchers/` | 5 个外部数据源抓取（weather/games/english/github/v2ex） | config(weather), 独立 |
| `formatters/` | Telegram HTML 消息构建（日常推送 + av + startgg） | fetchers(types), calendar, utils |
| `publishers/` | Telegram 消息发送（文本 + 图片） | config, bot/createBot |
| `reminders/` | 提醒系统全栈（db/repo/parser/scheduler/formatter） | config, utils |
| `scheduled/` | 调度入口：runMode 分发 + 固定 job 注册 | 几乎所有目录 |
| `services/` | 业务服务层（av/startgg/v2ex/vitamin/fitness/serverHealth） | reminders/db, config, formatters, publishers, ai |
| `utils/` | 纯工具函数（time/html/telegramMarkdown） | dayjs, marked |

## 关键耦合节点

- `config/index.ts` — 被几乎所有目录导入
- `reminders/db.ts` `getDb()` — 被所有 repository 共享的 SQLite handle
- `scheduled/runMode.ts` — 中心分发器，最大的跨目录 import 面
- `bot/interactive.ts` — 交互编排中心，覆盖提醒/startgg/av/vitamin 命令
- `publishers/telegram.ts` `sendTelegramMessage` — 统一输出通道
