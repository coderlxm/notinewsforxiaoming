## 2. 当前实现基线

### 2.1 内容限制

| 项目 | 当前限制 |
|---|---:|
| 素材总数 | 最多 30 项 |
| 视频数量 | 最多 5 段 |
| 全部文件总量 | 不超过 500 MiB |
| 单张图片 | 不超过 40 MiB |
| 图片像素 | 不超过 50 MP |
| 单段视频 | 不超过 500 MiB |
| 视频时长 | 不超过 5 分钟 |
| 视频画面 | 最大 3840 × 2160 |
| 视频帧率 | 最大 60 fps |

图片支持 JPEG、PNG、静态 WebP 和单张 HEIC/HEIF。视频支持 MP4、MOV，
视频编码支持 H.264 和 HEVC Main/Main10，音频支持 AAC 或无音频。

### 2.2 上传与整理

- 素材按选择顺序逐个上传。
- 每个文件由 `tus-js-client` 按 32 MiB 分片发送。
- `@tus/server` 与 `@tus/file-store` 直接把上传内容写入临时文件。
- 全部文件上传后，服务端按顺序整理素材。
- 图片生成 Journal 正式图和低清预览图。
- 视频通过 FFmpeg 流复制整理为 fast-start MP4，不重新编码画面和声音。
- HEVC 视频写入 `hvc1` 标记，并生成视频封面。
- 所有素材处理成功后才建立投稿并显示“已经送到小明”。

### 2.3 Screen Wake Lock

- 点击提交后立即申请 `screen` wake lock。
- 浏览器返回有效 `WakeLockSentinel` 后，页面才显示“屏幕常亮已开启”。
- 常亮覆盖文件上传和服务端整理两个阶段。
- 页面重新回到前台时会重新申请。
- 投稿成功、失败或页面卸载时释放。
- 浏览器不支持或没有授予常亮时，页面明确提示用户保持页面打开。

### 2.4 当前页面内 TUS 续传

当前版本允许同一个页面、同一份投稿中的短暂连接恢复：

- 重试间隔为 `0 / 3 / 5 / 10 / 20` 秒；
- 仅处理网络错误、HTTP 409、HTTP 423 和服务端 5xx；
- 通过同一个 TUS 上传地址查询服务端 offset 后继续；
- 业务校验类 4xx 不重试；
- 不把上传指纹持久化到浏览器；
- 刷新页面、关闭浏览器、页面被系统回收后不能恢复旧投稿。

这一实现更新了原设计文档中“不自动重试”的旧基线。当前只增加当前页面内的有限
TUS 续传，没有引入跨页面草稿、持久任务或第二条上传通道。

## 4. 线上熄屏验收记录

### 4.1 第一轮：熄屏但底层连接没有中断

时间范围：2026-07-27 00:37:27–00:37:59。

观察结果：

1. 客户端创建一份投稿并上传 4 项素材。
2. 第一个主要 TUS `PATCH` 请求持续约 13.9 秒。
3. 该请求完整返回 HTTP 204，期间没有出现新的 `HEAD` offset 查询。
4. 4 项素材处理接口全部返回 HTTP 200。
5. 最终 `/api/contributions` 返回 HTTP 200。
6. 用户在页面看到投稿成功。

结论：

> 本轮虽然屏幕熄灭，但上传连接一直保持，没有触发 TUS 续传。它证明短暂熄屏
> 不必然中断浏览器正在进行的上传，但不能单独证明断线恢复能力。

资源观察：

| 阶段 | CPU | Journal 内存 |
|---|---:|---:|
| 上传 | 峰值约 25% | 约 155 MiB |
| 素材整理 | 瞬时约 100% | 峰值约 287 MiB |

Journal 容器全程 healthy，零重启，无 OOM。

### 4.2 第二轮：底层连接发生变化并成功续传

时间范围：2026-07-27 00:40:11–00:41:17。

观察结果：

1. 客户端创建一份投稿并上传 4 项素材。
2. 第一个大文件使用固定 TUS 上传地址开始 `PATCH`。
3. 上传过程中，同一地址出现 `HEAD` 请求，客户端查询服务端已保存的 offset。
4. 随后客户端对同一地址继续发送 `PATCH`。
5. 中间再次出现一次 `HEAD → PATCH` 的偏移恢复序列。
6. 客户端没有重新创建该文件的 TUS 上传资源，也没有从头上传整份文件。
7. 4 项素材处理接口全部返回 HTTP 200。
8. 最终 `/api/contributions` 于 00:41:17 返回 HTTP 200。
9. 用户确认页面继续上传，并在收件箱收到投稿。

结论：

> 本轮在用户可见层面没有失败，但协议层真实发生了连接变化。TUS 查询既有
> offset 后继续同一文件，完整验证了“当前页面内短暂断线续传”的主路径。

资源观察：

| 指标 | 结果 |
|---|---:|
| 本轮约新增入站流量 | 99 MiB |
| 上传阶段 CPU | 约 17%–25% |
| 素材整理 CPU 峰值 | 约 96% |
| Journal 内存峰值 | 约 384 MiB / 1 GiB |
| 容器重启 | 0 |
| OOM | 否 |
| 最终健康状态 | healthy |

## 5. 资源压力结论

当前 `1 CPU / 1 GiB` Journal 容器可以完成已经验收的个人投稿负载：

- TUS 文件接收没有形成与完整文件等量的 Node.js 内存副本；
- 上传阶段 CPU 压力较低；
- FFmpeg、封面或图片整理阶段可以短时占满约 1 个 CPU；
- 两轮熄屏验收中的内存峰值最高约 384 MiB，距离 1 GiB 限额仍有明显余量；
- 处理期间健康接口持续返回 HTTP 200；
- 没有发生容器重启或 OOM。

这里能够确认的是已发生投稿的运行结果。由于当前媒体整理是全局单任务，
多人上传可以同时写入分片，但素材整理会按顺序等待；这属于当前个人项目的既定取舍。

## 6. 已确认的质量行为

### 6.1 分片上传不改变媒体质量

TUS 分片只改变网络传输方式，服务端按 offset 还原原始文件字节，不参与视频编码。
因此分片本身不会降低分辨率、帧率或码率。

### 6.2 手机视频整理不重新编码

当前 H.264 和 HEVC 视频使用 FFmpeg stream copy：

- 不降低 4K 分辨率；
- 不把 60 fps 改为 30 fps；
- 不把 HEVC 强制转换为 H.264；
- 不进行 HDR 到 SDR 的色调映射；
- 只规范容器、轨道、metadata、fast start 和 HEVC `hvc1` 标记。

用户已实际确认 60 fps 视频上传后仍以 60 fps 播放。

### 6.3 屏幕常亮与续传是两层能力

- Screen Wake Lock 用于减少系统自动熄屏造成的页面暂停；
- 用户主动锁屏时，系统仍可以释放 wake lock；
- 如果底层连接保持，上传直接继续；
- 如果连接中断但页面仍存在，TUS 使用服务端 offset 继续。

第一轮验证了“连接保持”，第二轮验证了“连接变化后续传”，两者共同覆盖了当前
手机投稿最常见的短暂熄屏场景。

## 7. 当前未覆盖的边界

以下场景没有足够的真实运行证据，不能根据本报告判定为已通过：

- 一次完整提交 30 项素材；
- 一份投稿恰好达到 500 MiB；
- 5 段视频同时达到各自上限；
- 3 位朋友在同一时间持续上传和整理大视频；
- 熄屏或断网时间超过当前有限重试窗口；
- 页面刷新、浏览器关闭或页面被系统回收后的恢复；
- 超过 5 分钟、超过 4K、超过 60 fps 的视频；
- ProRes、WebM、AVI、MKV、RAW、ProRAW 等约定外格式。

这些项目不是当前已发现故障，只是尚未被本轮真实验收覆盖。

## 8. 验收结论

朋友投稿上传链路已达到当前个人项目的正式使用要求：

- 主流手机照片、MP4/MOV、H.264/HEVC 和大体积手机视频能够进入统一主路径；
- 32 MiB TUS 分片能够通过现有 Cloudflare 与 Journal 链路上传；
- 视频整理保持原有画质与帧率；
- 上传和整理阶段资源压力处于当前容器可接受范围；
- Screen Wake Lock 能减少自动熄屏；
- 当前页面内的短暂连接中断能够使用 TUS offset 继续；
- 最终投稿入箱结果已经由用户和服务端日志共同确认。

本轮功能验收通过。
