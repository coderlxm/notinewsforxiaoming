# 前端组件库引入必要性评估

<!-- Review date: 2026-08-01 -->

## 一、结论

**当前不应新引入全量组件库，也不应将现有 Vant 扩展为全站 UI 框架。**

项目已经采用了更合适的最小形态：`vant@4.10.0` 已安装，但只由两个功能组件按需使用——信息流下拉刷新与无限列表。其余界面继续以项目自己的设计 token、语义 CSS 和浏览器原生控件实现。

这不是“完全不用组件库”的结论，而是：**成熟库只在它能完整替代一段已发生的复杂交互时局部接入；不能因为项目已有表单、弹窗或按钮，就让库接管整套视觉与组件边界。**

## 二、评估范围与证据等级

本次仅检查 `web` 前端的依赖、入口、49 个 Vue SFC、全局样式和已有前端决策文档；不改变页面、依赖或交互。

下列内容明确区分事实与判断：

- **源码事实**：来自当前工作区文件和锁文件。
- **官方资料**：用于确认 Vant 的产品定位，不替代对本项目的判断。
- **评估判断**：根据前两类证据得出的当前结论；若产品范围变化，应重新评估。

## 三、当前实现基线

### 3.1 已有的是“受控的局部组件库使用”

源码事实：

- 根 `package.json` 与 `pnpm-lock.yaml` 固定 `vant@4.10.0`，其 Vue peer dependency 与项目的 `vue@3.5.40` 匹配。
- `web/src/components/ui/JournalPullRefresh.vue` 具名导入 `PullRefresh`，用项目自定义插槽、样式 token 与 `:deep()` 结构样式承接下拉刷新。
- `web/src/components/journal/FeedView.vue` 具名导入 `List`，承接基于 cursor 的“加载更早记录”。
- `web/src/main.ts` 没有 `app.use(Vant)` 或全局组件注册；`web/vite.config.ts` 也没有 UI 库主题、自动导入或样式重置配置。

官方资料确认 Vant 是面向 Vue 移动 Web 的轻量、可定制组件库，并提供本项目正在使用的 PullRefresh 与 List 能力：[Vant 官方文档](https://vant.pro/vant/#/en-US/quickstart)、[PullRefresh](https://vant.pro/vant/#/en-US/pull-refresh)、[List](https://vant.pro/vant/#/en-US/list)。

评估判断：这两处都替代了原本需要手写的完整交互职责（触摸下拉状态与无限列表触发），而非只替换一个按钮或输入框的外观；保留它们符合项目的最小依赖原则。

### 3.2 界面已拥有清晰且有意的视觉主导权

源码事实：

- `web/src/assets/main.css` 集中定义颜色、字体、间距、圆角、深色模式、减少动效、焦点样式以及 `.button`、`.field`、`.notice` 等少量共享语义基础。
- `web/src/assets/contribution.css` 为独立投稿入口维护与主 Journal 相协调、但独立命名的视觉语言。
- 组件的专属视觉留在各自的 scoped style 中；富文本编辑、瀑布流、媒体展示、文章目录和档案卡 Loading 都依赖业务语义类、深层选择器或伪元素。
- 现有源码含 28 个原生 `input`、`textarea`、`select` 控件，以及 4 个 `dialog` 或 Popover 场景。它们分散在登录、筛选、投稿、内容编辑、文章发布和站点设置等具体流程中。

评估判断：这些控件的共同点主要是浏览器原生语义，而不是一套尚未存在的通用产品表单。用组件库替换会把视觉 token、状态样式、插槽结构和交互约定同时引入，不能删除现有的富文本、媒体和业务样式责任。

### 3.3 复杂交互不是“缺少基础组件”

源码事实：

- `CardActionMenu.vue` 使用原生 Popover、明确的菜单语义、键盘导航和定位逻辑，服务记录编辑、置顶、可见性及删除等专有动作。
- `PublishedTimeDialog.vue` 和 `ArticleTableOfContents.vue` 使用原生 `dialog`，分别承载时区明确的发布时间编辑与移动端文章目录。
- `RichTextEditor.vue` 基于 Tiptap，包含工具栏、上传、拖放/粘贴和正文资产选择；`ContributionMediaPicker.vue`、`EntryImagePicker.vue` 则服务各自的媒体流程。

评估判断：这些是产品语义明确的组合交互。若仅为弹窗、菜单或上传按钮替换成库组件，仍需保留大量项目逻辑和定制样式，且会增加视觉回归与双重交互模型的成本，因此不是净简化。

## 四、方案比较

| 方案 | 可删除的现有职责 | 新增成本 | 当前结论 |
| --- | --- | --- | --- |
| 保持现状：原生组件 + 语义 CSS + 两处 Vant 按需使用 | 无需迁移；已覆盖下拉刷新和无限列表 | 继续仅在真实重复处收敛样式 | 采用 |
| 将 Vant 扩展到按钮、表单、弹窗、菜单、上传等全站基础组件 | 很少；现有业务样式和组合逻辑仍需保留 | 主题适配、组件 API、样式覆盖、两套视觉规则并存 | 不采用 |
| 新增另一套桌面组件库 | 无；会与 Vant、原生控件和现有 token 并列 | 新依赖、设计语言冲突、学习和迁移成本 | 不采用 |
| 为本项目手写通用基础组件库 | 无成熟能力替换 | 长期维护一套并未被真实需求证明的 API | 不采用 |

## 五、当前边界

后续前端实现按以下边界执行：

1. Vant 保持按需具名导入，不进行全局注册，不引入全局主题、CSS reset、自动导入或完整组件集合。
2. 按钮、输入、提示、简单确认和信息展示继续复用现有语义 CSS 与原生 HTML；它们现在短、可读且与站点视觉一致。
3. `dialog`、Popover 和媒体选择只在成熟库能删除完整的交互实现时才考虑替换；只改变标签名称或外观不构成引入依据。
4. 不在现阶段为“统一性”预建 `BaseButton`、`BaseInput`、`BaseDialog` 等项目内基础组件层。已有的 `.button`、`.field`、`.notice` 足以承担当前确有的共享视觉。
5. 与 [UnoCSS 评估](./frontend-unocss-adoption-review-2026-07.md) 保持一致：设计 token 继续以 CSS variables 为唯一来源，避免组件库主题形成第二套 token 系统。

## 六、重新评估的准入条件

只有同时满足下列条件时，才值得针对具体能力重新选择组件库，而不是预先扩容：

1. 某类标准交互已在至少两个真实功能中重复，并且手写实现已包含焦点管理、键盘操作、触摸手势、定位、虚拟化或复杂状态协调等非业务职责。
2. 候选库可以完整删除该类职责的大部分实现，而不要求保留平行的自定义状态机、主题或组件包装层。
3. 接入后仍能复用现有 CSS token、深色模式和减少动效规则，并且不会引入第二套全局 reset 或设计 token。
4. 选型仅覆盖已发生的单一需求，先以一个组件按需导入落地；不把一次局部成功外推为全站迁移。

可触发重新评估的例子包括：同一套可搜索、多选、异步加载的选择器在多个管理流程中出现；或管理端实际出现需要排序、列控制、筛选联动与虚拟滚动的多列表格。现有代码尚未提供这些需求已发生的证据。

## 七、最终决策记录

```text
全量组件库：不引入
新增第二组件库：不引入
现有 Vant：保留，且仅保留按需局部使用模式
当前优先事项：继续维护 CSS token、语义基础类与业务组件边界
重新评估前提：成熟组件能删除一段已重复出现的完整复杂交互职责
```
