# Cloudflare HTTP/3 空闲连接失效：移动端写请求永久挂起 —— 复盘与警示

## 一、结论（已确认）

本问题根因已通过真实环境验证确定：

**iPhone 与 Cloudflare 边缘之间的 HTTP/3 (QUIC) 空闲连接在空闲期失效后仍被 iOS 复用，且 iOS 网络栈不把该失效转成 fetch 错误，导致写请求永久挂起。**

验证方式：在 Cloudflare 面板关闭该域名的 HTTP/3 后，问题消失，用户真实使用确认不再发生。

影响范围：iPhone Chrome（iOS WebKit/CFNetwork 网络栈）上的发布内容与编辑卡片等写操作。该问题此前被当作低频偶发问题，实际在真实使用中至少每天发生一次。

## 二、问题现象

### 用户可感知的现象

- 点击发布或编辑保存后，按钮和编辑区域进入 busy 状态，几十秒甚至永久不恢复。
- 刷新页面后再次执行相同操作成功。
- 一旦有一次操作成功，随后一段时间内的发布和编辑均正常。
- 连续换设备、连续发布的密集测试很难触发，容易误导为低频问题。
- 偶发"实际已经保存/发布成功，但页面仍卡住"。

### 现象的时间规律

1. 用户一段时间没有使用发布或编辑功能。
2. 突然进入页面进行第一次写操作，此时高概率出现永久 busy。
3. 刷新页面后执行相同操作，按历次真实使用观察会成功。
4. 一次操作成功后，随后一段时间内继续发布或编辑均成功。
5. 密集测试很难触发；自然空闲后的第一次实际使用才是主要触发窗口。

该规律是定位本问题的主轴：**写请求依赖的连接在空闲期间失效，刷新或首次成功重新建立连接**。

## 三、触发链路

### 1. 连接建立阶段

- 用户打开页面，iPhone Chrome 与 Cloudflare 边缘协商连接。
- Cloudflare 边缘宣告支持 HTTP/3（`alt-svc: h3`），iOS 15+ 默认优先使用 QUIC（UDP）。
- 客户端↔Cloudflare 边缘之间是 QUIC 连接；Cloudflare 回源到源站 OpenResty（源站仅监听 `443 ssl http2`，回源段为 TCP 长连接，不参与本故障）。

### 2. 空闲阶段

- 用户停止操作，连接进入空闲。
- Cloudflare 边缘的 QUIC 空闲超时机制关闭连接（空闲约 30 秒级即失效）。
- 同时 QUIC 走 UDP，运营商 NAT 对 UDP 映射的超时更短且静默丢弃，连接失效来源是双重的。
- iOS 网络栈连接池无感知，仍缓存该连接并认为可用。

### 3. 首次写请求阶段

- 用户执行写操作：
  - 发布：`POST /api/me/entry-uploads`（前置请求）→ `POST /api/me/entries`（正式创建）。
  - 已发布正文编辑：`PATCH /api/me/entries/:id/content`。
- 请求复用已失效的 QUIC 连接发出。
- UDP 无连接语义：数据包发出后没有任何反馈（服务器静默丢弃或 NAT 丢弃），也没有 TCP 那样的 RST。
- iOS 网络栈在该场景下不把连接失效转成 fetch 错误（与 WebKit 缺陷 215631 同型），fetch Promise 永不结束。
- 页面保持永久 busy，用户只能刷新。

### 4. 恢复阶段

- 刷新页面：页面销毁导致连接池清空，新请求建立新连接，立即成功。
- 偶发"实际已保存但页面仍卡"：请求数据恰好被服务端收到并处理（连接部分存活），但响应经失效连接回来时客户端收不到，Promise 不结束。

### 为什么发布和编辑两个链路都中招

两个链路共享同一个客户端网络栈与连接池。发布链路的第一个请求（uploads 前置）失败时，后续正式发布请求不会执行；编辑链路没有前置请求，保存请求本身就是页面存活期间的第一个写请求，直接复用失效连接。

## 四、为什么关闭 HTTP/3 后问题解决

### QUIC 失效检测机制的固有缺陷

- UDP 没有 FIN/RST 语义，连接关闭无显式信号。
- 连接 ID 失效后，服务器对旧连接上的数据包静默丢弃。
- 运营商 NAT 对空闲 UDP 映射静默超时，数据包在客户端侧就被丢弃。
- 客户端检测失效依赖 QUIC 的探测重传机制（PTO），而 iOS WebKit/CFNetwork 在该场景下不把探测超时转成 fetch 错误，请求表现为无限等待。

### HTTP/2 over TCP 的差异

关闭 HTTP/3 后，客户端与 Cloudflare 边缘协商为 HTTP/2 over TCP：

- TCP 有明确的关闭语义（FIN/RST），连接失效可被快速感知。
- HTTP/2 的 GOAWAY 帧告知客户端连接即将关闭，客户端应重建连接。
- 复用失效 TCP 连接时客户端能快速得到失败反馈，fetch 失败而非永久 pending。
- 因此写请求要么成功、要么快速失败，不会出现无限等待。

即：关闭 HTTP/3 不改变连接会被关闭的事实，但改变了客户端感知连接失效的能力——把"无限挂起"变为"正常失败或自动重建连接"。

## 五、排查过程复盘（走过的弯路）

1. **弯路一：默认客户端直连源站。** 最初围绕源站 OpenResty 的 `keepalive_timeout 60` 设计根因假设和实验方案（改为 0 消除可复用连接），但客户端实际经过 Cloudflare 代理，源站配置不在故障路径上，该实验方案作废。
2. **弯路二：未尽早核实 DNS 归属。** 本地环境 DNS 被代理软件劫持（返回 198.18.x 保留段假地址），从本机无法判断域名是否经过 CDN；需要从服务器或公共 DNS 核实。
3. **关键转折：确认 CDN 代理层。** 公共 DNS 解析得到 Cloudflare IP 段，实际请求响应头包含 `server: cloudflare`、`cf-ray` 并宣告 `alt-svc: h3`，确认客户端与源站之间存在 Cloudflare 边缘，故障假设转移到客户端↔边缘连接段。
4. **最终确认：关闭 HTTP/3。** 在 Cloudflare 面板关闭该域名 HTTP/3 后，故障消失，用户真实使用验证不再复发。

## 六、警示清单（防止再踩坑）

### 排查原则

1. 现象定位为"请求未到达源站"时，第一步必须确认客户端与源站之间是否存在 CDN 或代理层，再决定哪一段连接在故障路径上。
2. 涉及公网域名的连接故障，先在无代理污染的环境核实 DNS 归属和实际响应头。
3. 移动端 iOS"空闲后首次请求挂起"优先怀疑 CDN 边缘的空闲连接管理，QUIC 优先于 HTTP/2。
4. 机制解释必须区分已确认事实与推断；平台级结论必须经真实环境实验验证后才可表述为根因。

### 平台事实（长期有效）

1. Cloudflare 边缘宣告 HTTP/3 后，iOS 默认优先使用 QUIC。
2. QUIC 空闲连接失效来源双重：边缘空闲超时 + 运营商 NAT UDP 映射超时，客户端均无可靠感知。
3. iOS WebKit/CFNetwork 存在复用失效连接不转 fetch 错误的缺陷（WebKit 缺陷 215631 同型，官方状态 NEW；另见 257965 的长期 pending 记录）。
4. 源站 `keepalive_timeout` 只管理 CDN 回源段；CDN 回源失败会返回 5xx，不会造成客户端永久 pending，不能用来解释客户端侧挂起。

### 部署与实验检查单

1. 启用或关闭 HTTP/3 是对真实用户生效的平台改动，改动后必须用 iOS 真实设备验证"空闲后首次写请求"这一触发窗口，密集连续测试无法验证此类问题。
2. 客户端侧的超时兜底（15 秒有限等待）和发布前置探测请求只能缓解现象，不能替代连接层根因修复；引入时不要误以为问题已解决。
3. 本项目的发布进度探针（`sessionStorage` 阶段记录）保留，作为未来同类问题的第一手证据来源。

## 七、当前状态

- Cloudflare 面板已关闭 `feeds.xmcloud.buzz` 的 HTTP/3（2026-08-07 晚）。
- 关闭后用户真实使用确认故障消失。
- 客户端侧改动（发布前置请求纳入错误边界、15 秒有限等待、进度探针）保留为兜底。
- 源站配置未改动：`listen 443 ssl http2`，`keepalive_timeout 60`。
