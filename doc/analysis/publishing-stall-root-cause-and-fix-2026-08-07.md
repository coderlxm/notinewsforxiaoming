# 发布内容首次请求卡死：证据、根因边界与修复

## 问题影响

普通文字内容在点击发布后，按钮和编辑区域进入 busy，但几十秒内没有完成。刷新当前页面后重新填写并提交，发布通常立即成功。该问题破坏了发布入口的可信度，按 P0 处理。

## 已确认的源码行为

修复前的纯文字发布仍执行媒体上传会话：

```text
提交表单
→ 设置 uploading = true
→ POST /api/me/entry-uploads
→ 解析上传会话响应
→ POST /api/me/entries
→ 返回 /me
```

`createEntryUpload()` 位于 `useEntryMediaSubmit.submit()` 的 `try/finally` 之外。因此，第一个请求只要发生拒绝或响应读取异常：

- `uploading` 不会恢复为 `false`；
- 错误不会进入该 composable 的错误展示；
- 正式发布请求不会执行；
- 页面保持永久 busy，用户只能刷新。

这是源码可以直接确定的行为，不依赖浏览器问题是否能够稳定复现。

## 生产运行时证据

### 2026-08-07 20:22，iPhone Chrome

- 20:19:00，同一设备访问 `/api/me/entries`。
- 20:21:49，源站收到完整页面请求 `GET /me/entries/new`，与用户所述刷新后重试一致。
- 20:22:11.369，`POST /api/me/entry-uploads` 在 18.36 ms 内返回 200。
- 20:22:11.721，`POST /api/me/entries` 在 18.82 ms 内返回 200。
- 当天该成功请求之前，OpenResty 与应用日志均不存在对应的发布 POST。
- 同期没有匹配的 OpenResty 上游错误。

在用户确认 20:22 的内容是刷新后第二次成功发布这一前提下，第一次提交已经进入前端 busy，但没有到达源站。

### 2026-08-02，iPhone Chrome

- 第一次 `POST /api/me/entry-uploads` 已由源站返回 200。
- 后续 `POST /api/me/entries` 没有出现。
- 刷新后两个 POST 在同一秒正常完成。

这说明浏览器中的异步发布链可以停止在第一个请求的返回或后续执行阶段。现有服务端日志不能继续区分响应交付、响应体读取和 Promise 后续执行。

### 已发布正文编辑

用户确认 `/me` 卡片内直接编辑已发布正文也曾出现保存后永久 busy，刷新后再次编辑恢复。多数故障中修改没有保存，另有一次修改实际已经成功。

该链路只有一个幂等的 `PATCH /api/me/entries/:id/content`，并且已经位于 `try/catch/finally` 内。普通请求拒绝会执行 `finally` 并恢复 busy；永久 busy 表明至少部分故障中 Promise 长时间没有结束。偶发的“实际成功但页面仍卡住”则说明请求可能已经由服务端处理，但响应没有完整回到页面执行链。

这项证据排除了“媒体上传会话是唯一根因”，将根因边界提升到通用浏览器请求或响应链。

## 外部平台证据

iOS Chrome 使用 WebKit、Nitro 和 CFNetwork，而不是桌面 Chrome 的 Blink、V8 和 Chromium 网络栈：

- <https://developer.chrome.com/blog/chromium-chronicle-28>

WebKit 官方缺陷 215631 记录了 `fetch` 错误复用已关闭 TCP 连接的问题。报告者给出的特征包括低概率、受网络延迟影响以及连接关闭时机相关，目前状态为 NEW：

- <https://bugs.webkit.org/show_bug.cgi?id=215631>

WebKit 官方缺陷 257965 记录了 iOS 标签页中的请求进入长期 pending、源站在大部分故障窗口内没有收到请求、且难以稳定复现的现象。该记录主要针对 XHR，不能直接证明本项目的 `fetch` 属于同一缺陷，但证明 iOS WebKit 网络请求存在高度相似的故障类型：

- <https://bugs.webkit.org/show_bug.cgi?id=257965>

## 结论强度

### 已确认

- 第一个网络调用没有完整的错误边界。
- 任何该阶段的网络异常都会被放大成永久 busy。
- 已发布正文编辑也存在通用网络请求长期 pending 的历史现象。
- 刷新会重建前端状态；刷新后的服务端处理速度正常。

### 高度吻合但尚未确认

- 首始网络异常来自 iOS WebKit/CFNetwork 的空闲连接或页面生命周期问题。
- 刷新通过重建页面网络上下文或建立可用连接使下一次请求恢复。

### 当前不能声称

- WebKit 缺陷 215631 是唯一根因。
- 问题只存在于移动端。
- 本次修改能够修复浏览器引擎本身的网络缺陷。

## 本次主路径修复

### 发布前置请求

保留 `POST /api/me/entry-uploads` 作为正式创建之前的无副作用请求。运行时证据表明故障可能发生在请求未到达源站或响应未回到页面两种状态；如果直接让正式创建成为空闲后的第一个请求，响应丢失后重新提交可能产生重复内容，因此本次不采用该方案。

上传会话创建已移入 `useEntryMediaSubmit.submit()` 的 `try/catch/finally`。请求拒绝时，错误会显示、busy 会恢复，正文保留在当前页面。

该前置请求设置 15 秒有限等待。超过时间后浏览器请求被中止并显示“网络请求长时间没有响应”，用户可以在原页面重新点击发布。没有自动重试。

### 已发布正文编辑

`PATCH /api/me/entries/:id/content` 是用目标正文覆盖现有正文的幂等操作，也设置相同的 15 秒有限等待。超时后原有 `finally` 会恢复卡片状态，再次保存相同正文不会创建重复内容。

### 正式创建内容

`POST /api/me/entries` 不设置客户端超时。它不是幂等操作，在缺少请求幂等键的情况下，客户端超时后再次提交可能产生重复内容。发布前置请求刚刚成功后才进入正式创建，以降低正式写入成为失效连接首个请求的概率。

本次没有加入自动重试、替代发送通道或静默降级。

## 保留的诊断能力

发布进度探针继续记录以下阶段到当前标签页的 `sessionStorage`：

- `SUBMIT_ENTERED`
- `UPLOAD_REQUEST_STARTED`
- `UPLOAD_REQUEST_COMPLETED`
- `ENTRY_REQUEST_STARTED`
- `ENTRY_REQUEST_COMPLETED`
- `NAVIGATION_STARTED`

如果请求仍长期 pending，用户刷新同一标签页后可以看到最后阶段和时间。纯文字发布不再经过 `UPLOAD_*` 阶段，因此新的故障记录能够直接反映正式发布请求是否停止。

## 预期结果

- 发布前置请求拒绝或超过 15 秒不再造成永久置灰。
- 已发布正文编辑超过 15 秒后恢复可操作状态。
- 用户输入在上述网络错误后仍保留在当前表单，可以原地再次提交。
- 如果浏览器请求永久 pending，探针仍保留故障阶段，为后续与源站日志关联提供证据。
