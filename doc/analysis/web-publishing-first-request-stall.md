# Web 发布首次请求卡死分析

日期：2026-08-07

## 结论

P0 现象不是正文落库慢，也不是数据库、容器资源或文章服务阻塞。根因是 2026-07-31 引入视频上传后，普通内容即使只有文字，也必须先创建一个媒体上传会话，再发起正文发布请求。这个原本单请求的主路径因此变成了两个串行请求。

线上存在一条与用户描述完全一致的真实记录：第一次操作只完成了上传会话创建，最终正文请求没有抵达服务端；刷新后再次操作，两步请求立即完成。前端又把上传会话创建放在 `try/finally` 之外；如果该阶段最终以错误结束，`uploading` 不会恢复，整个表单仍会持续置灰。

本次修复恢复了纯文字主路径：没有新增媒体时不再创建上传会话，直接提交正文。只有确实选择了图片或视频时才进入媒体上传链路；媒体会话创建也被纳入既有错误状态生命周期，错误会直接显示并解除忙碌状态。

## 排查范围

- `/me` 到 `/me/entries/new` 的 Vue 路由与组件挂载时序
- `EntryPublisherView` 的发布、保存草稿和忙碌状态
- `useEntryMediaSubmit`、`useEntryPublisher` 与统一 Fetch 封装
- `/api/me/entry-uploads`、`/api/me/entries`、草稿更新路由
- 上传会话的内存状态、临时目录创建与正文落库服务
- 文章创建、文章保存和公开状态切换链路
- rndc02 上的 OpenResty、Cloudflare 回源、Docker 容器、应用日志和健康状态
- 相关改动的 Git 历史

## 源码行为

### 回归前

普通内容发布由前端直接向 `/api/me/entries` 提交一次请求。纯文字发布不存在媒体会话依赖。

### 回归后

提交 `372a41b feat: support video uploads in journal web publisher` 将普通内容发布改成：

1. 所有内容先调用 `/api/me/entry-uploads`。
2. 有媒体时通过 tus 上传并处理素材。
3. 再携带 `uploadId` 调用 `/api/me/entries` 或草稿更新接口。

`EntryPublisherView` 无条件调用 `mediaSubmit.submit()`，所以纯文字也执行第 1 步。`useEntryMediaSubmit.submit()` 在进入 `try` 之前等待 `createEntryUpload()`；该等待失败时不会进入 `catch/finally`，`uploading` 会一直保持 `true`。页面上的正文、设置和按钮都由该状态禁用。

服务端的上传会话保存在进程内 `Map` 中，并为每个会话建立临时目录。纯文字请求创建的空会话只用于给下一次正文请求提供 `publicId` 和时间，对文字内容本身没有必要。

文章创建与普通内容不同：`/api/me/articles` 是单请求，`useArticleEditor` 的 `saving` 状态由 `try/finally` 完整管理，没有发现上述两阶段回归，因此没有修改文章业务代码。

## 运行时证据

部署环境：rndc02，域名 `feeds.xmcloud.buzz`。

- 当前 Journal 容器处于 healthy 状态。
- 2026-08-07 一次正常纯文字发布中，上传会话接口和正文接口在同一秒完成，应用内响应耗时分别约 18ms，排除正文处理或 SQLite 长时间阻塞。
- OpenResty 对私有 API 配置的 `proxy_read_timeout` 为 120 秒。浏览器在等待期间不会自动改变前端忙碌状态。
- OpenResty 访问日志记录到 2026-08-02 的异常序列：
  - 11:16:18，iPhone Chrome 请求 `/api/me/entry-uploads`，服务端返回 200。
  - 此后没有对应的 `/api/me/entries` 请求，说明正文发布没有抵达 OpenResty 或应用服务。
  - 11:18:28，刷新后的同一客户端再次请求 `/api/me/entry-uploads`，同秒请求 `/api/me/entries`，两者均返回 200。
- 同一份日志中的正常纯文字发布均表现为上传会话和正文请求相邻完成；异常记录留下了未被正文消费的上传会话。

日志能够确定故障边界在“上传会话响应返回后、最终正文请求抵达服务端前”。现有日志不能进一步证明响应是在 Cloudflare、浏览器连接层还是响应读取阶段中断，因此不把具体网络节点写成确定结论。

## 根因

确定根因由两部分组成：

1. 主路径设计回归：纯文字发布被错误地绑定到媒体上传会话，增加了不必要的串行网络阶段和进程内会话依赖。
2. 前端状态生命周期缺口：上传会话创建不在 `try/finally` 内，该阶段失败后不能恢复 `uploading`，造成用户看到的永久置灰。

## 为什么刷新后表现为恢复

能够从源码确定的是：刷新会销毁当前页面的 JavaScript 执行环境，原组件实例及其中卡住的 `uploading`、`submitting` 状态随之消失；新页面会创建全新的 composable 实例，其忙碌状态重新从 `false` 开始。再次点击发布时，前端也会创建新的上传会话 ID，先前未消费的会话不会阻塞新会话。

线上日志只能证明已观察到的第二次操作成功，不能证明“每次刷新后必定发布成功”，也不能证明刷新一定建立了新的 TCP 或 HTTP/2 连接。浏览器可能复用连接，原始瞬时故障也可能再次发生。当前证据还不能在 Cloudflare、浏览器网络层、响应读取或前端继续执行之间唯一确定中断点。

因此应区分两个结论：刷新必然清除当前页面内已经卡住的 Vue 忙碌状态；刷新后的新发布请求是否成功并非理论保证，只是现有现场记录和用户多次实际操作中都成功。刷新不是业务修复，本次修复通过移除纯文字主路径中的额外上传会话阶段来消除这个故障窗口。

## 修复

- 协议中的 `uploadId` 改为可选。
- 没有新增媒体时，普通内容创建、保存草稿和发布草稿直接调用正文接口。
- 服务端在没有上传会话时直接生成 `publicId` 和创建时间，并用空素材列表完成原有内容校验与落库。
- 有新增媒体时继续使用现有 tus 上传、媒体处理和会话消费流程。
- 上传会话创建移入 `useEntryMediaSubmit.submit()` 的 `try/finally`，使媒体路径的错误状态和忙碌状态保持一致。
- 未增加重试、fallback、静默跳过或默认成功行为。

## 影响范围

- 纯文字新内容：由两次串行 POST 恢复为一次正文 POST。
- 无新增媒体的草稿保存或发布：不再创建空上传会话。
- 带图片或视频的新内容、草稿编辑：继续走原媒体上传链路。
- 文章创建、编辑、素材上传和公开状态切换：行为保持不变。
- 数据库结构、现有内容和部署配置：无需变更。
