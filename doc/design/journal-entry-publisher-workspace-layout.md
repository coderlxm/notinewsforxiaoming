# Journal 发布内容工作区布局优化方案

## 1. 问题判断

当前发布内容页面使用约 780px 的单列容器，正文、媒体、频道、可见范围、发布时间和操作按钮依次纵向堆叠。新增发布时间后，页面的独立区域进一步增加，主要问题不是容器单纯偏窄，而是内容编辑与发布设置没有分组：

- 正文和媒体需要较宽空间，但频道、范围和时间不需要占满整行。
- 多组短表单纵向排列，拉长页面并削弱主次关系。
- 直接放大整个单列会让正文行宽过长，同时不能减少设置项带来的纵向高度。
- 保存草稿和发布按钮位于页面底部，编辑内容较长时离当前操作位置较远。

## 2. 推荐方向

桌面端改为约 1120px 的发布工作区，采用“左侧内容编辑、右侧发布设置”的双栏结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 返回我的全部记录                                      发布内容 │
├──────────────────────────────────┬───────────────────────────┤
│ 正文                             │ 发布设置                  │
│ ┌──────────────────────────────┐ │                           │
│ │                              │ │ 内容频道                  │
│ │          正文输入区          │ │ [生活] [兴趣]            │
│ │                              │ │                           │
│ └──────────────────────────────┘ │ 发布范围                  │
│                                  │ [公开] [私有]            │
│ 图片与视频                       │                           │
│ ┌──────────────────────────────┐ │ 发布时间                  │
│ │      拖拽 / 选择媒体         │ │ [ ] 指定发布时间         │
│ │      媒体预览网格            │ │ [日期] [时间]            │
│ └──────────────────────────────┘ │                           │
│                                  │ [保存草稿] [发布]         │
└──────────────────────────────────┴───────────────────────────┘
```

推荐宽度：

- 工作区：复用现有 `--editor-workspace-width`，当前为 1120px。
- 左侧内容区：`minmax(0, var(--editor-width))`，保持约 780px 的舒适编辑宽度。
- 右侧设置区：剩余约 320px，足以承载短表单。
- 栏间距：约 1rem，与文章编辑工作区保持一致。

## 3. 信息分组

### 3.1 左侧：内容本体

左侧只保留会直接形成发布内容的部分：

1. 正文输入。
2. 图片与视频选择。
3. 已选媒体预览和移除操作。

正文继续保持当前行宽，不因为页面整体变宽而无限拉长。媒体选择区和预览网格获得完整主栏宽度，更适合多图片和视频场景。

### 3.2 右侧：发布设置

右侧新增一个语义明确的 `aside`，标题为“发布设置”，内部依次放置：

1. 内容频道。
2. 发布范围。
3. 发布时间。
4. 保存草稿和发布操作。

右侧使用一个统一设置面板承载这些字段，而不是让每个设置块像独立大模块一样散落在页面中。现有频道、范围和时间组件继续负责各自输入逻辑，父组件只调整结构。

设置栏在桌面端可以 `position: sticky` 固定在工作区顶部。用户编辑较长正文或查看媒体预览时，发布设置和操作按钮仍保持可达。设置栏不创建独立滚动容器，避免双滚动条和滚动嵌套。

## 4. 操作按钮

- “保存草稿”和“发布”放在右侧设置面板底部。
- 桌面端两个按钮并排，发布按钮保留主操作视觉权重。
- 上传或提交期间继续使用现有禁用状态和加载反馈。
- 不增加额外的顶部发布按钮或底部悬浮条，避免同一操作重复出现。
- 移动端回落单列后，按钮放在所有设置项之后，并适当扩大点击区域。

## 5. 响应式布局

### 桌面端（建议从 960px 起）

- 双栏工作区。
- 右侧发布设置保持顶部粘性。
- 正文和媒体始终位于左侧。

### 平板端（约 600px–959px）

- 回落为单列，避免主编辑区被压缩。
- 正文和媒体在前。
- 设置面板在后。
- 设置面板内部可将频道和发布范围组织成两列，发布时间占完整一行，减少纵向高度。

### 手机端（小于 600px）

- 完整单列。
- 日期和时间继续纵向排列，避免原生时间控件被压缩。
- 保存草稿和发布按钮各占可用宽度的一半；极窄屏仍保持可点击。
- 不使用固定侧栏或额外滚动区域。

## 6. 组件边界

### `EntryPublisherView.vue`

职责仍是发布流程编排和表单提交，本次只调整结构：

- 页面宽度切换为 `--editor-workspace-width`。
- 表单增加主编辑区与设置侧栏两个布局容器。
- 正文和 `EntryImagePicker` 放入主编辑区。
- 频道、范围、发布时间及操作按钮放入设置侧栏。

### `EntryChannelField.vue`

继续只负责频道选择，不增加发布流程状态。可以微调侧栏中的间距和卡片密度，但不改变 `v-model` 接口。

### `EntryVisibilityField.vue`

继续只负责公开/私有选择，不改变数据结构和事件契约。

### `EntryPublishedTimeField.vue`

继续只负责指定时间开关及日期时间输入。桌面侧栏内日期与时间并排；移动端纵向排列。

### `EntryImagePicker.vue`

继续留在主编辑区，不放进窄侧栏。媒体预览需要横向空间，这是当前布局中最不适合压缩的部分。

本次不新增 composable、不移动提交逻辑，也不引入新的表单组件。

## 7. 样式原则

- 复用文章编辑页已经使用的工作区宽度和双栏比例，让两种创作页面形成统一认知。
- 设置侧栏使用一个外层卡片完成视觉分组，避免再叠加过重阴影。
- 设置项标题、说明和控件继续沿用当前字号与主题变量。
- 输入控件保持明确标签和可见焦点状态。
- 主编辑区和设置区都设置 `min-width: 0`，防止长文本或原生日期控件撑破网格。
- 只使用 CSS Grid 和媒体查询完成响应式变化，不进行 JavaScript 宽度测量。

## 8. 不建议的方案

### 仅把单列从 780px 拉到 1120px

会减少两侧空白，但正文过宽、短设置项仍然各占一整行，不能解决结构问题。

### 三栏布局

正文、媒体、设置分别一栏会压缩媒体预览和设置控件，且平板适配复杂，不符合当前个人项目的简洁主路径。

### 折叠频道、范围或发布时间

这些设置数量不多，折叠会增加操作步骤，也容易让用户发布前忽略重要配置。通过侧栏分组即可解决密度问题。

### 弹窗承载发布设置

发布前额外弹窗会切断编辑流程，并让保存草稿与正式发布的状态关系更复杂，没有必要。

## 9. 修改范围

本次布局优化只需涉及发布内容页面及其现有字段组件的样式：

- `web/src/components/publisher/EntryPublisherView.vue`
- 视实际视觉密度小幅调整三个设置字段组件的 scoped CSS。

不涉及 API、服务端、数据库、上传流程或发布时间业务逻辑。

## 10. 验收标准

- 桌面端正文和媒体位于左侧宽栏，发布设置位于右侧窄栏。
- 页面使用现有工作区宽度，但正文行宽没有被无节制拉长。
- 右侧能完整展示频道、范围、发布时间和两个操作按钮。
- 长正文或较多媒体导致页面滚动时，桌面端发布设置仍方便操作。
- 平板和手机回落单列，没有横向溢出和独立侧栏滚动条。
- 保存草稿、正式发布、媒体上传及指定发布时间的行为保持不变。
