# 功能待办评估

> 评估标准：实现成本、日常使用频率、对个人效率的实际提升、与现有系统的契合度。

---

## ✅ 高优先级（实用，值得尽快做）

### 1. 个人"投递箱"
发文字/图片/文件到 bot，自动打标签（待办/资料/报销/灵感），后续 /inbox 检索。

**评估：高优先级，实用。**
这是个人助理的「收件箱」核心功能。信息捕获是 GTD 的第一步，降低记录摩擦直接提升效率。标签自动分类利用现有 AI 能力，技术成本低。与现有 bot 基础设施完全契合。

### 4. 每日工作包
每天固定时间推：今日日程、待办 top3、昨天未完成、重点链接（GitHub/V2EX/你订阅源）。

**评估：高优先级，实用。**
现有的各 push 模式是独立推送的，每日工作包把它们整合成一条有上下文的摘要，信息密度更高、骚扰感更低。本质是对现有数据的聚合展示，技术成本可控。

### 7. 家庭运维面板
服务器巡检消息做成"可操作卡片"：重试巡检、静默 x 小时、确认已处理。

**评估：高优先级，实用。**
现有的 server_health 推送是只读的，出问题时只能被动看。加上行内操作（callback_query 已有基础设施）让告警变成可闭环的任务，实用价值极高。改动范围小，只需扩展 callback handler。

### 8. 订阅中心
你现在 AV 订阅那套可抽象成通用订阅：演员/片商/关键字/作者都可配置，统一去重和推送策略。

**评估：高优先级，实用。**
AV 订阅的逻辑（RSS → 去重 → AI 处理 → 推送）已经跑通了，抽象成通用订阅层是自然的架构演进。而且订阅场景远不止 AV：GitHub release、博客、价格监控都适用，复用价值高。

---

## ⚡ 中优先级（实用但可后置）

### 2. 文件提醒联动
发一个文件并说"明天 10 点提醒我处理这个"，提醒消息里带原文件链接/预览。

**评估：中优先级，实用但依赖 #1。**
这是投递箱的自然延伸，实用场景明确（收到 PDF 账单 → 提醒付款）。但文件存储和引用需要 #1 的基础设施先到位，不应在投递箱之前做。

### 6. 收藏到知识库
转发文章/截图给 bot，AI 生成摘要 + 关键词，按主题沉淀，支持 /search 关键词。

**评估：中优先级，方向对但成本高。**
知识管理确实是真需求，但做好需要：向量嵌入、语义搜索、合理的主题聚类、内容去重。以个人助理的体量，全文关键词搜索 + AI 摘要已经够用，不必一上来就做重。

### 9. 周报自动化
每周自动汇总：完成了哪些提醒、错过了哪些、关注源更新了哪些，给你一条可读周报。

**评估：中优先级，锦上添花。**
数据都在库里（reminders 有完成/错过状态、push_history 有推送记录），实现成本低。但这属于"有了更好，没有也不影响日常使用"的功能，在核心循环跑通前不值得优先。

### 10. 快捷面板扩展
现在是预设提醒，后续可做二级菜单：提醒 / 订阅 / 抓取 / 巡检 / 记录。

**评估：中优先级，UI 优化。**
本质上是对已有功能的导航重构，不改底层逻辑。在功能逐渐增多时有必要做，但不是独立功能，应跟随对应模块一起上线。

---

## ❌ 伪需求或不实用

### 3. 语音速记
发语音 -> 自动转文字 -> 抽取待办和时间 -> 一键建提醒。

**评估：伪需求，投入产出比极低。**
问题不在 AI 提取（DeepSeek 能做），而在语音输入本身：Telegram 语音消息在桌面端几乎没人用，移动端语音转文字已有系统级方案（iOS 听写、Gboard），用户完全可以在输入框里说完直接发文字给 bot。额外做一条语音链路增加延迟和不确定性，体验反而更差。

### 5. 出行/位置触发（弱实时）
你发"到公司提醒我打卡"，配合手动按钮或简单定位消息触发提醒。

**评估：伪需求，技术不可行。**
Telegram Bot API 不支持后台读取用户位置。要实现要么用户手动发位置（失去了「自动触发」的意义），要么另起一个手机 App 做地理围栏。为一个提醒功能引入移动端开发完全不值得。老老实实用手动 /remind 或定时提醒更可靠。
