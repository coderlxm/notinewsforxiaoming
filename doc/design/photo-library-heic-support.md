# 照片墙 HEIC 支持实施方案

## 状态与目标

本方案记录后续为照片墙增加 HEIC/HEIF 支持的实施边界，当前暂不实施格式解码。

目标是让 Google Drive 相册中的 iPhone HEIC 照片能够像 JPEG 一样进入照片索引，并通过宿主机流式转换为 WebP 返回浏览器，同时继续满足以下约束：

- 浏览器只访问本站，不直连 Google。
- 原始照片和生成图片都不在宿主机持久化。
- JPEG 现有展示路径保持不变。
- 不支持的文件不影响其他相册和照片展示。
- 不增加重试、格式降级或失败后替代通道。

## 当前已确认事实

- 照片索引当前只接收 MIME 为 `image/jpeg` 且扩展名为 `.jpg` 或 `.jpeg` 的文件。
- 图片响应由宿主机读取 Drive 文件流，经 Sharp 调整方向、尺寸并编码为 WebP 后直接返回。
- 当前提供 `64px` 预览图、最大 `1600px` 卡片图和最大 `3000px` 查看图。
- Journal 镜像已声明安装 `libheif-examples`，项目其他媒体路径也存在 HEIC/HEIF 处理代码，但这不能直接证明照片墙当前的 Sharp 流式管道可以解码线上实际 HEIC 文件。

## 实施前提

正式写入 HEIC 解码逻辑前，使用一张实际由 iPhone 产生的样片确认以下运行时事实：

- Google Drive 返回的 MIME、文件扩展名、校验值和图片元数据。
- rndc02 当前 Journal 镜像内 Sharp/libvips 对该文件的解码、方向识别和色彩表现。
- 单张普通 HEIC 与高像素 HEIC 转换时的实际峰值内存和处理时间。

只有确认现有 Sharp 流式路径可用后才直接复用；如果不可用，再根据实际原因确定唯一解码实现，不在代码中并存多条解码路径。

## 数据识别与索引

支持范围限定为：

- JPEG：`image/jpeg`，扩展名 `.jpg` 或 `.jpeg`。
- HEIC/HEIF：Drive 实际返回的 `image/heic` 或 `image/heif`，扩展名 `.heic` 或 `.heif`。

索引为照片记录源格式，但公开 API 不暴露 Drive fileId、Google URL 或内部授权信息。相册排序、封面选择、拍摄时间和公开哈希 ID 规则沿用现有实现。

无法识别的格式继续直接忽略。只包含不支持格式的目录不进入公开相册列表，不影响其他相册。

## 媒体链路

目标链路如下：

```text
浏览器请求本站图片 URL
→ Journal 根据公开哈希定位 Drive 文件
→ 从 Google Drive 获取原始文件流
→ 在内存中解码 HEIC、应用方向并缩放
→ 编码为对应尺寸的 WebP
→ 流式返回浏览器
```

不创建原图副本、转换缓存或索引文件。现有带内容版本哈希的图片 URL 和浏览器长期缓存策略保持不变。

## 资源控制

HEIC 解码会展开完整像素数据，高像素照片的瞬时内存明显高于文件体积。实施时应使用成熟并发控制库，把照片墙 HEIC 转换限制为同时 1 至 2 张；等待中的请求不提前打开 Drive 下载流。

并发限制只控制资源占用，不加入重试、降级或替代格式。JPEG 是否共用该限制由实际资源数据决定，避免无依据地拖慢现有路径。

## 完成标准

- 混合放置 JPEG、HEIC 和其他文件时，JPEG 与 HEIC 正常进入相册，其他文件不影响页面。
- HEIC 的预览、卡片和灯箱查看图方向正确、比例正确、色彩可接受。
- 桌面端与移动端相册列表、详情页和灯箱保持现有交互。
- 浏览器请求中没有 Google 域名、Drive fileId 或 Google URL。
- 宿主机不产生原图或转换结果的持久化副本。
- 多张高像素 HEIC 同时出现在页面时，转换并发受到明确限制。
- 损坏或无法解码的单张 HEIC 只使该媒体请求暴露错误，不破坏照片目录索引和其他照片访问。
