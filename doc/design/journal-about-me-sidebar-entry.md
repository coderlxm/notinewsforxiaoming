# Journal 侧边栏「关于我」入口初版设计

## 1. 文档状态

- 状态：初版，等待评审
- 目标阶段：产品方案讨论
- 本文仅依据当前源码中的侧边栏、公开资料和弹层实现整理，不引用项目历史文档。

## 2. 需求背景

公开首页目前通过固定侧边栏提供「生活 / 文章 / 兴趣」三个内容频道。访客可以理解内容分类，但缺少一个自然的入口进一步了解站点主人并获取联系方式。

希望在桌面端侧边栏底部增加一个符合现有视觉风格的「关于我」可点击项。点击后，访客能够看到头像、Bio 和主动公开的联系方式。具体呈现方式尚未确定，需要先选定适合当前个人项目的最短交互路径。

## 3. 当前实现依据

当前源码表现为：

- 桌面公开页使用宽度约 200px 的固定侧边栏，信息流是独立滚动区域。
- 侧边栏当前只有三个频道项，频道项使用圆角背景、文字和左侧竖向标记表达状态。
- 移动端没有固定侧边栏，三个频道会变成信息流上方的横向导航。
- 项目已有基于原生 `dialog` 与 `Teleport` 的弹层交互，可复用关闭、遮罩、键盘和移动端适配方式。
- 公开资料已经包含头像和 Bio，并且可以在现有设置页维护。
- 频道页面已经保留独立实例与滚动位置，「关于我」交互不应破坏频道状态。

## 4. 产品目标

1. 访客可以从公开首页稳定找到「关于我」。
2. 点击后无需离开当前信息流，即可查看身份信息和联系方式。
3. 关闭后回到原频道、原列表状态和原滚动位置。
4. 联系方式由站点主人自行维护，并且只展示主动公开的内容。
5. 交互和视觉继续沿用当前 Journal 的克制、个人化风格。
6. 结构允许以后增加新的联系方式，但首版不引入通用页面搭建器。

## 5. 非目标

首版不包含：

- 站内私信或留言表单。
- 验证码、反垃圾、消息通知等联系系统。
- 访客账号或关注关系。
- 独立的完整个人主页。
- 联系方式访问统计。
- 微信二维码上传与裁剪能力。
- 自定义区块、富文本介绍或任意拖拽排序。

## 6. 呈现方式比较

| 方案 | 体验 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| 居中个人名片弹层 | 点击后在当前页面上展开一张个人名片 | 路径短；不改变频道；关闭后上下文完整；可复用现有 `dialog` 模式 | 不具备独立链接；内容容量有限 | 推荐 |
| 右侧抽屉 | 从页面右侧滑出关于信息 | 与固定侧栏空间关系自然；可承载较多内容 | 当前项目没有同类抽屉；移动端需另做底部抽屉；对短联系方式显得偏重 | 暂不采用 |
| 独立 `/about` 页面 | 跳转到完整关于页面 | 可分享和被搜索；未来内容容量最大 | 打断信息流；需要额外路由、返回与滚动恢复；首版信息不足以支撑完整页面 | 后续内容丰富后再考虑 |

## 7. 推荐方案

采用「侧边栏底部入口 + 响应式个人名片弹层」。

点击「关于我」后：

- 不切换频道，不销毁当前 Feed，不改变当前滚动位置。
- 在页面上方打开个人名片弹层。
- 桌面端使用紧凑的居中卡片。
- 移动端使用接近底部卡片的全宽布局，但仍保持统一的弹层语义和关闭方式。
- 关闭弹层后，焦点回到「关于我」入口。

该方案与当前信息量最匹配，也不会提前把一个简单的联系方式入口演变成完整个人主页系统。

## 8. 侧边栏入口设计

### 8.1 桌面端

侧边栏内部划分为上下两个区域：

- 上部：生活、文章、兴趣频道导航。
- 下部：关于我。

「关于我」通过 `margin-top: auto` 固定在侧边栏底部，不跟随频道数量挤在顶部。入口与现有频道项使用一致的高度、圆角、字号、悬停背景和左右内边距。

为了避免被误认为第四个频道：

- 使用简洁的个人轮廓图标替代频道竖向标记。
- 在入口上方保留轻量分隔或额外间距。
- 打开弹层时使用按下态，但生活 / 文章 / 兴趣中的当前频道仍然保持选中态。
- 使用 `aria-haspopup="dialog"` 和 `aria-expanded` 表达交互语义，不使用 `aria-current="page"`。

### 8.2 移动端

移动端不存在侧边栏底部，因此将「关于我」作为第四个横向入口放在频道导航末尾。

为了降低它与频道的混淆：

- 频道继续使用竖向标记。
- 「关于我」使用个人图标。
- 点击仅打开名片弹层，不改变频道 URL 和频道选中态。

320px 宽度下四项仍可容纳；实现时应适当收紧横向内边距，不缩小可点击高度。

## 9. 个人名片内容结构

### 9.1 身份区

- 当前公开头像。
- 固定名称「小明同学」。
- 当前公开 Bio。

首版直接复用站点已有头像和 Bio，不再维护第二套个人介绍，避免首页与名片内容不一致。

### 9.2 联系方式区

每种联系方式显示为一行：

- 渠道图标。
- 渠道名称。
- 对外展示值。
- 对应操作。

建议首批支持：

| 类型 | 展示示例 | 操作 |
| --- | --- | --- |
| Telegram | `@xiaoming` | 打开 Telegram 链接 |
| Email | `name@example.com` | 打开邮件客户端；同时允许复制 |
| 微信 | 微信号 | 复制微信号 |
| GitHub | `github.com/xxx` | 在新标签页打开 |
| 个人链接 | 自定义名称或域名 | 在新标签页打开 |

只有填写并启用的联系方式才对访客展示。首版不显示空占位，也不以默认内容假装已配置。

### 9.3 底部说明

可选展示一句简短说明，例如「欢迎通过以上方式联系我」。该文案应保持短小，首版不单独提供富文本编辑能力。

## 10. 联系方式数据设计建议

将联系方式并入现有公开资料，而不是写死在组件中。

建议公开资料增加 `contactItems`：

```ts
interface SiteContactItem {
  kind: 'telegram' | 'email' | 'wechat' | 'github' | 'website';
  label: string;
  value: string;
  url: string | null;
  enabled: boolean;
}
```

约束：

- `kind` 使用有限枚举，以确定图标和默认行为。
- `label` 用于展示渠道名称或个人链接名称。
- `value` 是访客实际看到或复制的内容。
- `url` 仅用于可跳转渠道；微信等复制型渠道为 `null`。
- `enabled` 控制是否公开展示。
- 首版由固定渠道顺序决定展示顺序，不增加拖拽排序。

站点设置页在当前头像、Bio、天气设置之后增加「联系方式」区域。保存后更新同一份公开资料，名片直接读取现有站点资料 Store。

## 11. 交互细节

### 11.1 打开与关闭

- 点击侧边栏入口打开。
- 点击关闭按钮、遮罩或按下 Escape 关闭。
- 弹层打开时焦点进入弹层，关闭后回到入口。
- 不修改路由，不向浏览器历史增加记录。
- 弹层内部不影响信息流组件的 KeepAlive 状态。

### 11.2 联系操作

- Telegram、GitHub 和个人链接使用新标签页打开。
- Email 支持打开邮件客户端，也提供复制入口。
- 微信点击后复制微信号。
- 复制成功复用项目现有 `ElMessage`，例如「微信号已复制」。
- 跳转链接显示明确的外部跳转视觉提示。

### 11.3 状态

- 公开资料加载完成后才呈现完整名片。
- 联系方式为空时只展示身份区，不展示一个空的联系方式标题。
- 入口本身始终可点击；资料读取错误沿用公开资料现有错误提示，不在名片中增加另一套兜底数据。

## 12. 视觉方向

个人名片不是社交平台资料页，保持当前 Journal 的留白和低饱和视觉：

- 卡片宽度建议为 440px 至 500px。
- 头像建议为 64px 至 72px。
- 名称使用当前正文主色和稍高字重。
- Bio 使用次级文字色，允许自然换行，不使用首页的横向滚动效果。
- 联系方式使用独立浅色行容器或细分隔线。
- 可点击行在悬停时使用现有 `surface-muted` 背景。
- 主要强调色继续使用当前红色变量，不为不同渠道引入大面积品牌色。
- 弹层圆角、边框、阴影和关闭按钮应复用现有 Journal 弹层语言。

## 13. 组件边界建议

### `PublicChannelNavigation.vue`

- 继续负责侧边栏结构。
- 增加底部「关于我」入口。
- 通过 `openAbout` 事件通知上层，不直接管理弹层。

### `AboutMeDialog.vue`

- 负责名片弹层、联系方式展示、复制和外部跳转。
- 通过 props 接收公开资料。
- 通过 `close` 事件交还关闭控制。

### `App.vue`

- 只管理弹层是否打开。
- 将现有公开资料传给名片弹层。
- 不把「关于我」建模成新的 Feed 路由。

### 站点公开资料链路

- 扩展公开资料协议、存储和设置表单。
- 联系方式与头像、Bio 使用同一加载和保存入口。

## 14. 首版实施范围

1. 桌面端侧边栏底部增加「关于我」。
2. 移动端频道导航增加「关于我」入口。
3. 新增响应式个人名片弹层。
4. 复用现有头像和 Bio。
5. 扩展公开资料以维护并返回联系方式。
6. 设置页增加固定类型的联系方式编辑区。
7. 完成链接跳转与复制反馈。

## 15. 后续可选演进

当个人介绍内容明显超过一张名片能够承载的范围时，再考虑：

- 独立 `/about` 页面和可分享链接。
- 微信二维码。
- 更长的个人介绍或经历时间线。
- 常用链接分组。
- 从个人名片进入完整关于页面。

这些能力不进入首版。

## 16. 验收场景

1. 访客在生活、文章或兴趣频道任意滚动位置点击「关于我」，关闭后仍停留在原频道和原位置。
2. 桌面端入口稳定位于侧边栏底部，不随信息流滚动。
3. 移动端可以直接找到「关于我」，点击后不切换当前频道。
4. 弹层显示与首页一致的头像和 Bio。
5. 只展示已启用且内容完整的联系方式。
6. 可跳转渠道按预期打开，复制型渠道提供明确成功消息。
7. 文章、生活、兴趣三个频道的缓存和滚动恢复不受影响。

## 17. 待确认问题

1. 首版实际需要公开哪些联系方式：Telegram、Email、微信、GitHub、个人链接中的哪些？
2. 微信首版只复制微信号是否足够，还是必须同时展示二维码？
3. 移动端把「关于我」作为第四个横向项是否符合预期？
4. 名片中的介绍是否直接复用现有 Bio，还是未来需要一段更长的「关于我」正文？

推荐首版选择：Telegram、Email、微信号复制和 GitHub；暂不做微信二维码；移动端使用第四个横向入口；介绍直接复用 Bio。
