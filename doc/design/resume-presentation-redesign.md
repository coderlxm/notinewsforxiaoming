# 个人简历展示严重偏差与呈现层重构建议

## 1. 问题定级

当前个人简历功能的数据上传、访问权限、限时分享和原文件下载主路径已经建立，但公开阅读体验与产品目标存在严重偏差。

该问题不是局部样式瑕疵，而是呈现模型选择错误：当前实现把“能打开上传文件”当成了“完成简历展示”，没有把简历作为个人站点中直接代表个人形象的独立内容类型处理。

现状不适合作为正式的对外简历页面。后续不应继续通过调整 iframe 圆角、间距或颜色修补，而应替换 PDF 和 Markdown 的正文渲染方式。

## 2. 当前实现事实

以下结论来自当前源码和实际页面截图：

- `PdfResumeViewer.vue` 使用同源 `<iframe>` 直接打开浏览器原生 PDF 阅读器。
- 浏览器自行绘制 PDF 工具栏、缩略图侧栏、页码、缩放、下载、打印和其他扩展功能，站点 CSS 无法控制这些区域。
- `ResumeView.vue` 在 iframe 外部还提供返回、文件信息和下载操作，形成两套相互重复的页面工具栏。
- `MarkdownResumeViewer.vue` 将经过服务端清洗的 HTML 按通用长文章排版渲染，采用文章式阅读宽度、标题节奏、段落行距和代码、表格样式。
- PDF 和 Markdown 虽然复用了站点颜色与字体变量，但没有共享一套“这是个人简历”的信息层级和视觉语言。

实际 PDF 页面表现为：深色站点外壳内部嵌入一套完整的深色浏览器阅读器，阅读器内部再展示白色 PDF 页面。页面存在三层视觉系统，割裂感明显。

## 3. 根因

### 3.1 PDF 的根因

原方案优先考虑了实现短、零新增渲染依赖、保留 PDF 文本选择和打印能力，因此选择浏览器原生 iframe。

这个选择适用于后台管理、内部资料或临时文件预览，但不适用于公开个人简历。原生阅读器具有以下不可消除的问题：

- UI 由浏览器决定，不同浏览器和设备的表现不一致。
- 原生工具栏、缩略图栏和扩展功能不能融入本站视觉风格。
- 页面外层操作与阅读器内部操作重复。
- 移动端可能只展示首屏、跳转到独立阅读器或使用完全不同的交互。
- 使用 `#toolbar=0` 等 PDF fragment 参数隐藏控件并非可靠、跨浏览器的产品方案，也不能解决内容区域的视觉归属问题。

### 3.2 Markdown 的根因

Markdown 只被当成了另一种文章来源。通用 Markdown HTML 能表达标题、段落和列表，却不能自动表达简历中的稳定语义，例如：

- 姓名、目标职位和个人概要；
- 联系方式；
- 公司、职位、任职时间和职责；
- 项目名称、角色、技术栈和成果；
- 教育经历；
- 技能分组。

没有语义约定时，前端只能套用通用文章 CSS，因此即使继续压缩行距、修改字体或增加分隔线，结果仍然更像博客文章，而不是简历。

### 3.3 设计阶段遗漏

此前方案过度强调“不新增复杂渲染系统”，低估了以下事实：

- 简历不是普通附件，而是面向招聘者和合作方的核心个人形象页面。
- “内容可以阅读”不等于“内容适合公开展示”。
- PDF 与 Markdown 是输入格式，不应该直接决定最终产品界面。
- 权限与文件管理完成，并不能代替独立的简历呈现设计。

## 4. 业内常见做法

### 4.1 结构化简历页面

简历生成器和高质量个人站点通常把经历、教育、技能等内容保存为结构化数据，再交给主题系统生成网页和 PDF。

- [Reactive Resume](https://docs.rxresu.me/use-cases/export-and-share-resumes)把公开简历链接与 PDF 导出视为两种并列用途：网页链接用于阅读当前版本，PDF 用于投递、邮件和固定版本留档。
- [JSON Resume](https://www.jsonresume.org/themes)使用标准简历数据和主题系统生成多种简历页面，而不是把任意 Markdown 当作普通文章直接展示。

这种方式能获得最完整的响应式布局、主题控制和信息层级，但要求输入内容遵循明确的数据结构。

### 4.2 品牌化文档阅读器

当产品必须忠实展示用户上传的 PDF 时，成熟文档分享产品通常提供自己的阅读器外壳，而不是暴露浏览器原生阅读器。

- [Dropbox DocSend](https://help.dropbox.com/account-settings/dropbox-docsend-custom-branding?fallback=true)把阅读器品牌、Logo 和强调色作为正式能力。
- [PDF.js](https://mozilla.github.io/pdf.js/examples/)提供 PDF 页面解析和 Canvas 渲染能力，产品可以只保留自己需要的页面、缩放和下载交互。

这种方式保留 PDF 的固定排版，同时让页面工具栏、背景、间距、翻页和加载状态归属于站点本身。

### 4.3 浏览器原生 iframe

原生 iframe/embed 仍常见于低成本 CMS、后台预览和内部文档页面。它的主要价值是开发成本低，而不是呈现质量高。

因此，当前方案并非技术上罕见，但用在本站的公开个人简历上属于产品层级不匹配。

## 5. 推荐目标

保留现有上传、替换、权限、分享、下载和服务端授权体系，只重构公开呈现层。

PDF 与 Markdown 不强求正文完全一致，但必须共享同一套页面外壳：

- 页面只保留一套站点控制的工具栏。
- 返回、权限状态、更新时间、分享和下载操作使用项目现有视觉语言。
- 正文区域明确进入“简历阅读模式”，不继续沿用文章详情页。
- 浅色与深色主题控制页面背景、工具栏和容器；PDF 纸张本身保持原始颜色。
- 手机、平板和桌面使用同一个响应式布局模型。

## 6. PDF 改进建议

### 6.1 推荐呈现

将当前 iframe 替换为站点控制的极简页面阅读器：

- PDF 页面按纵向纸张流居中排列。
- 页面之间保留明确但克制的间距和阴影，背景使用站点中性色，形成有意设计的“桌面上的纸张”效果。
- 默认适配内容区宽度，不在首屏显示缩略图侧栏。
- 工具栏只保留当前页/总页数、缩放、下载等真实需要的操作。
- 下载仍返回原始 PDF，不以预览产物替代原文件。
- 只加载视口附近页面，避免一次渲染较长 PDF 的全部高分辨率页面。

### 6.2 技术路线 A：PDF.js 自定义阅读器

这是最接近业内常规做法、交互质量最高的路线：使用 PDF.js 的解析与页面渲染能力，不使用其完整默认 Viewer UI，由本站实现极简外壳。

优点：

- 页面布局和工具栏可以完全融入项目。
- 可以保留较好的缩放、页码、文本层和链接能力。
- 浏览器端不需要新增服务端 PDF 转换基础设施。

限制：

- PDF.js 内部渲染调度会涉及 `requestAnimationFrame`。
- 当前项目规则禁止任何 RAF，因此采用该路线前必须由用户明确决定是否允许成熟第三方 PDF 渲染库内部使用 RAF。
- 未解决该规则冲突前，不得直接开始实现。

### 6.3 技术路线 B：上传时服务端生成页面预览

如果 RAF 禁令保持不变，可在上传 PDF 时由服务端把每页生成固定预览图，前端只展示页面图片流，原 PDF 继续负责下载。

优点：

- 前端结构简单、风格完全可控。
- 页面图片可以按站点图片策略加载，不需要浏览器 PDF Viewer。
- 不触碰前端 RAF 禁令。

限制：

- 需要引入可靠的 PDF 页面渲染能力及相应运行环境。
- 预览文字不能自然选择，PDF 内部链接不可交互。
- 需要保存和清理派生页面文件，上传处理链会明显变重。

### 6.4 不建议路线

- 继续保留 iframe，只隐藏部分浏览器工具栏。
- 用 CSS 包裹 iframe 伪装成站点组件。
- 接入 Google Docs Viewer 等第三方在线阅读器。
- 把 PDF 自动转换成无法保证版式正确的 HTML。

这些方式不能稳定解决当前核心问题，或者会引入隐私、外部依赖和版式失真。

## 7. Markdown 改进建议

### 7.1 建立简历 Markdown 约定

Markdown 应作为简历内容的编辑格式，而不是最终布局格式。建议为首版提供一份明确模板，并按 Markdown AST 的结构映射简历语义：

- 一级标题：姓名；
- 标题后的固定区域：目标职位、联系方式和个人概要；
- 二级标题：工作经历、项目经历、教育经历、技能等一级分区；
- 三级标题：公司、项目或学校；
- 三级标题后的辅助行：职位、时间、地点或技术栈；
- 列表：职责、行动和成果。

不建议使用文本正则猜测任意 Markdown 的含义。若文件不符合简历模板，应在上传阶段直接指出结构问题，不应静默退回文章样式。

### 7.2 简历专用主题

Markdown 简历页面应具备独立的视觉结构：

- 姓名和目标职位形成清晰的首屏身份区。
- 联系方式紧凑排列，不占用文章式段落高度。
- 一级分区使用统一标题线或时间轴结构。
- 公司/项目名称、角色和日期形成稳定的左右关系。
- 职责列表降低段间距，提高单位屏幕的信息密度。
- 技能按分组或紧凑标签展示。
- 桌面端利用横向空间，手机端自然改为单列，不依赖 JavaScript 测量。

Markdown 页面可以响应站点的浅色、深色和跟随系统主题；PDF 纸张则忠实保留原始视觉，两者通过共享外壳保持整体一致。

## 8. 保留不变的能力

本次呈现重构不应重做以下已经建立的能力：

- Markdown/PDF 文件上传与替换；
- 仅自己可见、访问口令、限时链接和完全公开；
- 访问 Cookie、授权失效和限时到期判断；
- About 页面入口；
- 原文件下载；
- 管理端的权限设置与链接生成。

访问判断必须继续覆盖简历内容接口、PDF/预览资源和下载接口，不能只保护页面外壳。

## 9. 建议实施顺序

1. 先确认 PDF 路线：允许 PDF.js 内部 RAF，或坚持服务端页面预览。
2. 建立统一的 `ResumeShell` 页面外壳，移除 iframe 内外两套工具栏并存的结构。
3. 替换 PDF 正文渲染器，形成自有的页面阅读体验。
4. 定义简历 Markdown 模板和结构约束。
5. 将 Markdown token 映射为简历语义组件，替换通用文章排版。
6. 调整 About 入口和简历页元信息，使其与新的呈现层一致。

## 10. 完成标准

重构后的结果应满足：

- 页面中不再出现浏览器原生 PDF 工具栏和缩略图侧栏。
- PDF 页面看起来属于当前站点，而不是嵌入的第三方应用。
- PDF 与 Markdown 都能在首屏明确表达姓名、职位和简历身份。
- Markdown 不再呈现为普通博客文章。
- 页面只存在一套操作区，不重复提供下载、缩放等能力。
- 手机、平板和桌面均不产生横向溢出或依赖浏览器专属 PDF 行为。
- 权限、限时分享、下载和旧授权失效逻辑保持不变。

## 11. 当前决策状态

当前 iframe PDF 预览和文章式 Markdown 预览应视为需要替换的临时实现，不再继续进行局部视觉优化。

正式开发前唯一需要用户确认的关键决策是：是否允许 PDF.js 这类成熟第三方 PDF 渲染库在其内部使用 RAF。该决定会直接确定 PDF 重构采用浏览器端自定义阅读器，还是上传时服务端生成页面预览。
