# Journal 公开内容分层与访客主页改造建议

- 状态：产品建议稿
- 日期：2026-07-20
- 适用范围：Journal 公开主页、公开分类页、Telegram Journal 保存结果卡片
- 关联文档：
  - `doc/design/telegram-journal-personal-feed.md`
  - `doc/design/telegram-journal-rich-blog.md`
  - `doc/design/journal-waterfall-layout-redesign.md`
  - `doc/design/journal-waterfall-layout-vue-masonry-alternative.md`

## 1. 结论

推荐把当前“所有公开内容直接进入同一个瀑布流”的结构改为：

> **一个有编辑感的访客主页 + 三条内容栏目 + 一个完整公开档案。**

三个栏目分别是：

1. **文章**：Web 富文本长内容；
2. **生活**：照片、视频、语音和日常文字等生活片段；
3. **随记**：短想法、观察、链接备注和临时感受。

首页不再承担“展示所有公开数据”的任务，只展示每个栏目的少量最近内容，并把访客引导到对应栏目。原有完整瀑布流保留到“全部档案”，继续承担时间浏览、标签浏览和分页。

`/note` 与 `/post` 继续只表达可见性，不承担栏目分类：

- `/note`：私有；
- `/post`：公开；
- 文章：由 Web 文章编辑器创建；
- 生活或随记：作为普通记录的展示栏目单独管理。

不新增 `/life`、`/thought` 等 Telegram 命令，不要求每次保存前选择分类，也不根据文字长度、是否带图片等条件自动猜测栏目。

## 2. 当前问题

当前公开首页只有一条按时间排序的信息流。以下内容使用相同层级和相近卡片密度连续出现：

- 有封面、标题和摘要的长文章；
- 照片、视频、语音等生活记录；
- 只有一两句话的随手想法；
- 不同标签、不同阅读时长和不同视觉重量的内容。

瀑布流解决了空间利用和卡片高度问题，但没有解决内容层级问题。内容增加后，访客面对的是“公开数据库的最新结果”，而不是一个能够快速理解的个人主页。

问题不在于卡片样式不够丰富，而在于首页同时承担了三个互相冲突的任务：

1. 展示站点主人是谁；
2. 呈现值得访客先看的内容；
3. 提供完整历史档案。

继续给卡片增加颜色、角标或图标，只会让同一条混合信息流更热闹，不能形成稳定的浏览预期。

## 3. 产品目标与边界

### 3.1 访客主页的单一任务

访客主页只回答一个问题：

> **最近的小明在生活什么、思考什么、认真写了什么？**

访客无需先理解 Telegram 命令、媒体类型或 Journal 数据结构，也不需要在一整页混合卡片中自行辨认内容性质。

### 3.2 公开档案的单一任务

公开档案负责完整性：

- 按时间浏览全部公开内容；
- 按栏目查看；
- 按标签进入专题；
- 继续分页查看更早记录。

### 3.3 不做的事情

- 不把 Journal 拆成三个独立子系统；
- 不建立多级栏目树；
- 不引入 AI 自动分类；
- 不根据媒体类型推断“生活”或“随记”；
- 不强迫 Telegram 每次记录都经过分类选择；
- 不改变 `/note` 私有、`/post` 公开的稳定语义；
- 不把现有标签改造成栏目；
- 不增加无限滚动、推荐算法或访客个性化排序。

## 4. 内容模型

### 4.1 保留现有维度

当前已有字段的职责继续保持：

| 维度 | 当前含义 | 是否改变 |
| --- | --- | --- |
| `visibility` | `private` / `public` | 不改变 |
| `bodyFormat` | `plain` / `rich`，区分普通记录与文章 | 不改变 |
| `contentType` | text、photo、video、voice、article 等载体形态 | 不改变 |
| `tags` | 跑步、旅行、技术等内容主题 | 不改变 |
| `pinned` | 在时间流中置顶 | 不改变，不复用为栏目 |

`visibility` 回答“谁能看”，`bodyFormat` 回答“是不是文章”，`contentType` 回答“内容以什么形式保存”，`tags` 回答“内容在谈什么”。这些维度都不适合同时承担“访客应在哪个栏目看到它”。

### 4.2 新增普通记录栏目

建议只为 `bodyFormat = plain` 的普通记录增加一个明确的栏目字段：

```ts
type JournalPlainCategory = 'life' | 'thought';
```

推荐数据库语义：

```text
plain_category = life | thought | null
```

- Telegram 普通记录：保存时默认为 `life`；
- Web 富文本文章：固定为 `null`，由 `bodyFormat = rich` 进入文章栏目；
- 普通记录不能进入文章栏目；
- 文章不出现“生活 / 随记”切换操作。

最终公开栏目由两个现有维度共同确定：

| 条件 | 公开栏目 |
| --- | --- |
| `bodyFormat = rich` | 文章 |
| `bodyFormat = plain` 且 `plainCategory = life` | 生活 |
| `bodyFormat = plain` 且 `plainCategory = thought` | 随记 |

### 4.3 为什么不使用标签充当栏目

现有 `#生活`、`#随笔` 等标签描述内容主题，用户可以同时添加多个。栏目则是访客界面的一级结构，一条普通记录只能选择一个。

如果把 `#随记` 约定成系统标签，会产生三类长期问题：

- 删除正文中的标签会意外改变栏目；
- 标签既要展示主题，又要承担系统控制语义；
- 以后修改栏目名称会牵动历史正文。

因此栏目应是独立字段，标签继续保持自由内容属性。

## 5. 信息架构

推荐公开站点路径：

| 页面 | 路径建议 | 职责 |
| --- | --- | --- |
| 访客主页 | `/` | 分栏目展示少量最近内容 |
| 生活 | `/life` | 普通生活记录瀑布流 |
| 随记 | `/thoughts` | 简洁的短记录时间流 |
| 文章 | `/articles` | 文章列表与摘要 |
| 全部档案 | `/archive` | 所有公开内容的完整瀑布流 |
| 公开详情 | `/p/:publicId` | 保持现有稳定链接 |

全局 Profile Bar 保持两项主导航：

- `公开主页`
- `我的资产`

公开区域内部增加一行非吸顶的栏目导航：

```text
首页   生活   随记   文章   全部档案
```

它属于公开内容本身，不进入全局吸顶 Profile Bar，避免桌面和移动端出现两层长期占位的导航。

## 6. 访客主页结构

首页不再直接渲染一个可无限分页的混合瀑布流。建议固定为三个有明确节奏的内容区：

```text
┌─────────────────────────────────────────────────────────────┐
│ Profile Bar：头像 / 简介               公开主页 / 我的资产 │
├─────────────────────────────────────────────────────────────┤
│ 首页       生活       随记       文章       全部档案       │
├─────────────────────────────────────────────────────────────┤
│ 最近文章                                           查看全部 │
│ ┌──────────────────┐ ┌──────────────────┐ ┌──────────────┐ │
│ │ 封面 / 标题 / 摘要 │ │ 标题 / 摘要      │ │ 标题 / 摘要  │ │
│ └──────────────────┘ └──────────────────┘ └──────────────┘ │
├─────────────────────────────────────────────────────────────┤
│ 生活片段                                           查看全部 │
│ ┌──────────┐ ┌──────────────┐ ┌──────────┐ ┌────────────┐ │
│ │ 图片记录  │ │ 视频 / 文字   │ │ 日常照片  │ │ 生活文字    │ │
│ └──────────┘ └──────────────┘ └──────────┘ └────────────┘ │
├─────────────────────────────────────────────────────────────┤
│ 最近随记                                           查看全部 │
│ JUL 20  一段简短想法或观察                                 │
│ JUL 18  一条链接备注                                       │
│ JUL 16  临时记下的一句话                                   │
└─────────────────────────────────────────────────────────────┘
```

建议首期数量：

| 区域 | 首页数量 | 表现形式 |
| --- | ---: | --- |
| 最近文章 | 3 | 封面、标题和摘要组成的编辑式列表 |
| 生活片段 | 8 | 继续复用当前瀑布流 |
| 最近随记 | 6 | 紧凑的单列时间流，不使用大卡片 |

首页三个区域均不提供“加载更多”，只提供“查看全部”。这样首页长度和信息密度始终可预期，数据增长不会把主页重新变成完整数据库。

区域为空时直接不渲染该区域，不拿其他栏目内容补位。

## 7. 三种内容采用三种阅读节奏

分类本身不足以解决混乱。三个栏目还应根据内容的阅读方式采用不同布局。

### 7.1 文章：主动阅读

- 强调标题、封面和摘要；
- 桌面端可以一张主文章加两张次级文章，或统一三张编辑式卡片；
- 栏目页使用较宽的单列或双列，不把长文章摘要塞进四列瀑布流；
- 日期退居辅助信息。

### 7.2 生活：视觉扫读

- 继续使用已经落地的 `@egjs/grid` 瀑布流；
- 图片和视频保留自然比例；
- 桌面 4 / 3 / 2 列、移动端双列的规则不改变；
- 保持加载更早记录和分页追加动画。

### 7.3 随记：连续轻读

- 使用紧凑的单列时间流；
- 每条保留日期、正文、标签，不使用大面积卡片边框；
- 多媒体仍可正常展示，但不以媒体尺寸决定栏目；
- 重点是让访客连续阅读思想片段，而不是在瀑布流中寻找短文字卡片。

三种节奏共同构成站点的识别点：文章像书页，生活像相册，随记像页边批注。它们继续使用同一套颜色、字体和日期书脊，因此不会变成三个互不相关的产品。

## 8. Telegram 记录路径

### 8.1 保持现有主路径

现有命令完全不变：

```text
/note 内容     -> 私有普通记录，默认生活
/post 内容     -> 公开普通记录，默认生活
Web 写文章      -> 私有文章，发布后进入文章栏目
```

“生活”作为普通记录默认值，是因为它是最宽泛、最不要求判断的容器。用户不需要在记录当下回答“这句话究竟算生活还是思想”。

### 8.2 随记作为可选整理动作

公开普通记录保存成功后，在现有结果卡片中增加一个栏目操作：

```text
已保存为公开动态 · 栏目：生活

[改为随记] [🔒 转为私有] [🌍 打开网站]
[🗑 删除]
```

点击后直接编辑原结果卡片：

```text
已保存为公开动态 · 栏目：随记

[改为生活] [🔒 转为私有] [🌍 打开网站]
[🗑 删除]
```

这符合现有 Telegram 交互原则：

- 默认保存路径不增加步骤；
- 只有需要区分随记时才点击一次；
- 复用并编辑现有结果消息，不产生新消息；
- 栏目与公开状态分别控制，不互相覆盖。

私有记录可以保存 `plainCategory`，但私有状态下无需在 Telegram 结果卡片突出栏目；当它被设为公开时，使用已经保存的栏目值。

### 8.3 私有 Web 管理

普通记录的管理菜单增加：

```text
移动到栏目
├── 生活
└── 随记
```

文章管理菜单不显示该项。栏目修改只更新当前记录，不重新创建内容、不改变公开链接，也不改变可见性。

## 9. 视觉方向

本次不重做已经稳定的视觉系统，继续复用当前 Token：

| Token | 色值 | 用途 |
| --- | --- | --- |
| Paper | `#F7F7F5` | 页面背景 |
| Card | `#FFFFFF` | 卡片表面 |
| Ink | `#20201E` | 主文字 |
| Graphite | `#72716C` | 日期、摘要和辅助信息 |
| Pomegranate | `#C43B46` | 当前栏目、链接和强调 |

字体继续保持：

- 标题和文章：`Noto Serif SC` / 系统宋体；
- 正文和交互：Inter / 系统无衬线；
- 日期书脊：现有 condensed 字体。

栏目不使用三套高饱和配色区分。结构、排版密度和内容形态已经足够表达差异，额外颜色会重新制造杂乱感。

移动端继续保留吸顶 Profile Bar；栏目导航和首页区块标题正常滚走。生活栏保持双列，文章和随记改为单列。

## 10. 数据与接口影响

### 10.1 数据迁移

历史数据采用一次性确定规则：

- `bodyFormat = rich`：保持文章，不写普通记录栏目；
- `bodyFormat = plain`：统一写入 `life`；
- 不根据历史标签、正文长度或附件类型自动迁移到 `thought`；
- 需要归入随记的历史记录由私有 Web 管理页面手动调整。

这个规则不会误判历史内容，也不会让未来产品规则依赖一次性的文本启发式逻辑。

### 10.2 公开读取

公开查询增加明确栏目条件：

```text
category=life
category=thought
category=article
```

文章条件由 `bodyFormat = rich` 决定，普通栏目条件由 `plainCategory` 决定。`contentType` 继续只用于媒体格式筛选。

首页建议提供一个聚合读取结果，固定返回三个限量数组：

```ts
interface PublicHome {
  articles: JournalEntry[];
  lifeEntries: JournalEntry[];
  thoughts: JournalEntry[];
}
```

栏目页和全部档案继续使用现有游标分页。

### 10.3 Feed 与稳定链接

- `/p/:publicId` 不改变；
- 现有 RSS 和 JSON Feed 继续按时间包含全部公开内容；
- 首期不为三个栏目分别创建订阅源；
- 标签链接进入完整公开档案并携带标签条件，不把标签绑定到单一栏目。

## 11. 方案比较

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 只给卡片加“文章 / 日常 / 随记”角标 | 实现最少 | 仍是同一条混合瀑布流，访客仍需自行筛选 | 不采用 |
| 只在首页增加三个筛选 Tab | 可以快速切换 | 首次访问只能看到其中一种内容，主页仍等于列表页 | 作为栏目页导航，不作为完整答案 |
| 只展示置顶内容 | 主页很干净 | 每次公开后还要额外维护置顶，且 `pinned` 语义被放大 | 不作为首页主结构 |
| AI 自动判断生活或随记 | 用户操作少 | 分类不可预测，出错后需要纠正，增加非主路径依赖 | 不采用 |
| 新增 Telegram 分类命令 | 分类明确 | 扩大命令表，混淆“公开状态”和“内容栏目” | 不采用 |
| 访客主页分区 + 栏目页 + 完整档案 | 主页清晰、历史完整、采集路径不变 | 需要新增普通记录栏目和首页聚合 | 推荐 |

## 12. 推荐实施顺序

### 第一阶段：先建立栏目事实

1. 增加普通记录 `life / thought` 栏目字段；
2. 历史普通记录统一迁移为 `life`；
3. 私有 Web 管理菜单支持切换栏目；
4. Telegram 公开结果卡片支持在生活和随记之间切换。

这一阶段完成后，数据已经可以稳定表达栏目，公开页面仍可暂时保持原样。

### 第二阶段：拆分公开浏览

1. 增加生活、随记、文章和全部档案路径；
2. 分类页复用现有详情、标签和分页能力；
3. 生活栏目复用瀑布流；
4. 文章与随记使用各自的阅读布局。

### 第三阶段：把 `/` 改为访客主页

1. 首页改为三个限量区块；
2. 每个区块提供“查看全部”；
3. 首页取消混合瀑布流分页；
4. 全量历史浏览迁移到 `/archive`。

## 13. 产品验收标准

- 第一次访问主页时，无需滚动很远即可辨认文章、生活和随记三个内容层级；
- `/note` 和 `/post` 的含义、输入方式和默认成功路径不改变；
- 保存一条普通 `/post` 不需要先选择栏目；
- 用户可以在同一条 Telegram 结果卡片中把公开记录切换为随记，并且不新增消息；
- 文章不会出现在生活或随记栏目；
- 生活、随记和文章栏目均能独立分页浏览；
- 全部档案仍能按统一时间线看到所有公开内容；
- 标签、公开详情链接、RSS 和 JSON Feed 保持连续；
- 首页内容数量固定，不随数据库总量持续拉长；
- 移动端 Profile Bar 只有一层吸顶区域。

## 14. 最终建议

本项目的采集端和展示端应明确分工：

- Telegram 负责尽可能低成本地记录和决定公开状态；
- 私有 Web 负责必要的整理；
- 公开主页负责让访客理解内容；
- 公开档案负责保存完整时间线。

因此，不应让 `/note`、`/post` 承担更多产品语义，也不应继续让首页直接等同于数据库列表。以“主页分区、栏目浏览、完整档案”三层结构组织内容，可以在不牺牲现有记录效率的前提下，长期容纳越来越丰富的文章、生活与随记。
