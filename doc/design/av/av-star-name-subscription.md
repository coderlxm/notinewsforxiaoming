# AV 女优名订阅设计

## 1. 目标

在现有 `/avsub` 基础上补一个“按女优名添加订阅”的入口，解决下面这类使用问题：

- 用户习惯输入的是简体中文名
- JavBus 实际收录的是繁体、日文汉字、假名混写，甚至是别名
- 用户不知道对应的 `star/<id>`，也不方便每次先去站内人工搜索

本次目标不是做一个通用 AV 搜索系统，而是补齐一个高频、低心智负担的订阅入口：

- 用户给出“自己习惯输入的女优名”
- bot 借助 DeepSeek 把名字转换成更接近 JavBus 实际收录的候选名
- 再到 JavBus 搜索并验证是否存在唯一女优目标
- 成功后仍然回到现有 `star/<id>` 订阅主路径

## 2. 当前问题

当前 `/avsub add` 只支持完整 JavBus URL。

这条主路径本身没有问题，但对“只知道中文常用名”的场景不友好：

- `流川春香` 这类简体中文输入，未必能直接命中 JavBus 收录名 `流川はる香`
- 用户自己常用的中文别名，未必等于 JavBus 的 canonical 名
- 问题不只是简繁转换，还包含假名、异体字、站内别名

结果就是：

- 用户知道想订谁，但不知道站内实际名字
- 也不知道对应的 `star/<id>`
- 只能手动去站内反复搜索，再复制 URL

## 3. 为什么不做纯简繁转换

这次不建议做纯规则转换，也不建议只接 `opencc` 之类的简繁库。

原因很直接：

- 这个问题不只是“简体 -> 繁体”
- 还会遇到日文假名混写
- 还会遇到站内使用的别名或旧艺名

像 `流川春香 -> 流川はる香` 这种情况，单靠字符集转换并不能得到可搜索结果。

因此这次更合适的方案是：

- 用 AI 做“一次性名称归一”
- 再用 JavBus 实际搜索结果做最终校验

AI 负责给候选名，JavBus 负责验证存在性，避免把“是否真的有这个女优”交给模型瞎猜。

## 4. 方案选择

### 4.1 方案 A：纯规则转换

做法：

- 用户输入名字后
- 只做简繁转换、空格清洗、少量字符替换
- 然后直接去 JavBus 搜索

不选原因：

- 覆盖不了假名混写
- 覆盖不了别名
- 命中率不稳定

### 4.2 方案 B：AI 生成候选名 + JavBus 搜索验证

做法：

- DeepSeek 先把用户输入转成 1 组可能的 JavBus 女优名候选
- 再逐个去 JavBus 搜索
- 从搜索结果里提取 `/star/<id>`，确认是否存在唯一目标

这是本次推荐方案。

原因：

- 只在“新增订阅时”调用 AI，不进入定时抓取主链路
- 既能处理简繁，也能处理假名和别名
- 最终是否成功仍由 JavBus 搜索结果决定，不靠 AI 直接拍板

### 4.3 方案 C：做通用名称搜索，支持女优 / 系列 / 制作商 / 发行商

这次不做。

原因：

- 用户当前痛点明确集中在女优名
- 系列 / 制作商 / 发行商的名称搜索语义不一样
- 一次把所有类型都做进来，会明显抬高交互和判定复杂度

本次先只支持“女优名 -> `star/<id>`”。

## 5. 设计结论

### 5.1 命令入口

建议新增专门子命令：

- `/avsub addstar <女优名>`

而不是把现有 `/avsub add` 改成“既吃 URL 又吃名字”的混合入口。

原因：

- 保持现有 `/avsub add <javbus_url>` 语义稳定
- 明确告诉用户：当前只支持“女优名”这一个名称入口
- 避免把“缺协议的错误 URL”误判成名字搜索

首版帮助文案示例：

```text
AV 订阅管理
• /avsub add https://www.javbus.com/star/vwq
• /avsub addstar 流川春香
• /avsub list
• /avsub remove 3
```

### 5.2 用户链路

`/avsub addstar 流川春香`

处理顺序：

1. 清洗输入名称
2. 调 DeepSeek 生成候选收录名
3. 逐个到 JavBus 搜索候选名
4. 从搜索结果里提取 `/star/<id>`
5. 如果存在唯一目标，则组装 `https://www.javbus.com/star/<id>`
6. 复用现有 `resolveAvSubscription()` 继续探测订阅名称
7. 复用现有去重、入库、立即检查这条主路径

也就是说，这次新增功能只负责把“女优名”解析成“现有 URL 订阅主路径可接受的目标 URL”。

后半段不另写一套订阅逻辑。

### 5.3 DeepSeek 的职责边界

DeepSeek 只做一件事：

- 根据用户输入，输出最多 3 个“可能是 JavBus 实际收录名”的女优名候选

它不直接决定订阅是否成功，也不直接输出 `star/<id>`。

建议返回固定 JSON：

```json
{
  "candidates": ["流川はる香", "流川春香", "流川春香(别名)"]
}
```

约束：

- 只返回 JSON
- `candidates` 最多 3 个
- 按命中概率从高到低排序
- 不要解释
- 没把握时不要乱编过多候选

这样做的好处是：

- AI 输出形态稳定
- 后续搜索逻辑简单
- 对源站请求数有明确上限

### 5.4 JavBus 搜索验证

搜索层建议独立成一个单独 service，不把外站细节散落到 bot handler 里。

截至 2026-07-05，本地检查 JavBus 页面脚本时，站内搜索入口会拼出：

- `https://www.javbus.com/search/<keyword>&type=&parent=ce`

结合当前部署前提，实际搜索请求会从美国 VPS 发出，这次不考虑大陆区域才会遇到的年龄验证页分支。

因此实现时只需要把这件事封装在搜索 service 里：

- 搜索 URL 组装

业务层只感知：

- `searchJavBusStarsByName(name) -> StarSearchHit[]`

不感知 JavBus 搜索页细节。

### 5.5 搜索结果判定规则

对每个候选名，按顺序串行执行搜索。

每次搜索后的判定规则：

1. 从返回 HTML 中提取所有 `/star/<id>` 链接
2. 按 `targetId` 去重
3. 得到当前候选名对应的唯一女优集合

分支如下：

- 如果去重后是 `0` 个：继续尝试下一个候选名
- 如果去重后是 `1` 个：直接认定命中，结束搜索
- 如果去重后大于 `1` 个：记录为歧义结果，继续尝试下一个候选名

全部候选跑完后的最终判定：

- 命中过唯一目标：成功
- 一个都没命中：报“未找到对应 JavBus 女优，请改用完整链接”
- 只出现歧义结果：报“匹配到多个女优，请改用完整链接”，并附上候选链接

这里不做自动二次猜测，不让 AI 再替我们做最后仲裁。

## 6. 交互和报错策略

### 6.1 成功

沿用现有成功链路：

- 添加订阅成功
- 立即只检查这个新订阅一次

示例：

```text
已添加 AV 订阅：流川はる香 [女优]
https://www.javbus.com/star/xxxx
开始立即检查这个订阅...
```

### 6.2 DeepSeek 不可用

如果没有 `DEEPSEEK_API_KEY`，直接报错。

这次功能的设计前提就是“让 AI 负责一次名字归一”，不做纯规则兜底。

示例：

```text
AV 订阅操作失败：未配置 DEEPSEEK_API_KEY，当前无法按女优名添加订阅。
```

### 6.3 没找到

示例：

```text
AV 订阅操作失败：未找到对应的 JavBus 女优，请改用完整链接。
```

### 6.4 多结果歧义

示例：

```text
AV 订阅操作失败：匹配到多个 JavBus 女优，请改用完整链接：
https://www.javbus.com/star/aaa
https://www.javbus.com/star/bbb
```

## 7. 性能影响

这次方案对现有定时 `av_update` 没有新增成本。

新增成本只发生在 `/avsub addstar` 当下，而且成本边界明确：

- 1 次 DeepSeek 调用
- 最多 3 次 JavBus 搜索请求
- 串行执行，不并发打源站

这符合当前项目的性能约束：

- 不把 AI 带进定时任务
- 不把搜索带进定时任务
- 不对 JavBus 额外放大并发压力

## 8. 数据模型

这次不需要新增表，也不需要改 `tracked_targets` 结构。

原因：

- 最终落库的仍然是现有结构：`source + target_type + target_id + name`
- 新增能力只是“把名字解析成 star URL”
- 用户输入的原始名字不是运行时主数据，首版没有必要持久化

如果后面要统计“哪些中文别名最常见”，再考虑单独记录输入词。

本次先不做。

## 9. 代码落点

建议改动收敛在以下位置：

- `src/bot/interactive.ts`
  - 新增 `/avsub addstar <name>`
  - 更新 `/avsub` help 文案
- `src/services/avSubscriptionService.ts`
  - 保留现有 URL 解析逻辑
  - 新增“女优名 -> URL 订阅”解析入口
- `src/services/avStarNameResolver.ts`
  - 新文件
  - 负责 DeepSeek 候选名生成
  - 负责 JavBus 搜索验证
  - 只输出唯一 `star` 目标
- `src/ai/client.ts`
  - 复用现有 DeepSeek client

本次不需要改：

- `src/services/avTracker.ts`
- `src/services/avRepository.ts`
- `src/reminders/db.ts`

除非实现时发现需要补少量帮助函数，否则主链路不应被碰重。

## 10. 本次不做

这次明确不做下面这些扩展：

- 系列 / 制作商 / 发行商的名称添加
- `/avsub add` 自动兼容非 URL 文本
- 本地简繁词典缓存
- 名字搜索结果的交互式候选按钮
- 记录用户原始输入别名
- 用 AI 直接决定最终订阅对象

先把“女优名 -> 唯一 `star/<id>` -> 现有订阅主路径”打通即可。
