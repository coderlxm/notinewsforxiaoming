# Journal 首页固定侧边栏与内容频道 PRD

## 1. 文档状态

- 状态：已确认并进入实施
- 产品范围：公开首页及公开信息流
- 首版频道：生活、文章、兴趣
- 不涉及：我的资产、朋友投稿、文章详情、Telegram Bot 命令改版

## 2. 需求背景

当前所有公开内容都按发布时间进入首页同一条信息流。图片、视频、生活记录、长文章和兴趣内容混合展示，访客只能连续浏览，无法快速进入自己关心的内容。

不同访客的阅读目的并不一致：

- 有人只想看学习、工作及其他需要完整阅读的长文章；
- 有人更关心照片、视频和日常生活；
- 有人只想浏览游戏、摄影、设备等兴趣相关内容。

随着公开内容继续增长，首页需要从“全部内容的混合列表”演进为“有稳定入口的个人内容空间”。侧边栏用于长期承载一级内容入口，信息流负责展示当前入口下的内容。

## 3. 产品目标

1. 桌面端公开首页固定展示侧边栏，侧边栏不随内容滚动。
2. 页面纵向滚动只发生在信息流区域，站点身份区和侧边栏保持稳定。
3. 首版提供生活、文章、兴趣三个互斥频道，访客能一次点击切换内容范围。
4. 当前公开内容获得明确归属，不再全部无差别地混在首页。
5. 频道结构允许以后调整名称、顺序、图标、增加新频道，或在频道内继续细分，但首版不建设栏目后台和二级筛选栏。
6. 保留现有详情、标签、媒体展示和公开链接，不因频道改造复制内容。

## 4. 非目标

- 不引入推荐算法或根据访客画像自动排序；
- 不增加关注、点赞、收藏等社交能力；
- 首版不建设频道内标签栏、多级栏目树或频道管理后台；
- 不使用标签自动猜测频道；
- 不允许一条记录同时出现在多个一级频道；
- 不调整“我的资产”和朋友投稿页面布局；
- 不把侧边栏做成包含大量设置入口的后台导航。

## 5. 核心产品定义

### 5.1 频道是什么

频道是公开信息流的一级入口，回答“这条内容主要应该在哪个入口被访客看到”。首版频道为：

| 频道 | 内容口径 | 首版展示重点 |
| --- | --- | --- |
| 生活 | 日常文字、照片、视频、聚会和生活记录 | 继续采用媒体优先的瀑布流 |
| 文章 | 通过文章编辑器发布的长内容 | 强调标题、封面、摘要和阅读入口 |
| 兴趣 | 游戏、摄影、数码、影音等个人兴趣内容 | 首版继续复用瀑布流，内容增长后再决定是否拆分 |

频道与标签相互独立：

- 频道是唯一的一级归属，一条记录只能属于一个频道；
- 标签用于描述更细的主题，一条记录仍可拥有多个标签；
- `#摄影`、`#工作` 等标签不会自动决定频道；
- 修改标签不会改变频道；
- 生活、文章、兴趣三个一级频道未来都可以在各自信息流上方增加标签栏，用标签继续细分当前频道内的内容。

### 5.2 首版归属规则

- 文章编辑器创建的内容自动归入“文章”，不要求额外选择；
- 普通公开记录默认归入“生活”，不增加发布前的必选步骤；
- 需要进入“兴趣”的普通记录，由发布或编辑页面明确选择；
- 历史文章归入“文章”；
- 其余历史公开记录统一归入“生活”；
- 历史兴趣内容由站点主人后续手动整理，不根据正文、标签或附件进行自动判断。

这套规则优先保证现有发布主路径不被打断，同时让分类结果可以被理解和纠正。

## 6. 信息架构

### 6.1 桌面端结构

公开首页采用固定外壳与独立信息流滚动区：

```text
┌──────────────────────────────────────────────────────────────┐
│ 现有身份区：头像 / 小明同学 / Bio                           │
├───────────────┬──────────────────────────────────────────────┤
│ 固定侧边栏     │ 可滚动的信息流区域                          │
│               │                                              │
│ ● 生活         │ 当前频道标题 / 未来标签栏                    │
│   文章         │                                              │
│   兴趣         │ 当前频道内容                                 │
│               │                                              │
│ 未来底部扩展区  │                                              │
│               │ 加载更早内容                                 │
└───────────────┴──────────────────────────────────────────────┘
```

布局规则：

- 现有站点身份区继续位于页面顶部，不随信息流滚动；
- 身份区下方占据剩余视口高度；
- 侧边栏宽度首版控制在约 `200–224px`，固定在左侧；
- 信息流区域占据剩余宽度，并成为页面唯一纵向滚动容器；
- 侧边栏与信息流之间使用留白或细分隔线，不增加厚重卡片外框；
- 信息流宽度继续遵循现有瀑布流列数和卡片宽度规则，不因侧边栏出现而强行压缩卡片。

### 6.2 侧边栏内容

首版侧边栏可见内容只包含频道导航：

```text
生活
文章
兴趣
```

交互规则：

- 当前频道使用现有强调色、浅底和明确文字共同表示；
- 整行均可点击，不只让文字成为点击目标；
- 每个频道允许配置稳定标识、展示名称、图标和顺序；
- 首版不展示每个频道的内容数量，避免增加额外统计请求；
- 频道为空时仍保留入口，并在信息流区域显示真实空状态；
- 不提供“全部”入口，避免公开首页重新退化成混合信息流；
- 侧边栏结构分为上方主导航区和底部扩展区，首版底部扩展区不展示内容；
- 底部扩展区未来可承载“关于我”等低频全站内容，不与频道列表混排。

### 6.3 路由与默认频道

建议首版使用同一个公开首页路由，通过查询参数表达频道：

| 地址 | 页面含义 |
| --- | --- |
| `/` | 默认生活频道 |
| `/?channel=article` | 文章频道 |
| `/?channel=interest` | 兴趣频道 |

这样无需为每个频道复制页面，未来增加频道时也不需要增加一套页面结构。频道状态写入 URL，刷新、分享链接、浏览器前进和后退都能恢复当前频道，不再增加本地持久化状态。

无法识别的频道参数直接作为无效地址处理，不静默切换到其他频道。

### 6.4 移动端

移动端不保留占据横向空间的左侧栏。三个频道转换为身份区下方的横向频道栏：

```text
生活       文章       兴趣
```

- 频道栏保持可见，信息流在其下方滚动；
- 首版三个频道平均分配宽度，不使用汉堡菜单或抽屉；
- 以后频道数量超过一行可容纳范围时，再改为横向滚动，不在首版提前实现；
- 移动端仍只有信息流内容发生纵向滚动。

## 7. 频道切换行为

1. 首次进入 `/` 时展示生活频道。
2. 点击侧边栏频道后更新 URL，并加载对应频道的第一页内容。
3. 新频道从顶部开始展示，不继承前一个频道的滚动位置。
4. 打开详情后关闭，回到原频道及原信息流位置。
5. 标签点击只筛选当前频道，不跨频道汇总同名标签。
6. 当前频道加载、空状态、加载更早内容和结束状态沿用现有信息流反馈。
7. 频道切换不使用前端对已加载数据进行临时筛选，服务端按频道返回数据，确保分页结果完整。

首版不缓存三个频道各自的长列表和滚动位置。只有真实使用表明频繁切换造成明显体验问题后，再考虑频道级页面缓存。

## 8. 内容发布与管理

### 8.1 发布

- 写文章：自动进入文章频道，界面不显示可修改的频道选择；
- 发布普通内容：提供“生活 / 兴趣”选择，默认生活；
- Telegram 现有发布路径：继续直接成功，普通内容默认生活；
- 频道只影响公开展示位置，不改变公开或私有状态。

### 8.2 编辑

- 普通记录的管理入口增加“所属频道：生活 / 兴趣”；
- 文章始终显示为文章频道，不允许修改为生活或兴趣；
- 修改频道直接移动现有记录，不创建副本、不改变详情地址和发布时间；
- 私有记录可以提前保存频道，公开后按该频道展示。

## 9. 数据与扩展性

### 9.1 数据表达

建议为记录增加稳定的频道标识：

```ts
type JournalChannel = 'life' | 'article' | 'interest';
```

数据层保存稳定标识，不保存中文展示名称。中文名称、图标、排序和是否出现在公开导航中由一份集中配置维护，例如：

```ts
const publicChannels = [
  { slug: 'life', label: '生活', order: 10 },
  { slug: 'article', label: '文章', order: 20 },
  { slug: 'interest', label: '兴趣', order: 30 },
];
```

首版不把频道配置存进数据库，也不提供管理界面。未来增加频道时，只需要：

1. 增加一个稳定标识和展示配置；
2. 允许发布或编辑路径选择该标识；
3. 决定该频道复用现有瀑布流还是采用新的内容布局。

页面组件不得分别写死三组 `if/else` 布局入口；侧边栏和移动频道栏都由同一份有序配置渲染。

三个一级频道内部也保留进一步细分空间。未来的信息流结构为“当前频道 → 频道内标签栏 → 内容列表”，不同频道可以拥有不同的标签集合。标签栏位于信息流滚动区域上方，但不进入本次实施范围。

### 9.2 服务端读取

公开信息流接口增加频道过滤条件，并继续使用现有时间顺序和游标分页：

```text
GET /api/feed?channel=life
GET /api/feed?channel=article
GET /api/feed?channel=interest
```

频道过滤必须在分页前由数据库完成，不能先分页再由前端或服务端过滤当前页。

### 9.3 历史数据迁移

- 所有历史文章写入 `article`；
- 其他历史记录写入 `life`；
- 不自动产生 `interest` 历史记录；
- 迁移只增加频道归属，不修改可见性、发布时间、标签、资源和公开链接。

## 10. 页面范围

### 10.1 本次需要调整

- 公开首页外壳；
- 桌面固定侧边栏；
- 移动端频道栏；
- 公开信息流频道切换与频道查询；
- 普通内容发布和编辑时的频道选择；
- 历史内容频道迁移。

### 10.2 本次保持不变

- 公开详情页主体结构；
- 我的资产表格与瀑布流切换；
- 朋友投稿流程；
- 文章编辑器正文能力；
- RSS 和 JSON Feed 的全量时间顺序；
- 天气、Bio、头像和站点设置。

## 11. 加载与状态设计

- 初次进入频道时，骨架结构必须与该频道真实布局的列数一致；
- 切换频道时只替换信息流内容，固定身份区和侧边栏不进入加载态；
- 空频道显示“这里还没有内容”，并保留当前频道高亮；
- 接口错误直接展示在信息流区域，不切换频道，也不展示其他频道内容；
- 加载更早内容继续在当前滚动容器内触发；
- 侧边栏本身不出现骨架屏，因为首版频道配置是静态内容。

## 12. 产品验收标准

- 桌面端打开公开首页时，侧边栏固定可见，滚动内容不会带动侧边栏移动；
- 页面只有信息流区域产生纵向滚动，浏览器外层不出现第二条纵向滚动条；
- 生活、文章、兴趣三个入口均可直接访问并刷新恢复；
- `/` 默认进入生活频道，不再展示混合的全部公开内容；
- 每个频道只返回属于自己的记录，分页过程中不会漏项或混入其他频道；
- 文章发布后自动进入文章频道；
- 普通内容默认进入生活，并可明确调整为兴趣；
- 历史文章和普通记录完成确定性归属，原详情链接保持有效；
- 从详情返回后仍处于原频道和原滚动位置；
- 移动端通过固定频道栏完成同样的三频道切换，不显示桌面侧边栏；
- 后续增加第四个频道时，导航由集中配置渲染，不需要复制一套首页组件。

## 13. 已确认决策与后续方向

### 13.1 `/` 默认生活，暂时取消全部入口

已确认 `/` 默认进入生活，并暂时取消公开“全部”入口。三个一级频道就是首版公开内容的完整入口，不再同时保留混合信息流。

如果未来真实使用需要完整时间线，再单独讨论低优先级入口，不在本次预留或实现。

### 13.2 所有一级频道都允许继续细分

生活、文章、兴趣都只是一级频道，未来均可继续细分。计划在信息流滚动区域上方增加当前频道的标签栏，用于筛选该频道内部更具体的主题，例如生活中的旅行、文章中的学习与工作、兴趣中的摄影与游戏。

标签栏不属于本次范围。本次只需保证频道数据与页面结构不会阻碍后续接入，不提前实现标签栏交互、标签配置或视觉样式。

### 13.3 侧边栏未来可以承载更多全站内容

首版侧边栏只展示公开内容频道，但布局上保留独立底部扩展区。未来可以在底部加入“关于我”等低频信息或入口，也可以继续评估是否吸收其他全站导航。

本次不提前放置空白占位、不可用入口或“即将上线”内容，只保留能够自然扩展的上下布局结构。

## 14. 推荐的首版结论

- `/` 默认生活；
- 文章自动归入文章频道；
- 普通内容默认生活，可手动改为兴趣；
- 桌面端固定左侧栏，移动端固定横向频道栏；
- 仅信息流滚动；
- 频道配置集中维护，但首版不建设动态后台；
- 不提供“全部”主入口，也不自动猜测历史兴趣内容；
- 三个一级频道未来都可通过信息流上方的标签栏继续细分；
- 侧边栏底部为未来“关于我”等内容保留结构扩展能力。

这套首版先解决访客无法选择内容方向的问题，同时为以后增加频道和扩展侧边栏留出清晰位置，不把个人站点提前做成复杂内容管理系统。
