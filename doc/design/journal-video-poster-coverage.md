# Journal 视频封面补全方案

## 1. 文档定位

- 状态：已实施
- 日期：2026-07-26
- 目标：让 Journal 信息流和详情页中的视频在播放前稳定展示真实视频封面
- 范围：朋友投稿视频、Telegram 视频、圆形视频、视频动画与视频贴纸
- 原则：复用现有 `preview_relative_path` 和 `/media/:assetId/preview`，不新增封面表、不引入任务队列、不改变视频文件

本次只补齐一条主路径：

> 视频进入 Journal 时生成一张 WebP 封面，历史视频一次性补齐；前端在信息流、详情主舞台和缩略图中统一使用这张封面。

## 2. 当前事实

### 2.1 已经存在的能力

朋友投稿的视频在服务端整理为 MP4 后，已经执行以下处理：

1. FFmpeg 提取第一张可解码画面；
2. Sharp 将画面整理为最长边 960 px、quality 82 的 WebP；
3. 文件写入与视频同目录的 `*.preview.webp`；
4. `journal_assets.preview_relative_path` 保存封面路径；
5. API 已通过 `JournalAsset.previewUrl` 返回 `/media/:assetId/preview`；
6. 现有媒体路由已经按原视频相同的公开/私有权限提供 WebP。

因此，刚才约 247 MiB 的朋友投稿视频并不是没有生成封面。线上记录显示它已经有
`preview_relative_path`，当前缺口是信息流视频组件没有使用 `previewUrl`。

### 2.2 仍然缺失的能力

Telegram 写入链路目前只给图片生成预览，视频、圆形视频和 MP4 动画不会生成封面。
服务器启动时的历史补齐服务也只处理图片。

当前线上共有 6 个可播放视频资产：

| 来源与类型 | 数量 | 已有封面 | 缺少封面 |
|---|---:|---:|---:|
| 朋友投稿视频 | 1 | 1 | 0 |
| Telegram 视频 | 3 | 0 | 3 |
| Telegram MP4 动画 | 2 | 0 | 2 |

前端存在三处断点：

- 信息流卡片的 `JournalProgressiveVideo` 没有接收 `previewUrl`；
- 详情页视频没有设置 `poster`；
- 多媒体详情的缩略图对视频只显示通用播放符号，没有展示封面。

## 3. 产品效果

### 3.1 信息流卡片

- 视频区域在播放器内容就绪前即展示真实封面，不再是空白色块；
- 视频封面沿用当前图片的“模糊预览 → 清晰内容”过渡效果；
- 封面继续使用视频自身宽高比，不改变现有卡片高度和宫格布局；
- 封面上保留浏览器原生视频控件，不额外设计第二套播放状态；
- 圆形视频继续保持圆形裁切；
- 点击播放后由现有视频播放器接管，封面自然退出。

### 3.2 详情页

- 单视频和多媒体主舞台在播放前展示同一张封面；
- 多媒体缩略图直接展示各视频封面，并叠加小型播放标记以区别照片；
- 切换图片和视频时继续复用现有索引与暂停逻辑，不增加全局状态。

### 3.3 数据完整性

- 新朋友投稿视频继续沿用现有封面标准；
- 新 Telegram 视频在写入记录前生成封面；
- 当前 5 个缺少封面的 Telegram 历史资产在服务启动阶段依次补齐；
- 视频存在但封面生成失败时直接暴露错误，不写入一条缺少封面的新视频记录；
- 不显示默认图、不用通用渐变代替真实封面、不静默跳过失败视频。

## 4. 服务端设计

### 4.1 统一视频封面服务

新增轻量的 `JournalVideoPreviewService`，只负责：

```text
视频绝对路径
  → FFmpeg 在视频约 10%、35%、60% 位置各提取一张候选画面
  → Sharp 统计候选画面的亮度与信息量
  → 选择最有效的一张候选画面
  → Sharp 转为最长边 960 px、quality 82 的 sRGB WebP
  → 原子写入目标 preview 路径
  → 删除全部临时候选图
```

候选帧使用 FFmpeg 输入跳转直接定位，每个位置只解码一帧，不顺序扫描整段视频。选择时
排除接近纯黑、亮度变化极低的画面，再从剩余候选中选择信息量最高的一张。这样可以避开
视频开头常见的黑场、淡入和镜头盖未打开画面，同时把单个视频的额外工作限制为三次
单帧解码。

如果视频在三个候选位置本身都接近黑色，最终封面只能反映视频的真实内容；首版不为此
生成虚构封面，也不引入完整视频场景扫描或人工选帧。

`JournalContributionMediaService` 改为调用该服务，删除其内部重复的海报生成代码；
输出参数和错误表现保持不变。

### 4.2 新 Telegram 视频

`JournalIngestService` 在 Telegram 文件下载完成后按现有展示口径识别可播放视频：

- `video`；
- `video_note`；
- 非图片 MIME 的 `animation`；
- 视频 MIME 的 `sticker`。

识别为视频后，在临时资产目录中调用视频封面服务。原视频和封面都成功后，才一起
移动到正式目录并写入 `preview_relative_path`。

这一步只解码一帧，不转码、不调整原视频尺寸、不改变 MIME，也不影响 Telegram bot
原本的消息解析和发送路径。

### 4.3 历史视频补齐

增加与现有图片补齐方式一致的 `JournalVideoPreviewBackfillService`：

1. Repository 查询 `preview_relative_path IS NULL` 的可播放视频资产；
2. 按资产 ID 顺序逐个生成封面；
3. 每张封面完成后立即更新对应资产的 `preview_relative_path`；
4. 任一资产失败时抛出带资产 ID 的明确错误。

该服务在 Journal 开始提供页面之前运行。线上当前只有 5 个待补资产，原视频均小于
8 MiB，因此不需要后台任务、并发处理、进度表或持久队列。后续重启只执行一次空查询。

### 4.4 数据与接口

不新增数据库迁移：

- `journal_assets.preview_relative_path` 已经满足存储需要；
- `JournalAsset.previewUrl` 已经在共享协议和前端类型中存在；
- `/media/:assetId/preview` 已经支持鉴权、缓存策略和 WebP 响应；
- 删除整条 Journal 记录时，现有按目录删除会同时清理视频及其封面。

Repository 只增加“查询缺少视频封面的资产”和“完成视频封面补齐”两个直接方法。

## 5. 前端设计

### 5.1 `JournalProgressiveVideo`

组件新增 `previewSrc` 属性，由父组件传入视频资产的 `previewUrl`。组件仍只拥有自身的
加载状态，不建立 store 或 composable。

组件结构与 `JournalProgressiveImage` 保持一致：

1. 底层 `<img>` 使用 `previewSrc`，应用现有的 `blur(14px)` 和轻微放大；
2. 上层 `<video>` 同时使用 `previewSrc` 作为 `poster`；
3. 封面图片和视频首帧数据都就绪后，在 320 ms 内淡出模糊层、淡入清晰播放器；
4. 系统开启“减少动态效果”时取消动画。

同一个 960 px WebP 同时承担模糊层和清晰 `poster`，浏览器缓存会复用资源。因此不生成
第二张低清封面，也不增加字段或媒体请求路径。视频本体继续使用 `preload="metadata"`，
不改变当前播放器加载策略。

现有 `fit="cover" | "contain"`、圆形裁切和视频错误暴露方式不变。状态仍使用组件内的
少量 `shallowRef`，并在 `src` 或 `previewSrc` 改变时一起重置。

### 5.2 信息流与普通详情

`MediaGallery.vue`：

- 卡片视频向 `JournalProgressiveVideo` 传入 `asset.previewUrl`；
- 普通详情中的原生 `<video>` 设置 `poster`；
- 图片路径和音频、文件附件不变。

### 5.3 多媒体详情主舞台

`JournalMediaStage.vue`：

- 主视频设置 `poster`，封面可见时不再用文字加载层遮住画面；
- 视频缩略图使用 `asset.previewUrl`；
- 缩略图上叠加播放标记；
- 继续在切换媒体和关闭详情时暂停当前视频。

组件继续遵循 Vue 的单向数据流：资产及封面 URL 由父级 props 传入，当前索引和播放器
就绪状态保留为组件本地状态。

## 6. 实施顺序

1. 抽出统一的视频封面生成服务；
2. 接入朋友投稿与 Telegram 新视频写入链路；
3. 增加历史视频补齐查询和启动阶段处理；
4. 让信息流视频组件消费 `previewUrl`；
5. 补齐普通详情、主舞台和视频缩略图；
6. 部署时先完成历史封面补齐，再向用户提供带封面的前端页面。

最后一步的顺序保证前端不会先拿到 `previewUrl = null` 的旧视频，因此无需加入默认封面
或其他兜底分支。

## 7. 完成口径

- 刚才约 247 MiB 的朋友投稿视频在信息流中直接显示真实封面；
- 信息流视频从模糊封面平滑过渡到清晰播放器，与图片加载效果一致；
- 当前 3 个 Telegram 视频和 2 个 MP4 动画均拥有真实封面；
- 新增朋友投稿或 Telegram 视频后，API 返回非空 `previewUrl`；
- 信息流单视频、视频宫格、圆形视频均保持现有布局；
- 详情主舞台和缩略图展示与信息流一致的封面；
- 播放、暂停、媒体切换、公开/私有访问权限保持现有行为；
- 视频原文件不发生重新编码或质量变化。

## 8. 首版不做

- 手工上传或裁剪自定义封面；
- 扫描完整视频寻找语义上“最好看”的一帧；
- 为视频封面增加独立数据表或版本字段；
- 后台任务、并行回填、重试或失败降级；
- 改变视频编码、码率、分辨率或色彩；
- 为没有真实封面的资产展示默认封面。
