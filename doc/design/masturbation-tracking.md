# “撸了吗”自慰记录功能设计

## 1. 目标

在当前单用户 Telegram bot 中增加一个轻量的自慰次数记录入口，用于回答三个日常问题：

- 今天记录了几次
- 最近一段时间的频率如何
- 上一次是什么时候

功能只记录客观次数和时间，不评价行为是否健康，不给出医学建议，也不把记录发送给 AI 或外部服务。

## 2. 首版范围

首版包含：

- 手动记一次
- 查看今日状态
- 查看近 7 天、近 30 天统计
- 撤销误记的一次记录
- 从 Telegram 常驻键盘和 `/lu` 命令进入

首版不包含：

- 定时询问或催促
- 目标次数、戒断目标和打卡奖惩
- 原因、方式、时长、色情内容等详细备注
- 健康判断、趋势预测或 AI 分析
- 图表、导出和 Web 管理页面
- 多用户数据隔离设计

这些内容都不是“记录习惯和次数”主路径所必需的，暂不进入实现范围。

## 3. 核心交互

### 3.1 入口

提供两个等价入口：

- Telegram 命令：`/lu`
- 常驻键盘按钮：`📝 撸了吗`

发送自然文本“撸了吗”也视为打开状态卡片。打开卡片本身不新增记录，避免查看时误记。

状态卡片示例：

```text
📝 撸了吗

今天：1 次
本周最近 7 天：3 次 / 2 天
上一次：今天 14:26

[记一次] [查看统计]
```

“最近 7 天”表示包含今天在内的 7 个北京时间自然日；`3 次 / 2 天` 分别表示总次数和发生过记录的天数。

### 3.2 记一次

点击“记一次”后，以 bot 收到回调的当前时间新增一条记录，并回复新的确认卡片：

```text
✅ 已记录

本次：2026-07-18 21:36
今天：2 次

[撤销本次] [查看统计]
```

一次点击对应一条记录。一天可以记录多次，不做每日上限。

不增加二次确认。误触后通过“撤销本次”直接删除刚创建的那条记录。

### 3.3 撤销

确认卡片中的“撤销本次”携带本次记录 ID，只删除对应记录。删除后把原确认卡片更新为：

```text
↩️ 已撤销本次记录
今天：1 次
```

同时支持：

```text
/lu undo
```

该命令删除时间上最新的一条记录，并在回复中明确展示被撤销的发生时间。若没有记录，直接说明当前没有可撤销内容。

首版不提供任意历史记录列表和按 ID 删除，避免把简单记录功能扩展为管理系统。

### 3.4 统计

点击“查看统计”或发送 `/lu stats`，展示：

```text
📊 撸了吗统计

今天：1 次
最近 7 天：3 次 / 2 天
最近 30 天：8 次 / 6 天
距上一次：1 天 6 小时

最近 7 天
07-12  0
07-13  1
07-14  0
07-15  0
07-16  2
07-17  0
07-18  1

[记一次] [刷新]
```

统计保持中性，只展示原始频率：

- 总次数
- 有记录的天数
- 距上一次经过时间
- 最近 7 个自然日的每日次数

不展示“正常/过多/健康”等判断，也不计算带价值导向的“成功坚持天数”。

没有任何记录时展示“还没有记录”，不虚构开始日期、平均值或连续天数。

## 4. 时间口径

- 数据库存储 ISO 8601 UTC 时间。
- 所有日期分组和界面展示统一使用 `Asia/Shanghai`。
- “今天”“最近 7 天”“最近 30 天”均按北京时间自然日计算。
- 最近 7 天包含今天和之前 6 天；最近 30 天包含今天和之前 29 天。
- 记录时间以 bot 实际收到“记一次”操作的时间为准，首版不支持补录和修改发生时间。

## 5. 数据模型

在共享 SQLite 中新增独立明细表：

```sql
CREATE TABLE masturbation_records (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  occurred_at TEXT NOT NULL,
  created_at TEXT NOT NULL
);

CREATE INDEX idx_masturbation_records_occurred_at
ON masturbation_records(occurred_at);
```

选择“一次行为一行”，而不是“每天一行累计次数”，理由是：

- 可以准确展示上一次时间和间隔
- 撤销只需删除一条明确记录
- 每日、7 天和 30 天次数均可直接从明细聚合
- 不需要维护日期累计值与明细之间的一致性

项目是单用户工具，因此表中不增加用户、设备、来源、备注或状态字段。Telegram 鉴权仍统一复用现有 `TG_CHAT_ID` 检查。

`created_at` 表示数据写入时间；首版中它与 `occurred_at` 基本相同，但两者语义分开，后续若明确需要补录，不必改变已有字段含义。

## 6. 代码结构

保持功能独立，避免继续扩大 `interactive.ts` 中的业务 SQL：

### 新增文件

- `src/services/masturbationRepository.ts`
  - 新增记录
  - 按 ID 删除记录
  - 删除最新记录
  - 查询最新记录
  - 查询时间范围内的明细
- `src/services/masturbationTracker.ts`
  - 组合今日、7 天、30 天统计
  - 生成最近 7 天的每日计数
- `src/formatters/masturbationFormatter.ts`
  - 状态卡片、确认消息和统计消息
  - Inline 按钮

### 修改文件

- `src/reminders/db.ts`
  - 创建 `masturbation_records` 表和时间索引
- `src/bot/callbacks.ts`
  - 解析 `masturbation:*` 按钮回调
- `src/bot/interactive.ts`
  - 注册 `/lu`
  - 处理“📝 撸了吗”和“撸了吗”文本入口
  - 处理新增、撤销、统计和刷新按钮
- `src/reminders/formatter.ts`
  - 在现有常驻键盘末尾增加“📝 撸了吗”
  - 在帮助信息中增加 `/lu` 说明

不改提醒调度、固定任务、AI 解析和 `src/reminders/recurring.ts`。

## 7. 命令与回调约定

命令：

```text
/lu          打开今日状态卡片
/lu stats    查看统计
/lu undo     撤销最新一条记录
```

Inline 回调：

```text
masturbation:add
masturbation:stats
masturbation:refresh
masturbation:undo:<recordId>
```

回调只接受固定动作和数字记录 ID，不接收 SQL、日期或自由文本。

“撸了”不作为首版自然语言新增指令。它在闲聊中可能出现，直接记入会产生误操作；新增记录只通过明确的“记一次”按钮完成。

## 8. 隐私边界

这是敏感个人数据，首版采用当前项目已有的最短数据路径：

```text
授权 Telegram 私聊 → bot → 本地 SQLite
```

- 不调用 DeepSeek。
- 不写入普通运行日志；日志只记录功能动作，不包含次数、日期明细或记录 ID。
- 不主动推送统计。
- 不发送到新的外部服务。
- 数据会随现有 `data/notinews.sqlite` 一起进入项目已有的数据库备份范围；该行为应在实施前由用户确认是否接受。

Telegram 聊天中仍会保留 bot 回复的次数和时间，这是选择 Telegram 作为交互界面带来的现有可见范围，功能本身不额外隐藏或自动删除消息。

## 9. 主路径

```text
点击“📝 撸了吗”
→ 查看今天次数和上一次时间
→ 点击“记一次”
→ 写入一条发生时间
→ 返回本次时间、今日次数和“撤销本次”按钮
```

统计是这条主路径的旁支，不引入提醒、后台任务、缓存或额外状态机。

## 10. 后续独立 Web 看板扩展

### 10.1 当前数据模型可以直接支持

`masturbation_records` 采用“一次行为一条明细”，后续 Web 看板可以从同一份数据计算：

- 日、周、月次数
- 每日次数日历
- 有记录天数
- 两次记录之间的间隔
- 按星期几、小时段分布
- 任意日期范围的趋势

因此，为了未来看板不需要把首版改成每日汇总表，也不需要提前增加统计快照或缓存表。稳定的自增 `id`、`occurred_at` 和 `created_at` 已足够作为首版数据契约。

### 10.2 推荐的数据访问边界

独立 Web 项目不应拥有写入 NotiNews SQLite 的能力。记录仍只从 Telegram bot 产生，Web 首版只负责展示。

根据部署位置分两种情况：

#### 与 NotiNews 部署在同一台服务器

Web 后端可以使用只读连接访问 `data/notinews.sqlite`，查询 `masturbation_records`。SQLite 当前使用 WAL，常驻 bot 写入时可以同时进行普通读取。

该方式路径最短，但 Web 项目会依赖 NotiNews 的数据库文件路径和表结构，只适合两个项目明确部署在同一台个人服务器的情况。

#### 与 NotiNews 部署在不同服务器

由 NotiNews 增加一个只读 HTTP 数据接口，Web 后端通过接口读取聚合数据。接口只返回看板需要的统计结果，不开放任意 SQL，也不开放新增和删除记录。

推荐的最小接口可以是：

```text
GET /api/masturbation/summary?from=2026-07-01&to=2026-07-31
GET /api/masturbation/daily?from=2026-07-01&to=2026-07-31
```

是否引入 HTTP 服务、具体鉴权方式和返回结构，应等 Web 项目真实开始时根据部署环境单独设计；本次 Telegram 功能不提前增加端口、服务或密钥。

### 10.3 看板所需的时间约定

Web 项目必须沿用本设计的时间语义：

- `occurred_at` 是实际统计依据。
- 数据库存储 UTC ISO 8601 时间。
- 日历和区间边界按 `Asia/Shanghai` 计算。
- 日期范围参数表示北京时间自然日，后端转换为 UTC 查询边界。

这样 Telegram 统计和 Web 看板对“今天”“某天”的计数不会产生口径差异。

### 10.4 当前无需预埋

首版不为尚未开发的 Web 项目增加：

- HTTP API
- Web 用户表或权限表
- 每日汇总表
- 数据同步任务
- 消息队列
- 独立数据库
- 图表专用字段

等 Web 项目的部署位置、展示指标和访问方式明确后，再选择“同机只读 SQLite”或“只读 API”，不会影响当前已经记录的数据。

## 11. Review 时需要确认

实现前需要确认以下产品选择：

1. 是否接受默认记录精确到分钟，而不是只保存日期。 决策：接受记录到分钟
2. 是否接受“撸了吗”只打开卡片，必须再点“记一次”才新增记录。 决策：接受
3. 是否需要补录历史记录；本设计首版不支持。 决策：不需要
4. 是否接受记录进入现有 SQLite 备份，还是需要明确排除这张表。 决策：记录进入现有备份
5. 常驻键盘按钮文案使用直白的“📝 撸了吗”，还是改成更隐蔽的名称。 决策：使用直白的文案
