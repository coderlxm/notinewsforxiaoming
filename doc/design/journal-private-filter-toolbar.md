# Journal 私有信息流筛选栏紧凑化方案

## 1. 文档状态

- 状态：已 Review，已实施
- 页面范围：登录后的 `/me`，同时覆盖表格与瀑布流视图
- 本次目标：压缩桌面端筛选区高度，并将手动提交改为输入后自动查询
- 不涉及：筛选字段调整、URL 持久化、服务端筛选接口和公开信息流

## 2. 当前实现判断

当前 `EntryFilters.vue` 将筛选区拆成可折叠标题、可见性选择、正文/标签/格式、日期和操作按钮三层。展开后在宽屏上仍固定为两排输入区，加上标题行实际占用三层高度；当前截图的内容宽度足以让全部输入框位于同一排，可见性按钮则更适合作为独立的第一层选择。

当前筛选提交还有两个与自动查询相关的事实：

- `EntryFilters` 只在点击“筛选”或“清空”时向 `FeedView` 发出完整 `FeedFilters`；
- `FeedView.applyFilters()` 当前调用 `journal.loadPrivate()`，除了查询筛选结果，还会重复请求与筛选条件无关的“往年今日”。

自动查询不能简单地把现有提交函数绑到每次键盘输入上，否则会放大请求量，并让“往年今日”产生无意义的重复请求。

## 3. 产品方案

### 3.1 桌面端布局

桌面端取消独立的“筛选 / 全部记录 / 收起”标题行，将可见性与具体筛选字段分成两个紧凑层级：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ [全部] [私有] [公开]                                                        │
│ [正文关键词____________] [标签______] [全部格式▼] [从__ 到__] [清空]       │
└──────────────────────────────────────────────────────────────────────────────┘
```

信息优先级和宽度分配：

- 可见性维持当前三段式选择，单独位于第一行，不与输入框机械并排；
- 正文关键词承担主要伸缩空间，优先获得剩余宽度；
- 标签与格式使用较短的稳定宽度；
- “从 / 到”合并为一个日期范围组，但仍使用当前两个原生日期输入；
- 保留“清空”，移除“筛选”按钮；没有生效条件时“清空”保持原位置并禁用，避免布局跳动；
- 输入框标签使用当前小号字段标题，不依赖 placeholder 代替字段含义。

桌面端卡片最终保留两条紧凑内容带，去掉原有独立标题层，并保证第二行输入框不再拆行。

### 3.2 中小屏适配

不强迫所有宽度都维持单排：

- 宽桌面：第一行只放可见性，第二行展示其余全部条件；
- 中等宽度：允许工具栏自然分成两排，避免输入框过度压缩；
- 手机：保留“筛选 + 当前条件摘要 + 展开/收起”入口，展开后使用单列布局，避免筛选表单长期占据首屏。

响应式只通过 CSS 断点完成，不监听视口，也不维护桌面和移动端两套筛选状态。桌面端标题行隐藏、筛选面板常驻；手机端标题行显示，并由现有 `expanded` 状态控制面板。

### 3.3 自动查询规则

所有筛选控件改动后自动应用，不再需要提交动作：

- 正文关键词、标签、可见性、格式、起止日期和清空动作统一进入一次 350ms 防抖；
- 用户连续输入或快速调整多个条件时，只使用停止操作时的最新完整筛选快照发起查询；
- 清空会立即更新控件内容，并经过同一 350ms 防抖刷新结果，避免与尚未触发的输入查询形成两次请求；
- 初次挂载只显示父组件传入的现有条件，不主动重复查询；
- 从卡片或详情点击标签时，继续立即应用该标签，并同步更新筛选栏显示。

350ms 在个人内容搜索中能明显抑制逐字请求，同时不会让筛选显得迟钝。首版不增加可配置项。

### 3.4 查询期间的反馈

自动查询继续沿用 `FeedView` 现有的结果替换状态：

- 防抖等待期间不改变结果区；
- 请求开始后，表格视图显示现有表格骨架，瀑布流显示现有卡片骨架；
- 请求完成后替换为最新筛选结果；
- 空结果和请求错误继续沿用当前信息流处理方式。

不在筛选栏增加新的文字 loading、进度条或状态提示，避免为了通常很短的一次查询增加额外视觉噪音。

## 4. 技术方案

### 4.1 防抖实现

使用项目已经安装的 `@vueuse/core@14.3.0`：

```ts
import { useDebounceFn } from '@vueuse/core';

const queueApply = useDebounceFn(() => {
  emit('apply', { ...draft });
}, 350);
```

本地安装版本从 `@vueuse/core` 正常导出 `useDebounceFn`，其 Vue peer dependency 与项目当前 Vue 3.5 一致。该函数直接用于控件事件，不增加新的 `watch`，也不手写 `setTimeout`、取消器或防抖状态。

`EntryFilters` 继续保留一个本地 `draft` 负责控件即时显示，并继续通过现有 `apply` 事件一次性向父组件提交完整筛选快照。这样 `FeedView` 仍是已应用筛选条件和请求行为的唯一业务编排层。

### 4.2 私有 Feed 请求

`FeedView.applyFilters()` 保留当前结果替换与布局状态收口，但查询改为调用：

```text
journal.refreshPrivateFeed(filters)
```

而不是：

```text
journal.loadPrivate(filters)
```

两者都使用现有 `/api/me/entries` 筛选接口；区别是前者只替换 Feed，不会在每次自动筛选时重新请求“往年今日”。首次进入 `/me`、登录和重新激活页面仍沿用各自现有加载路径。

私有信息流中的标签点击也统一交给 `applyFilters()`，避免维护另一条重复的筛选请求逻辑。公开信息流的标签路由行为不变。

### 4.3 组件边界

本次无需新增组件或 composable：

```text
FeedView.vue
└─ EntryFilters.vue
```

- `EntryFilters.vue`：负责筛选控件、响应式布局、本地草稿和防抖后的 `apply` 事件；
- `FeedView.vue`：接收完整筛选条件，刷新私有 Feed 并控制结果替换状态。

筛选字段、`FeedFilters` 类型、私有 API 参数和服务端实现保持不变。

## 6. 取舍

- 自动筛选会比手动提交产生更多请求，但 350ms 防抖会把连续操作合并，且每次筛选从两条请求降为一条；对于单用户个人项目，这个成本可接受。
- 中等宽度设备的输入区可能继续换行，这是为了保证输入框可用宽度；宽桌面下则固定为“可见性一行、其余输入一行”。
- 手机继续需要一次“展开”操作，但默认更节省首屏空间，也避免六类条件长期占满页面。
- 筛选条件仍只保存在当前私有 Feed 实例中，不进入 URL；这与现有行为一致，本次不扩大为筛选状态持久化需求。

## 7. Review 验收口径

- 当前截图对应的宽桌面下，可见性按钮位于第一行，其余筛选框完整位于第二行，不再显示独立标题行或第三行日期区；
- 页面中不再出现“筛选”提交按钮；
- 连续输入正文或标签时不会逐字发起查询，停止输入约 350ms 后使用最新内容查询；
- 修改可见性、格式或日期后无需额外确认即可更新结果；
- 快速连续修改多个条件时只应用最终组合；
- 清空后全部控件恢复默认值，并自动恢复全部记录；
- 自动筛选不会重复刷新“往年今日”；
- 表格和瀑布流使用同一套筛选行为；
- 手机端仍能折叠筛选区，展开后所有字段可完整操作；
- 现有空状态、分页、详情和视图切换行为不受影响。
