# Journal 瀑布流视觉重构方案

## 1. 文档状态

- 状态：待 Review
- 范围：`web` 目录的信息流、卡片和站点外壳
- 不涉及：Journal 数据模型、Fastify API、Telegram 采集、文章编辑器能力
- 产品定位：个人生活档案，不转型为公开社交平台

## 2. 背景

当前 Web 使用 `680px` 窄栏单列信息流。这个结构适合连续阅读，但没有充分利用桌面宽度，也弱化了图片、视频、文章封面等不同内容的视觉差异。随着 Journal 同时承载 Telegram 随手记录、媒体记录和 Web 富文本文章，单列等宽卡片开始显得重复且密集。

本次希望借鉴小红书的信息密度和瀑布流浏览方式，让用户能快速扫视大量生活记录，同时保留当前项目安静、私密、可长期阅读的个人档案感。

这里借鉴的是：

- 多列瀑布流布局；
- 媒体优先的卡片构图；
- 紧凑的作者、时间和标签信息；
- 移动端自然滑动浏览的内容密度。

不借鉴的是：

- 点赞、收藏、评论、关注等社交指标；
- 推荐算法、频道矩阵和无限推荐；
- 强运营导航、红点和高饱和促销视觉；
- 为填满版面而裁切或伪造内容。

## 3. 设计目标

### 3.1 核心目标

1. 公开首页在桌面端呈现 3–4 列瀑布流，移动端呈现 2 列紧凑卡片。
2. 图片、视频、纯文字和长文章拥有不同但统一的卡片构图。
3. 用户可以更快扫视记录，同时仍能明确看出日期、公开状态、置顶和标签。
4. 公开详情与文章正文继续保持适合阅读的单栏宽度。
5. 私有资产页保留筛选、编辑、置顶、可见性和删除能力，不为了瀑布流牺牲管理效率。

### 3.2 非目标

- 不修改现有路由和 API。
- 不引入 Vue Router、Pinia或新的 UI 组件库。
- 不加入点赞、评论、收藏或统计数据。
- 不做拖拽排序、虚拟列表或无限滚动。
- 不为瀑布流增加后端图片裁切、缩略图或额外媒体元数据。
- 不增加布局失败后的替代实现；布局问题直接在主实现中修正。

## 4. 设计判断

### 4.1 页面唯一任务

首页的唯一任务是：让小明快速扫到一段想重新打开的生活记录。

因此首页不设置传统大幅 Hero。首屏最有辨识度的内容应当就是个人身份和真实记录本身，避免额外宣传区把内容推到首屏以下。

### 4.2 视觉方向：桌面上的生活照片墙

视觉不直接复制小红书的纯白商品流，而采用“桌面上的生活照片墙”：卡片像尺寸各异的照片、便笺和剪报，被规整地摆在一个宽阔但安静的画布上。

整体从当前偏暖的奶油色与陶土色组合，调整为更清爽的纸白、墨黑与石榴红。原因是当前配色本身已经接近常见的暖米色模板，瀑布流继续沿用会显得像通用生活方式模板，难以形成个人识别。

### 4.3 唯一视觉签名：日期书脊

每张卡片左上区域保留一条窄小的“日期书脊”：

```text
JUL
20
```

它来自日记本、底片日期和档案标签，而不是无意义编号。它同时完成三个任务：

- 让时间成为整个信息流最稳定的视觉索引；
- 在高低不一的卡片中建立统一节奏；
- 取代重复出现的大头像，降低每张卡片的头部噪音。

这是本次设计唯一刻意突出的装饰性元素，其余视觉保持克制。

## 5. 信息架构与页面布局

### 5.1 全站外壳

站点外壳从 `680px` 窄栏扩展为最大 `1440px` 的内容画布：

```text
┌──────────────────────────────────────────────────────────────┐
│ 头像  小明同学 / 一句签名                公开记录  我的资产 │
├──────────────────────────────────────────────────────────────┤
│ 最近记录                                      标签/筛选入口 │
│                                                              │
│  ┌────────┐  ┌──────────┐  ┌────────┐  ┌───────────┐        │
│  │        │  │          │  │        │  │           │        │
│  │  图片  │  │ 纯文字   │  │ 视频   │  │ 文章封面  │        │
│  │        │  │          │  │        │  │           │        │
│  ├────────┤  │          │  ├────────┤  ├───────────┤        │
│  │ 摘要   │  └──────────┘  │ 摘要   │  │ 标题摘要  │        │
│  └────────┘  ┌──────────┐  └────────┘  └───────────┘        │
│              │   图片   │                                    │
│              └──────────┘                                    │
└──────────────────────────────────────────────────────────────┘
```

Header 仍是单行个人身份，不加入侧边栏。滚动后不吸顶，避免占用移动端内容空间。

### 5.2 响应式列数

| 视口 | 画布边距 | 列数 | 列间距 |
| --- | ---: | ---: | ---: |
| `>= 1360px` | `32px` | 4 列 | `20px` |
| `960–1359px` | `28px` | 3 列 | `18px` |
| `600–959px` | `20px` | 2 列 | `14px` |
| `< 600px` | `10px` | 2 列 | `8px` |

移动端坚持两列，这是与当前单列体验最明显的产品变化。卡片正文、按钮和标签需要随之收敛；文章详情、登录页和编辑页不采用两列。

### 5.3 布局实现

首版使用 CSS Multi-column 实现真实瀑布流：

```css
.feed-grid {
  columns: 4;
  column-gap: var(--waterfall-gap);
}

.feed-card {
  break-inside: avoid;
  margin-bottom: var(--waterfall-gap);
}
```

选择它的原因：

- 当前列表是按时间追加的浏览流，不存在必须严格横向逐行阅读的表格语义；
- 能直接适应图片和正文造成的自然卡片高度；
- 不需要手写列高算法或引入布局库；
- 现有分页追加可以继续工作。

明确接受其阅读顺序为“先从上到下填满一列，再进入下一列”。如果 Review 阶段要求严格按行从左到右阅读，应改用成熟的 Vue masonry 库，并以 DOM 顺序和键盘顺序一致作为选型条件，不在项目中手写定位算法。

## 6. 卡片系统

### 6.1 通用结构

卡片不再统一显示头像、姓名、完整徽章和全部管理动作。推荐结构：

```text
┌─────────────────────┐
│ JUL 20        ···   │  日期书脊 + 私有管理菜单
│                     │
│ 内容媒体 / 文章封面 │
│                     │
│ 标题或正文摘要      │
│ #旅行  #朋友        │
│ 21:34      私有/置顶│
└─────────────────────┘
```

公开流不重复显示每张卡片的作者，因为页面头部已经明确唯一作者。私有流显示可见性和置顶状态，管理动作收进卡片右上角菜单，避免四个文字按钮破坏瀑布流密度。

### 6.2 图片与视频卡片

- 媒体置于卡片顶部，使用资产自身比例展示。
- 不强制所有图片裁成相同宽高比。
- 单图占据完整卡片宽度；多图保留紧凑拼图，但首图优先获得最大面积。
- 视频、语音和文件继续使用现有原生可操作控件，不伪装成静态封面。
- 正文超过 72 个中文字符时在信息流截断，详情页完整展示。

### 6.3 纯文字卡片

- 没有媒体时，让正文成为主要视觉内容。
- 根据文本长度使用两档字号，而不是随机变化：短句使用较大字号，长文本使用常规字号。
- 短句卡片可使用低饱和背景色，但颜色由内容类型固定映射，不按数据随机生成。
- 结构化内容只展示最关键的 2–3 行；完整字段留在详情页。

### 6.4 富文本文章卡片

- 有封面：封面在上，标题和摘要在下。
- 无封面：标题作为卡片视觉主体，使用展示字体。
- 摘要最多显示约 3 行。
- 整张卡片可点击进入详情，私有模式下右上菜单仍能直接进入编辑。

### 6.5 置顶内容

置顶不改变跨列尺寸，也不做大卡片，以免破坏稳定布局。只通过日期书脊旁的一枚实心图钉标识，并继续由后端排序决定其位置。

### 6.6 管理动作

私有卡片右上角增加一个省略号按钮，展开一个就地菜单：

- 编辑；
- 置顶 / 取消置顶；
- 设为公开 / 转为私有；
- 删除。

删除仍在卡片内进入明确的二次确认态，不新增全局弹窗系统。菜单打开时不改变其他卡片状态。

## 7. 各页面调整

### 7.1 公开首页 `/`

- 使用宽画布瀑布流。
- 页面标题从“最近记录”收敛为轻量标题行。
- 标签筛选结果仍在同一页面呈现，并提供清除标签。
- “加载更早记录”位于瀑布流之后，保持明确点击加载。
- 不加入推荐分类或悬浮发布按钮。

### 7.2 公开详情 `/p/:publicId`

- 不使用瀑布流。
- 普通记录详情宽度约 `760px`，富文本文章约 `820px`。
- 保留返回信息流入口。
- 日期书脊可作为详情页时间标记，但内容主体保持连续阅读。

### 7.3 私有资产 `/me`

- 登录后使用与公开首页相同的瀑布流骨架。
- 筛选器默认折叠成一行摘要工具条，展开后显示现有筛选字段。
- “往年今日”位于筛选器下方，作为横向可滚动的独立卡片带，不混入主瀑布流，避免用户误判时间顺序。
- “写文章”和“退出登录”继续保留在标题区。

### 7.4 登录页

- 保持单一居中卡片，不加入瀑布流装饰。
- 背景可隐约复用日期书脊的纵向刻度，但不展示假数据卡片。

### 7.5 文章编辑页

- 编辑器继续保持单栏，不随首页变宽。
- 编辑区约 `780px`，媒体管理面板可在宽屏时放到右侧窄栏。
- 预览使用新的文章详情视觉，而不是瀑布流摘要卡片。

## 8. 视觉系统

### 8.1 色彩

| Token | 色值 | 用途 |
| --- | --- | --- |
| `paper` | `#F7F7F5` | 页面底色，接近档案纸而非暖奶油色 |
| `card` | `#FFFFFF` | 卡片与输入区 |
| `ink` | `#20201E` | 主文字 |
| `graphite` | `#72716C` | 时间、说明和次级信息 |
| `pomegranate` | `#C43B46` | 日期书脊、链接和主要操作 |
| `mist` | `#ECECE8` | 分隔、浅底和边框 |

深色模式不简单反转为纯黑，使用墨灰背景与略暖白字，石榴红提高明度以维持辨识度。

### 8.2 字体角色

- 标题与短句：`Noto Serif SC` / `Songti SC`，用于文章标题和短文本卡片。
- 正文与操作：系统无衬线字体栈，保证中文和控件清晰。
- 日期书脊与元信息：`Arial Narrow` / `Roboto Condensed` 类窄体回退栈，形成档案标签感。

不新增远程字体请求。若后续确定需要稳定的窄体字形，再将字体文件作为站点静态资源管理。

### 8.3 形状与阴影

- 卡片圆角由当前 `1.15rem` 收敛到 `12px`。
- 常态使用 `1px` 浅边框，不使用明显悬浮阴影。
- Hover 仅轻微上移并增强边框，不做缩放。
- 媒体圆角与卡片边缘保持同心关系。

## 9. 交互与可访问性

- 卡片主体可点击时使用真实按钮或链接语义，避免只给容器绑定点击。
- 右上管理菜单支持键盘打开、关闭和逐项聚焦。
- 两列移动布局下，主要点击目标仍不小于约 `40px`。
- 文本不能只靠颜色表达公开、私有或置顶状态。
- 动效仅用于卡片 Hover 和菜单出现，并尊重 `prefers-reduced-motion`。
- 图片继续使用现有替代文本；没有描述的 Telegram 图片保持空替代文本，不自动生成描述。

## 10. 组件调整建议

### 10.1 页面与布局组件

| 组件 | 单一职责 | 主要契约 |
| --- | --- | --- |
| `App.vue` | 站点外壳和现有轻量路由 | 向页面下发 `navigate` |
| `FeedView.vue` | 信息流数据编排与页面区块组合 | 接收模式/详情参数，响应导航 |
| `WaterfallFeed.vue` | 只负责瀑布流容器和条目分发 | `entries`、`mode`；上抛卡片事件 |
| `FeedToolbar.vue` | 标题、筛选摘要和页面级动作 | 筛选状态、登录状态；上抛操作 |
| `OnThisDayRail.vue` | 横向展示往年今日 | `entries`；上抛卡片事件 |

### 10.2 卡片组件

保留当前普通记录与文章两种业务卡片，不强行合并为一个巨型组件：

| 组件 | 调整方向 |
| --- | --- |
| `EntryCard.vue` | 改为瀑布流普通记录卡片，拆出头部与管理菜单 |
| `ArticleCardContent.vue` | 区分摘要卡与详情文章，摘要采用瀑布流构图 |
| `CardDateSpine.vue` | 渲染日期书脊和时间 |
| `CardActionMenu.vue` | 统一普通记录与文章的私有管理动作 |
| `MediaGallery.vue` | 增加 `card/detail` 展示模式，卡片模式更紧凑 |

组件继续使用明确的 props-down / events-up。`useJournalApi` 保持数据源与请求入口，不在卡片中直接调用 API。

## 11. 数据与接口影响

本方案不需要新增或修改后端接口。现有数据已经包含布局所需字段：

- `contentType` 决定卡片内容类型；
- `assets` 提供媒体和尺寸信息；
- `bodyFormat` 区分普通记录与文章；
- `title`、`contentText`、`tags` 形成摘要；
- `sourceCreatedAt` 生成日期书脊；
- `visibility`、`pinned` 支持私有管理状态。

媒体比例优先使用已有 `width / height`，实际展示仍以媒体元素的原始比例为准。不新增比例默认值伪装已知尺寸。

## 12. 实施拆分

### 阶段一：布局骨架与视觉 Token

- 调整全局画布宽度、色彩、圆角、间距和响应式断点。
- 把公开信息流替换为多列瀑布流。
- 保持详情页、登录页和编辑页为单栏。

### 阶段二：卡片重构

- 新增日期书脊与统一管理菜单。
- 分别重构普通记录、文章摘要和媒体布局。
- 将完整内容与结构化字段留给详情页。

### 阶段三：私有资产体验

- 收敛筛选器为可展开工具条。
- 将往年今日改为独立横向卡片带。
- 处理私有卡片的编辑、可见性、置顶和删除状态。

### 阶段四：详情与编辑视觉统一

- 更新普通记录详情和文章详情排版。
- 调整文章编辑页的宽屏布局和新版预览。
- 完成深色模式和窄屏细节。

## 13. Review 决策点

实施前需要确认以下设计选择：

1. 是否接受移动端两列布局；这是本次体验变化最大的部分。
2. 是否接受 CSS Multi-column 的纵向填充阅读顺序，还是要求严格横向逐行排序。
3. 日期书脊是否作为这次重构的核心视觉签名。
4. 私有管理动作是否统一收进右上角菜单。
5. “往年今日”是否独立为横向卡片带，而不是进入主瀑布流。

## 14. 推荐结论

推荐按本方案推进：公开首页和私有资产页采用响应式瀑布流，移动端保持两列；详情与编辑继续使用单栏；以日期书脊建立个人档案识别度；私有操作收进统一菜单；后端与数据模型保持不变。

这能获得接近小红书的浏览效率，但最终呈现仍是“小明同学的生活档案”，而不是一个缺少社交数据的小红书复制品。
