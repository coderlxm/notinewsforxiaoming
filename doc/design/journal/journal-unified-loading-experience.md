# Journal 统一 Loading 体验设计

## 1. 文档状态

- 状态：待 Review
- 范围：Journal Web 的页面级读取、瀑布流排版等待和按钮级异步操作
- 产品定位：个人档案与生活信息流，不做通用 UI 框架
- 实施边界：仅调整 Vue 前端，不修改 API、数据模型和部署架构，不新增第三方依赖

## 2. 问题与证据

### 2.1 运行时证据

当前从公开信息流点击文章后，详情页会直接出现纯文本“正在读取记录…”，数据返回后又立即替换为文章正文。用户已确认这一过程缺少动画与视觉承接，进入文章时显得生硬。

### 2.2 源码行为

- `FeedView.vue` 使用一个普通 `div.feed__loading` 表达信息流和详情读取，没有进入、离开或内容揭示动画。
- `WaterfallFeed.vue` 在数据读取后还会经历独立的排版阶段，并再次显示自己的“正在读取记录…”。两段等待属于同一用户任务，但由两个视觉状态分别表达。
- `ArticleEditorView.vue` 使用普通 `notice` 显示“正在读取文章…”。
- 登录、加载更多、保存、上传和删除只替换按钮文字，各处节奏与视觉反馈不一致。
- `App.vue` 的个人信息栏始终保留；因此 Loading 不需要遮住整个页面，也不应做全屏遮罩。
- 已缓存的公开信息流从详情返回时不再重新读取。新的 Loading 设计不得破坏这一行为。

### 2.3 设计判断

生硬感并不只是“缺少一个转圈动画”，而是由三件事共同造成：

1. 页面已经切换，但新内容区域没有稳定的视觉承接物；
2. Loading 和真实内容直接互换，没有离场与入场节奏；
3. 请求等待与瀑布流排版等待使用两个相互独立的状态，容易形成连续跳变。

因此不采用通用旋转圆圈，而建立一套与“纸张、档案、日期书脊”视觉一致的轻量 Loading 语言。

## 3. 目标

1. 点击文章后，详情页结构立即成立，用户能够马上看到返回入口和明确的内容区域。
2. Loading 自然淡入，数据完成后柔和退场，正文随后被“展开”，不发生硬切。
3. 信息流的数据读取与瀑布流排版共享同一个等待阶段，不连续闪现两个 Loading。
4. 页面级、区域级和按钮级反馈使用同一种视觉符号，但保持符合场景的大小与占位方式。
5. 不为动画增加接口等待时间，不用动效掩盖错误，也不加入重试、降级或静默失败。
6. 尊重系统的减少动态效果设置，并保持清晰的状态播报。

## 4. 视觉方案：正在翻阅的档案卡

### 4.1 核心符号

Loading 使用一张极简的“档案卡”作为统一符号：

```text
┌──────────────┐
│┃  ━━━━━      │
│┃  ━━━━━━━━   │
│┃  ━━━━━━     │
└──────────────┘
    正在展开记录…
```

- 左侧石榴红竖线来自现有日期书脊，是整个站点已有的视觉签名。
- 三条浅灰“墨迹”代表正在整理的文字，不模拟具体内容，也不伪造文章骨架。
- 卡片使用现有 `surface-card`、`border-subtle` 和 `radius-card`，自动适配深色模式。
- 不使用圆形 spinner、彩色渐变、品牌 Logo 动画或全屏蒙层。

### 4.2 动画节奏

| 阶段 | 时长 | 表现 |
| --- | ---: | --- |
| Loading 延迟出现 | `120ms` | 快速请求不显示 Loading，只保留稳定内容区域 |
| Loading 入场 | `180ms` | `opacity: 0 → 1`，整体向上移动 `4px` |
| 档案卡呼吸 | `1600ms` 循环 | 红色书脊与三条墨迹依次做轻微明暗变化 |
| Loading 离场 | `120ms` | 仅淡出，不缩放、不改变高度 |
| 内容入场 | `240ms` | `opacity: 0 → 1`，向上移动 `6px` |

缓动统一使用当前卡片动画已经采用的 `cubic-bezier(0.22, 1, 0.36, 1)`。只动画 `opacity` 和 `transform`，不动画高度、边距或定位属性。

Loading 的 `120ms` 延迟只控制视觉是否出现，不延迟接口请求，也不强制延后已经返回的内容。

### 4.3 文案

文案说明当前动作，不使用抽象的“Loading”：

| 场景 | 文案 |
| --- | --- |
| 公开 / 私有信息流首次读取 | 正在整理记录… |
| 普通记录或文章详情 | 正在展开记录… |
| 已有文章进入编辑页 | 正在打开文章… |
| 个人资产身份与数据读取 | 正在打开个人档案… |
| 加载更早记录 | 正在读取更早记录… |
| 登录、保存、上传、删除 | 登录中… / 保存中… / 上传中… / 删除中… |

文字本身不做逐点动画，避免屏幕阅读器重复播报；动态感只来自标记的装饰层。

## 5. 三种使用层级

### 5.1 Reading：详情和编辑器

用于文章详情、普通记录详情和已有文章编辑页。

- 页面标题栏先出现，返回按钮始终可以操作。
- 标题栏下方建立固定的阅读等待区，最小高度使用 `clamp(20rem, 48vh, 34rem)`。
- Loading 位于等待区视觉中心。
- 请求完成后 Loading 淡出，文章或记录以内容入场动画出现。
- 请求失败时错误直接替换 Loading，并继续使用现有 `role="alert"`，不显示空白内容或默认正文。

文章详情效果：

```text
← 返回信息流                                  永久记录

                 ┌──────────────┐
                 │┃  ━━━━━      │
                 │┃  ━━━━━━━━   │
                 │┃  ━━━━━━     │
                 └──────────────┘
                    正在展开记录…
```

### 5.2 Canvas：信息流与瀑布流

用于公开首页、标签信息流、登录后的个人资产列表，以及瀑布流首次排版。

- 页面标题与筛选区先出现。
- 数据请求和 Masonry 排版合并成一个 `preparing` 状态。
- `preparing` 结束条件是：接口已完成，并且 Masonry 已触发有效的 `renderComplete`。
- 整个过程中只保留一份 Canvas Loading，文案保持“正在整理记录…”，不会从 Feed Loading 跳成 Waterfall Loading。
- Canvas 等待区最小高度使用 `clamp(18rem, 42vh, 30rem)`，避免 Loading 退场前容器突然改变高度。
- 瀑布流在 Loading 后方完成定位，未就绪时保持不可见；布局完成后与 Loading 交叉淡入淡出。
- 空数据只在请求完成且排版阶段结束后显示空状态，Loading 和空状态不连续闪现。
- 从文章返回已被 `KeepAlive` 缓存的信息流时，数据和布局都已存在，不进入 `preparing`，也不再次显示 Loading。

### 5.3 Inline：按钮与卡片局部操作

用于登录、加载更多、保存文章、上传图片、修改可见性和永久删除。

- 操作范围只覆盖发起动作的按钮或卡片，不替换整页内容。
- 按钮保持原尺寸，忙碌时显示缩小版书脊标记与原有动作文案。
- 使用 `aria-busy="true"` 并保持禁用状态，避免重复操作。
- 卡片编辑、置顶、可见性和删除继续由现有 `mutationEntryId` 精确定位到单张卡片，不出现全局 Loading。
- 上传图片时只锁定文章编辑区相关操作，不遮住已编辑正文。

## 6. 状态切换规则

### 6.1 文章详情

```text
点击文章
  → 详情标题栏立即出现
  → 请求超过 120ms 时 Loading 柔和出现
  → 数据成功：Loading 淡出 → 正文淡入
  → 数据失败：Loading 淡出 → 原始错误明确出现
```

### 6.2 信息流首次进入

```text
页面标题立即出现
  → 请求数据
  → 数据进入不可见的瀑布流
  → Masonry 完成真实排版
  → 统一 Loading 淡出
  → 已排版卡片淡入
```

### 6.3 返回缓存信息流

```text
文章详情
  → 返回信息流
  → KeepAlive 恢复原组件与滚动位置
  → Masonry 重新计算容器宽度
  → 直接显示原信息流，不出现 Loading
```

这里的 Masonry 重算属于已存在内容的校正，不被解释成新的读取任务。

### 6.4 快速响应

接口在 `120ms` 内完成时，Loading 标记不出现，真实内容直接执行 `240ms` 的轻量入场。这样避免快速请求产生一闪而过的“正在读取”。

## 7. Vue 组件设计

### 7.1 组件边界

| 文件 | 单一职责 | 输入 / 输出 |
| --- | --- | --- |
| `components/ui/JournalLoading.vue` | 渲染统一档案卡标记、文案和三种尺寸 | Props：`variant`、`label`；无业务事件 |
| `composables/useDeferredLoading.ts` | 将真实 Loading 状态转换为延迟 `120ms` 的视觉状态 | 输入：只读布尔 Ref；输出：只读 `visible` |
| `FeedView.vue` | 根据公开、私有、详情场景选择 Loading 文案并编排内容切换 | 继续使用现有 Journal 状态，不持有动画计时细节 |
| `WaterfallFeed.vue` | 合并接口读取与 Masonry 排版状态，控制画布何时可见 | 新增 `loading` Prop；不向外暴露 Masonry 实例 |
| `ArticleEditorView.vue` | 在已有文章读取期间显示 Reading Loading | 继续使用 `useArticleEditor()` 的 `loading` |

不增加全局 Loading Store、请求拦截器、事件总线或统一异步任务状态机。Loading 状态仍由现有业务 composable 持有，视觉组件只消费状态。

### 7.2 `JournalLoading.vue`

建议接口：

```ts
interface Props {
  variant?: 'canvas' | 'reading' | 'inline';
  label: string;
}
```

- 使用 `<script setup lang="ts">`。
- 根节点自带 `role="status"`、`aria-live="polite"` 和 `aria-atomic="true"`。
- 图形标记设置 `aria-hidden="true"`。
- `canvas` 与 `reading` 只改变占位尺寸，不复制模板。
- `inline` 使用同一图形的紧凑版本，可嵌入按钮。

### 7.3 `useDeferredLoading.ts`

这个 composable 只负责视觉延迟：

- 源状态变为 `true` 后等待 `120ms` 再显示；
- 源状态在等待期间恢复为 `false` 时取消显示；
- 源状态变为 `false` 后立即交给 Vue Transition 执行离场；
- 组件卸载时清理计时器；
- 不修改真实请求状态，不设置最短接口时长，不吞掉错误。

它同时被 `FeedView`、`WaterfallFeed` 和 `ArticleEditorView` 使用，因此独立为 composable，而不是在三个组件中重复计时逻辑。

### 7.4 内容过渡

Loading 与正文、空状态、错误状态的切换使用 Vue `<Transition>`：

- 相同标签的状态分支提供稳定 `key`；
- Reading 场景使用 `mode="out-in"`，避免正文与 Loading 语义同时存在；
- Canvas 场景使用现有同网格区域叠放方式，避免两个元素的高度相加；
- 动画类写在拥有该过渡的组件中，通用颜色与动效时长写入全局 token。

## 9. 无障碍与减少动态效果

- 每个可见区域最多存在一个 `role="status"`，避免重复播报同一加载过程。
- 页面或区域容器在等待期间设置 `aria-busy="true"`。
- 错误继续使用 `role="alert"`，Loading 不会覆盖或延迟错误。
- Loading 图形不承载信息，关键信息始终由文字提供。
- `prefers-reduced-motion: reduce` 下：
  - 取消循环呼吸、位移和淡入淡出；
  - 保留静态档案卡与状态文案；
  - 内容直接出现，不改变数据流。
- 深色模式复用现有 token，不增加固定浅色背景。

## 10. 明确不做

- 不引入 Skeleton、动画或 UI 组件库。
- 不添加顶部全局进度条、全屏遮罩或路由级 spinner。
- 不为不同内容类型生成假标题、假图片或多套骨架。
- 不增加接口重试、超时提示、离线降级或默认内容。
- 不缓存详情数据来规避 Loading；详情仍按现有快照读取主路径加载。
- 不为了让动画完整播放而人为延迟真实内容。
- 不改变刚完成的公开信息流 `KeepAlive` 与滚动恢复逻辑。

## 11. 验收观察项

1. 从公开瀑布流进入文章时，标题栏先出现，等待状态自然入场，正文柔和出现。
2. 快速响应时不闪现 Loading 文案。
3. 慢速响应时动画持续自然，没有旋转突兀感或布局抖动。
4. 数据读取完成到瀑布流排版完成之间只有一个连续 Loading。
5. 从详情返回缓存信息流时不出现 Loading，并保持原滚动位置。
6. 详情、信息流、文章编辑器和按钮操作使用同一视觉符号。
7. Loading、空状态和错误状态不会在同一时刻叠加。
8. 桌面、移动端、浅色和深色模式都保持现有档案风格。
9. 开启减少动态效果后没有循环动画，状态文字仍清晰可见。

## 12. 推荐实施顺序

1. 建立 `JournalLoading.vue`、动效 token 和减少动态效果规则。
2. 先改文章详情的 Reading Loading，解决当前最明显的生硬问题。
3. 合并 Feed 与 Waterfall 的 Canvas Loading，保持现有稳定高度方案。
4. 接入文章编辑页和登录页。
5. 最后统一加载更多、保存、上传与删除等 Inline Loading。

这个顺序只用于控制修改范围；每一步都复用同一个视觉组件，不产生临时的第二套 Loading。
