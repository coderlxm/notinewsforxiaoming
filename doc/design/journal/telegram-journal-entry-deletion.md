# Journal 记录删除功能设计

## 1. 结论

删除调整为首版必备能力，采用“二次确认后的永久删除”：

- `/me` 私有资产页提供所有记录的删除入口，是历史记录管理的完整入口；
- Telegram 每次保存成功后的结果卡片增加删除按钮，服务于刚保存后立即纠错；
- 单条消息删除该条记录，相册删除整个 `media_group_id` 对应的信息流记录；
- 同时删除正文、标签、Telegram 原始 JSON、结构化数据、附件数据库行和服务器附件文件；
- 不增加软删除字段、回收站、自动清理任务、删除审计表或后台队列；
- 删除不操作用户原始 Telegram 消息，只删除 Journal 中已归档的副本；
- 删除失败直接显示实际错误，不把部分失败显示成成功，也不自动重试。

这与项目的单用户定位一致：删除入口足够直接，误触由二次确认控制，数据模型仍只有一份有效记录。

## 2. 删除单位

Web 中的一张信息流卡片就是一个删除单位。

| 内容 | 删除范围 |
| --- | --- |
| 普通文本或单个媒体 | 当前 `journal_entries` 行及其全部 `journal_assets` |
| Telegram 相册 | 同一 `chat_id + media_group_id` 的全部 `journal_entries` 行及其全部附件 |
| 公开记录 | 与私有记录相同；删除后公开详情、RSS 和 JSON Feed 同时不再出现 |
| 纯结构化记录 | 当前记录及其原始 Telegram JSON、结构化数据 |

相册不提供“只删除其中一张”的入口。当前产品把整个相册聚合为一张卡片，可见性和置顶也按整组操作；删除继续沿用同一边界，避免网页显示、Telegram 语义和数据库行为不一致。

## 3. Web 交互

删除入口只出现在登录后的 `/me`，公开首页与公开详情页不显示管理按钮。

1. 每张可编辑卡片底部在“编辑、置顶、公开/私有”之后增加“删除”。
2. 点击后在当前卡片内展开确认区，不使用浏览器原生确认框，也不跳转新页面。
3. 确认文案为“永久删除这条记录及其附件？此操作无法撤销。”；相册额外显示将删除的附件数量。
4. 提供“取消”和“确认删除”两个按钮；确认按钮使用明确的危险色。
5. 请求期间只锁定当前卡片的管理按钮。
6. 成功后从当前信息流、“往年今日”和详情状态中移除该卡片；如果用户位于该记录详情页，则返回 `/me`。
7. 失败时保留卡片和确认区，直接显示服务端错误。

不要求输入密码或记录标题再次确认。本站是单用户、已登录的个人资产页，两次明确点击足以控制误触；文字确认会明显拖慢高频整理。

## 4. Telegram 交互

保存成功卡片的按钮调整为：

```text
[公开/私有切换] [打开网站]
[🗑 删除]
```

点击“删除”后编辑同一条 bot 结果消息：

```text
确认永久删除这条 Journal 记录及其附件？
原始 Telegram 消息不会被删除。

[确认删除] [取消]
```

- 确认后调用 `rndc02` 内部删除接口，并把原结果消息编辑为“已删除此 Journal 记录。”；
- 取消后恢复原保存结果和按钮；
- callback data 使用短前缀、`publicId` 和一位可见性标记，保持在 Telegram 的 64-byte 限制内；
- 不新增通用 `/delete` 命令，也不建立 Telegram 历史列表。旧结果卡片没有新增按钮时，统一从 `/me` 删除。

这样覆盖两个真实主路径：刚保存错了可在 Telegram 原地处理，任意历史记录从网站集中管理，同时不把 bot 扩展成第二套后台。

## 5. API 与共享协议

新增两个语义一致、鉴权方式不同的接口：

### 5.1 Web 管理接口

```http
DELETE /api/me/entries/:id
Cookie: Journal 管理会话
```

仅 `/me` 登录态可调用。`:id` 可以是相册中任一成员的数据库 ID，服务端负责解析完整删除单位。

### 5.2 Telegram 内部接口

```http
DELETE /api/internal/telegram-entries/:publicId
Authorization: Bearer <JOURNAL_INGEST_TOKEN>
```

继续复用现有双节点内部鉴权，不新增 token、端口或节点间协议。

### 5.3 成功响应

```json
{
  "deletedEntryCount": 1,
  "deletedAssetCount": 2
}
```

共享协议增加删除结果 Zod schema。找不到记录返回 `404`，鉴权失败保持现有 `401`；重复删除不返回伪成功。

## 6. 后端处理

新增一个短小的 `JournalDeletionService`，负责把数据库删除和附件删除组织为一个明确主路径。Repository 只负责解析删除单位和执行 SQLite 行删除，Storage 只负责删除已经解析出的精确附件目录。

处理顺序：

1. 按 `id` 或 `publicId` 查询目标记录；不存在立即返回 `404`。
2. 普通记录只选中自身；相册按 `chat_id + media_group_id` 选出全组记录。
3. 一次性读取全组 `journal_assets.relative_path`，计算精确的记录目录和删除数量。
4. 校验每个目标都位于 `data/assets/YYYY/MM/<public_id>/`，禁止把数据根目录、`assets` 根目录或未解析路径交给递归删除。
5. 删除这些记录专属附件目录；任一文件操作失败立即终止，不执行数据库删除。
6. 在一个 SQLite transaction 中先删除对应 `journal_assets`，再删除对应 `journal_entries`。
7. 返回实际删除的记录数和附件数。

SQLite 与本地文件系统不存在真正的跨存储事务。首版不为极低概率的磁盘故障引入软删除状态机、消息队列或补偿任务；通过“精确路径校验、附件先删除、数据库单事务删除”保证正常主路径短而可审计。任何异常均直接暴露，由实际错误决定人工处理，不继续执行后续步骤。

当前外键没有 `ON DELETE CASCADE`，无需为这一功能重建 SQLite 表；显式先删附件行、再删记录行即可。也不新增数据库迁移或状态字段。

## 7. 删除后的可见结果

- 公开首页、公开详情、标签页、`/me`、搜索和“往年今日”不再返回该记录；
- 公开永久链接返回 `404`；
- 原附件 URL 因数据库授权记录已删除而返回 `404`；
- 公开媒体响应要求重新验证缓存，避免浏览器在删除后继续把旧的长缓存当作有效内容；
- RSS 与 JSON Feed 下次请求时不再包含该记录；
- 删除后可再次从原 Telegram 消息执行 `/note` 或 `/post`，它会作为新记录重新保存并获得新的 `publicId`；
- 置顶、公开/私有等状态随记录直接消失，不保留墓碑数据。

## 8. 备份边界

“永久删除”指当前运行中的 Journal 数据与媒体立即删除，不表示重写历史备份。

`rndc02` 现有 rclone 每日压缩备份会继续按 30 天规则保留。删除前生成的备份在到期前仍可能含有该记录，方案不扫描或修改已上传的压缩包。若未来从旧备份整体恢复，旧记录也可能随备份恢复；这是当前灾备模型的明确边界。

首版不增加跨备份删除清单或恢复后的自动二次删除，否则需要长期 tombstone、恢复协调和额外状态，超出个人工具所需的最小架构。

## 9. 最小实现范围

| 层 | 变更 |
| --- | --- |
| 共享协议 | 增加删除结果 schema 与类型 |
| Journal 后端 | 增加删除服务、Repository 整组删除、Storage 精确目录删除、两条 DELETE 路由 |
| Telegram client | 增加按 `publicId` 删除请求 |
| Telegram handler | 保存结果卡片增加删除、确认、取消三个 callback 交互 |
| Vue 前端 | API 增加删除请求，composable 移除本地记录，卡片增加内联确认区 |
| 数据库与部署 | 无迁移、无新环境变量、无新服务、无定时任务 |

## 10. 首版验收行为

- 文本记录可从 `/me` 经二次确认删除，页面立即移除该卡片。
- 带图片、视频、语音或文件的记录删除后，记录与全部附件均不可访问。
- 相册从任一聚合卡片删除时整组消失，组内附件全部删除。
- 公开记录删除后，公开首页、永久链接、RSS 和 JSON Feed 均不再出现。
- Telegram 新保存结果可原地发起删除、取消确认或确认删除，不新增聊天消息。
- 删除不会删除用户发送的 Telegram 原始消息。
- 未登录 Web 请求、无效内部 token、未知记录和附件文件操作失败均明确报错。
- 删除不影响提醒、订阅、其他 bot 功能或 `rndc02` 上已有服务。

## 11. 明确不做

- 回收站、软删除、撤销期限；
- 批量选择、按筛选结果批量删除、清空全部；
- 单独删除相册中的某一个附件；
- 自动删除 Telegram 原消息；
- 改写或提前删除历史 rclone 备份；
- 删除审计、操作日志页面、后台清理队列；
- 为删除失败加入重试、静默跳过或后台补偿。
