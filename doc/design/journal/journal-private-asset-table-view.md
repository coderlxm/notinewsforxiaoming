# Journal「我的资产」双视图实现方案

## 1. 文档状态

- 状态：已 Review，已实施
- 页面范围：登录后的 `/me`「我的资产」
- 本次目标：在保留现有瀑布流的前提下，增加可切换的表格视图
- 不涉及：公开信息流、详情页视觉、Journal 数据模型、数据库和服务端接口

## 2. 当前实现判断

当前「我的资产」并不是一份独立的文件列表，而是按 `JournalEntry` 展示的记录流：一条记录可以包含正文、文章、图片、视频、音频或文件等多个素材。现有私有接口已经返回表格首版需要的时间、来源、内容类型、状态、标签和素材元数据，并负责筛选、固定顺序与游标分页。

因此首版建议明确采用以下口径：

> 表格一行代表一条 Journal 记录，而不是一个物理文件；该记录包含的素材数量和总体积在同一行汇总展示。

这样表格与瀑布流只是同一结果集的两种呈现方式，可以直接共用当前筛选、分页、详情和管理能力，不需要复制状态，也不需要增加资产级接口。如果未来需要逐文件检索、排序或清理，再单独设计“一行一个文件”的素材管理页。

## 3. 产品方案

### 3.1 视图切换入口

视图切换只在已登录的「我的资产」中显示，放在“往年今日”和主结果列表之间，作为结果区工具条的一部分，不放进页面标题右侧现有的刷新、发布、设置等操作区，避免头部继续变拥挤。

```text
┌──────────────────────────────────────────────────────────────┐
│ 筛选条件                                                     │
├──────────────────────────────────────────────────────────────┤
│ 往年今日                                                     │
├──────────────────────────────────────────────────────────────┤
│ 当前资产                                      [瀑布] [表格] │
├──────────────────────────────────────────────────────────────┤
│ 当前选中视图的内容                                           │
└──────────────────────────────────────────────────────────────┘
```

切换控件采用两个等高按钮，文字与图标同时表达含义：

- 瀑布：保持当前默认视图；
- 表格：进入高信息密度的记录表；
- 当前项使用现有强调色、边框和底色表达，不新增一套视觉语言；
- 使用 `aria-pressed` 表达选中状态，键盘焦点样式沿用现有按钮规范。

### 3.2 切换行为

- `/me` 默认代表表格视图；
- `/me?view=waterfall` 代表瀑布流，已有的 `/me?view=table` 链接仍按表格视图解析；
- 切换时不重新请求数据，不清空筛选条件，也不重置已经加载的分页数据；
- 刷新页面、浏览器前进或后退时，当前视图由 URL 恢复；
- 不写入 `localStorage`，避免增加一份和路由可能冲突的持久状态；
- 从表格打开详情时使用 `/me?entry=<id>`，关闭详情后仍回到表格；
- 从顶部导航重新进入 `/me` 时采用默认表格视图。

`FeedView` 的缓存 key 仍保持现有 `private`，不会因为视图切换创建两份私有数据实例。视图状态只决定结果区渲染哪个组件。

### 3.3 表格信息结构

桌面端建议使用以下列，交由 Element Plus `ElTable` 负责列布局与横向滚动：

| 列 | 内容 | 设计目的 |
| --- | --- | --- |
| 时间 | 发布时间；次行显示最近更新时间；置顶记录带置顶标记 | 快速按时间扫视 |
| 内容 | 预览图、标题或正文摘要、标签 | 作为一行的主要识别信息 |
| 状态 | 草稿，或公开 / 私有 | 直接发现未发布和私有记录 |
| 打开 | 明确的打开按钮 | 避免把整行变成不可见的点击区域 |
| 类型 | Telegram / Web 来源；图片、视频、文章等内容类型 | 区分记录来源与形态 |
| 素材 | 素材项数及已知总体积 | 了解记录实际占用与复杂度 |

内容列规则：

- 富文本文章优先显示标题，普通记录显示正文摘要；
- 有视觉素材时只加载第一张可用的 `previewUrl` 作为小尺寸预览，不在表格中加载原图或播放视频；
- 纯文字、音频或文件记录显示真实类型标识，不制造假缩略图；
- 摘要最多两行，标签最多显示一行，避免单条记录把表格撑得过高；
- 素材体积由已有 `byteSize` 汇总；缺少体积元数据时只展示素材数量，不把未知值当作零。

表头首版不提供排序。当前接口采用“置顶优先、记录时间倒序”的固定游标顺序，在浏览器中只对已加载页排序会产生误导；真正的列排序应与服务端游标规则一起设计。

### 3.4 行交互与管理动作

首版表格聚焦“快速扫视和打开”，不在每一行重复实现瀑布卡片的正文编辑、发布时间弹窗和删除确认状态：

- 已发布记录点击“打开”进入现有详情浮层，在浮层中继续使用完整管理菜单；
- 草稿沿用当前行为，直接进入草稿编辑页；
- 标签仍可点击并应用到现有筛选；
- 置顶、可见性、编辑和删除的业务实现保持不变，只是表格中统一从详情进入；
- 瀑布流原有卡片内快捷管理不做任何删减。

这一选择能避免出现两套编辑和删除交互，也让首版变更集中在展示层。代价是从表格管理已发布记录会比瀑布流多一次“打开详情”，属于本方案明确接受的取舍。

### 3.5 移动端形态

移动端仍然呈现表格，而不是切回卡片：

- 将“时间、内容、状态、打开”放在列顺序前部，来源、类型和素材位于后部；
- 缩略图缩小，摘要保持最多两行，标签不占用额外行；
- 通过 `ElTable` 自身的横向滚动查看后部次要列，不把所有信息强行压缩到手机宽度；
- 不使用脚本监听视口，不维护第二份移动端列状态，也不渲染另一套移动表格；
- 不设置固定高度，避免页面纵向滚动与表格内部纵向滚动互相争抢。

这样移动端仍然能感知自己处于表格视图，核心内容也能优先出现；需要查看完整元数据时再横向移动。`ElTable` 能稳定处理这一滚动边界，但不会自动决定哪些信息更重要，因此列顺序和单元格内容仍由 Journal 自己设计。

### 3.6 加载、空状态与分页

- 表格复用现有 Vant 无限列表和游标分页，加载更早记录时直接追加行；
- 初次加载、刷新和重新筛选使用贴合列宽的表格骨架行，不复用瀑布流的长方形卡片骨架；
- “没有符合当前筛选条件的记录”和“已经看到全部记录”继续使用现有文案与位置；
- 瀑布流仍由 `WaterfallFeed` 自己报告布局完成；表格没有异步排版引擎，由 `FeedView` 在表格 DOM 更新后完成现有分页和刷新状态收口；
- 该状态衔接使用显式事件和现有加载函数，不新增 `watch`，也不引入动画帧调度。

## 4. 技术实现

### 4.1 状态与路由

新增共享类型：

```ts
type AssetView = 'waterfall' | 'table';
```

由 `App.vue` 统一解析私有路由：

- 无 `view` 参数时为 `table`；
- `view=waterfall` 时为 `waterfall`，已有的 `view=table` 仍解析为 `table`；
- 视图类型通过 prop 单向传入 `FeedView`；
- `FeedView` 通过 `changeAssetView` 事件请求切换，由 `App.vue` 更新 URL；
- 私有详情的打开、关闭和删除返回路径都保留当前 `view` 参数；
- 私有 Feed 的 KeepAlive key 不包含视图类型，确保两种展示共享同一份筛选结果和分页数据。

这种数据流让 URL 成为唯一视图状态源，不需要在组件内部同步路由与本地状态。

### 4.2 组件拆分

```text
App.vue
└─ FeedView.vue                    数据、筛选、分页、详情与视图选择
   ├─ AssetViewSwitch.vue          纯展示的双按钮切换器
   ├─ WaterfallFeed.vue            现有瀑布流，保持原实现
   └─ AssetTableView.vue           表格结构与表格加载状态
      ├─ AssetTableContentCell.vue 内容列的缩略图、摘要与标签
      └─ JournalAssetTablePlaceholder.vue
```

组件职责：

- `AssetViewSwitch.vue`：接收当前 `view`，只发出用户选择；
- `AssetTableView.vue`：封装 `ElTable` 与 `ElTableColumn`，接收 `entries` 和加载状态，通过列插槽输出打开记录、选择标签和布局完成事件；
- `AssetTableContentCell.vue`：负责内容列的缩略图、摘要和标签，不持有请求状态；
- `FeedView.vue`：继续作为唯一的数据与业务动作编排层，按当前视图选择渲染器；
- `WaterfallFeed.vue`：不改布局算法、卡片结构和现有交互。

表格使用项目已经安装的 Element Plus `2.14.3` 中的 `ElTable` 和 `ElTableColumn`。当前 Vue `3.5.x` 满足该版本声明的 Vue peer dependency，两个组件及其类型也已经由本地包正常导出，不增加新依赖。

具体接入约束：

- 继续采用按需导入，只在 `main.ts` 增加 Table 与 TableColumn 对应样式，不载入 Element Plus 全量样式；
- 设置稳定的 `row-key="id"`，让分页追加和记录更新复用现有行；
- 使用普通 `ElTable`，不使用 `ElTableV2`。当前数据由游标分页逐步追加，没有需要虚拟表格解决的超大一次性数据集；
- 不给表格设置 `height` 或 `max-height`，纵向滚动仍由当前页面承担，`ElTable` 只处理列布局与横向溢出；
- 内容、状态、素材等非标准单元格使用作用域插槽，数据变更仍由 props 向下传递，用户操作通过事件向上返回；
- 使用 Journal 的颜色变量覆盖 `ElTable` 表头、行、边框、悬停和深色主题变量，避免出现一块突兀的默认后台表格；
- 内容摘要继续使用明确的两行截断，不依赖只在鼠标悬停时可用的溢出 Tooltip；
- 加载态继续使用贴合最终列结构的自定义骨架行，不使用整表遮罩式 loading。

`ElTable` 的价值是减少列宽、对齐、滚动和后续扩展的基础实现；缩略图、信息层级、移动端列顺序和 Journal 风格仍由本项目负责。相较原生表格，它会增加一部分表格组件样式和运行时代码，但在当前已经采用 Element Plus 的项目中，这个成本小于长期维护一套自定义表格布局。

### 4.3 渲染切换

结果区采用互斥渲染：

```text
assetView === waterfall → WaterfallFeed
assetView === table     → AssetTableView
```

不同时把瀑布流隐藏在页面中。切到表格时卸载 Masonry 实例，切回时用父组件保留的同一份 `entries` 重新挂载瀑布流，避免隐藏容器宽度影响瀑布流测量，也避免两套媒体节点同时占用内存。

### 4.4 数据与接口

首版不增加服务端改动：

- 列表数据继续来自当前私有 Feed 接口；
- 筛选继续由当前 `FeedFilters` 和服务端完成；
- 分页继续使用当前 `nextCursor`；
- 缩略图、素材数量和体积直接从 `JournalEntry.assets` 派生；
- 日期和文件体积继续复用现有 `formatEntryTime`、`formatFileSize`。

## 5. 预计文件范围

### 新增

- `web/src/components/journal/AssetViewSwitch.vue`
- `web/src/components/journal/AssetTableView.vue`
- `web/src/components/journal/AssetTableContentCell.vue`
- `web/src/components/journal/JournalAssetTablePlaceholder.vue`

### 修改

- `web/src/types.ts`：增加视图类型；
- `web/src/App.vue`：解析并保留 `view` 查询参数，传递视图状态；
- `web/src/components/journal/FeedView.vue`：接入切换器和表格渲染器，复用现有列表状态；
- `web/src/main.ts`：按需载入 Element Plus Table 与 TableColumn 样式。

`web/src/router.ts` 不需要增加新页面路由；表格通过 `/me` 的查询参数表达。

## 6. 实施顺序

1. 增加视图类型和 `/me` 查询参数解析，先打通刷新、前进后退与详情返回路径。
2. 增加结果区视图切换器，并让默认 `/me` 渲染 `AssetTableView`。
3. 使用 `ElTable` 实现表格、内容单元格和移动端横向浏览。
4. 接入表格骨架、空状态、无限分页与刷新完成状态。
5. 对齐表格的颜色、边框、字号、间距和深色主题，使其与现有 Journal 页面一致。

## 7. Review 验收口径

- 直接访问 `/me` 时页面默认显示表格视图；
- 切换到表格后立即使用当前已经加载的记录，没有额外刷新或筛选丢失；
- 表格中能快速识别时间、内容、来源、状态和素材规模；
- 表格继续按现有服务端顺序追加更早记录；
- 从表格打开详情、关闭详情后仍返回表格及原有筛选结果；
- 草稿从表格打开后仍进入原有编辑页；
- 刷新 `/me` 后仍为表格视图，刷新 `/me?view=waterfall` 后仍为瀑布流；
- 切回瀑布流后复用当前列表数据，现有瀑布流交互保持完整；
- 手机宽度下优先看到时间、内容、状态和打开入口，并可横向查看其余列，不退化成瀑布卡片；
- 表格加载占位与最终行的高度和列结构接近，不产生明显位移。

## 8. 首版明确不做

- 不把每个图片或视频拆成独立表格行；
- 不增加列排序、批量选择、批量删除或导出；
- 不增加列宽拖动、列自定义、虚拟滚动；
- 不在公开信息流增加表格入口；
- 不新增接口、数据库字段或视图偏好持久化；
- 不复制一套表格内正文编辑和删除确认流程。

这些能力都可以在真实使用表明有必要后继续扩展，不进入本次双视图的最小实现范围。
