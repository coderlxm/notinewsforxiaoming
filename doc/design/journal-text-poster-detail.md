# Journal 纯文字海报详情设计方案

## 1. 文档状态

- 状态：决策已确认，首版已实施
- 范围：普通纯文字记录的 Web 详情展示
- 核心形态：桌面端“文字海报 + 完整正文”双栏，移动端“文字海报在上 + 完整正文在下”
- 实现原则：仅调整前端展示，不改变 Telegram 记录方式、数据库、接口和媒体存储

## 2. 当前行为与问题

### 2.1 当前源码行为

- `JournalDetailLayout.vue` 只有在记录包含图片、视频、动画或视觉贴纸时才渲染左侧 `JournalMediaStage`。
- 普通纯文字记录没有视觉媒体，因此进入 `detail-layout--single`，详情内容被限制为最大 `760px` 的单栏。
- `JournalDetailOverlay.vue` 同样只依据视觉媒体决定弹层尺寸，无视觉媒体时使用 `detail-overlay--compact`。
- 记录接口已经提供 `contentText`、正文格式、标签、时间和可见性；生成文字海报不缺数据。

### 2.2 产品判断

纯文字碎片、疑问和短感想虽然没有真实图片，但仍可拥有一个明确的视觉主体。左侧海报承担“第一眼看到的内容”，右侧继续承担完整阅读、元信息和管理操作，两者职责不同，因此允许文字内容有意重复。

首版不把海报生成并保存成图片，而是用 CSS 背景与真实文本实时渲染。这样能得到同类视觉效果，同时不增加图片生成、上传、缓存、迁移和删除链路。

## 3. 首版目标与非目标

### 3.1 目标

1. 普通纯文字记录在桌面详情弹层中也采用现有 `62% / 38%` 双栏结构。
2. 左侧展示与项目视觉一致的文字海报，右侧继续展示完整正文和已有操作。
3. 长文本在海报中保持稳定版式，不挤压、不溢出；完整内容始终可在右侧阅读。
4. 移动端不压缩成窄双栏，而是先展示海报，再自然衔接正文。
5. 不改变带图片、视频、语音、文件或富文本文章的现有详情行为。

### 3.2 非目标

- 不生成、保存或下载真实图片。
- 不增加海报主题选择器、自定义背景、字号配置或编辑入口。
- 不做关键词识别、语义分析和自动重点标黄。
- 不随机选择背景，避免同一条记录每次打开时外观变化。
- 不修改 Telegram 消息，也不让海报成为新的记录资产。
- 不加入 Canvas、截图工具或新的 npm 依赖。

## 4. 适用条件

一条记录同时满足以下条件时展示文字海报：

```ts
entry.bodyFormat === 'plain'
&& entry.contentText.trim().length > 0
&& entry.assets.length === 0
```

因此首版只处理“真正的纯文字记录”：

- 图片、视频、动画和视觉贴纸继续使用现有媒体舞台；
- 语音、音频和文件记录继续使用现有单栏，避免海报掩盖其主要内容类型；
- 富文本文章继续使用独立阅读形态，不压入右侧窄栏；
- 空正文记录不构造无意义海报。

## 5. 详情形态

### 5.1 桌面端

视口宽度不小于 `960px` 时，纯文字详情复用媒体详情的弹层尺寸和分栏比例：

```text
┌──────────────────────────────────────────────────────────┐
│                              │ 作者 / 时间         关闭 │
│                              │                        │
│       CSS 纸张背景            │ 完整正文               │
│                              │                        │
│       文字视觉摘要            │ #标签                  │
│                              │                        │
│       装饰标点 / 日期          │ 私有管理动作            │
│                              │                        │
└──────────────────────────────────────────────────────────┘
             约 62%                         约 38%
```

- 左侧沿用 `JournalMediaStage` 已建立的视觉占位，不新增第三种弹层尺寸。
- 海报本体保持 `4:5` 的视觉比例；桌面端铺满同为 `4:5` 的左侧舞台，不在舞台内部再次设置百分比宽度或固定上限，避免形成大面积黑边。
- 桌面弹层把海报确定的 `4:5` 比例作为左侧舞台比例，复用真实图片的宽高比尺寸算法动态计算弹层宽高，不再使用通用媒体弹层尺寸。
- 右侧继续复用 `JournalDetailContent`，它是正文的权威展示，不复制业务操作。

### 5.2 移动端

小于 `960px` 时继续使用现有全屏详情和单一滚动轴：

1. 顶部显示文字海报；
2. 下方显示完整正文、元信息和管理操作；
3. 海报宽度占满内容区，高度由固定比例控制，不在纸张外保留黑色舞台边距；系统安全区留白进入纸张内部；
4. 不在移动端维持左右双栏，也不产生横向滚动。

## 6. 文字海报视觉

### 6.1 首版固定主题

首版只提供一套稳定主题，延续当前项目的“个人档案 / 纸张 / 时间轴”语言：

- 底色使用低饱和纸张色，而不是照搬小红书黑色面板或高亮黄色；
- 以现有石榴红作为小面积强调色；
- 背景使用 CSS 渐变、细线和低透明度的大标点形成层次；
- 日期作为辅助信息放在边角，继续呼应信息流的日期脊柱；
- 正文使用项目已有字体变量，不额外加载字体文件。

背景全部由 CSS 生成，不依赖远程图片。浅色和深色站点主题下都保持同一张“纸”的品牌色，只调整外围舞台与边界的对比度，避免海报本身随系统主题完全反相。

### 6.2 装饰标点

装饰符号只根据现有文本做确定性选择：

- 包含 `?` 或 `？`：显示低透明度大问号；
- 其他内容：显示低透明度引号。

装饰元素设置 `aria-hidden="true"`，不参与正文含义，也不增加复杂的内容分类逻辑。

### 6.3 文本层级

海报直接使用 `contentText`，保留原始换行，不使用 `v-html`。根据字符数量采用三个明确字号档位：

| 文本长度 | 海报字号倾向 | 展示方式 |
| --- | --- | --- |
| `1–30` 个字符 | 大 | 完整展示，适合一句话或疑问 |
| `31–70` 个字符 | 中 | 完整展示，收紧行距 |
| `71` 个字符以上 | 小 | 展示视觉摘要并限制行数 |

长文本海报只承担预览。它在可用行数内截断并显示省略号，右侧仍呈现完整正文，因此不需要为了塞下全文持续缩小字号。

首版不做截图中那类词语标黄。自动判断“应该强调哪个词”缺少可靠数据依据，也会把一个简单展示功能扩展成内容分析功能；以后如果确实需要，可基于用户显式标记设计，而不是猜测。

## 7. 组件与最小改动

### 7.1 新增组件

新增 `web/src/components/journal/JournalTextPoster.vue`：

- 接收一个 `JournalEntry`；
- 派生字号档位和装饰符号；
- 渲染背景、日期与文字摘要；
- 不保存内部业务状态，不发出事件；
- 整个海报区域设置 `aria-hidden="true"`，避免屏幕阅读器重复朗读右侧完整正文。

### 7.2 调整 `JournalDetailLayout.vue`

新增两个派生状态：

- `hasTextPoster`：符合第 4 节适用条件；
- `hasLeadingStage`：存在视觉媒体或文字海报。

渲染优先级保持唯一且清晰：

1. 有视觉媒体时渲染 `JournalMediaStage`；
2. 否则满足纯文字条件时渲染 `JournalTextPoster`；
3. 其他内容不渲染左侧舞台。

布局 class 由“是否存在媒体”改为“是否存在左侧舞台”。`JournalDetailContent` 当前的 `hasMediaStage` 属性可同步改名为 `hasLeadingStage`，使移动端间距语义与真实行为一致。

### 7.3 调整 `JournalDetailOverlay.vue`

弹层尺寸判断加入同一纯文字条件：

- 视觉媒体或纯文字海报：使用现有宽版详情尺寸；
- 富文本文章：保持现有富文本尺寸；
- 语音、文件等：保持现有紧凑尺寸。

该判断保持为简单 computed，不建立新的全局状态或内容类型系统。

### 7.4 不需要调整的部分

- `JournalDetailContent.vue` 除可选的属性语义改名外，不改变正文和操作逻辑；
- `JournalMediaStage.vue` 不承担文字海报，避免继续膨胀媒体组件职责；
- `App.vue` 的路由、历史和弹层关闭逻辑不变；
- 后端接口、数据库结构、Telegram bot 和媒体存储全部不变。

首版实际范围是一个新展示组件，以及详情布局和弹层尺寸两处接线。

## 8. 内容与可访问性边界

- 右侧完整正文是唯一语义正文，海报只是视觉副本。
- 海报正文使用 Vue 文本插值，避免把 Telegram 文本解释成 HTML。
- 日期来自记录已有时间，并使用现有日期格式能力，不另写日期解析。
- 超长单词、URL 和连续字符允许换行，不撑破海报边界。
- 海报不提供点击行为，不与关闭、编辑或媒体控制争夺交互区域。
- 现有弹层进入、退出过渡保持不变，不新增逐帧测量或 `requestAnimationFrame`。

## 9. 验收边界

1. 不含附件的普通纯文字记录在桌面详情中显示双栏。
2. 左栏是稳定的文字海报，右栏仍可读到完整原文。
3. 短、中、长三类文本均不会溢出海报；长文本只在海报内省略。
4. 问句与普通陈述使用确定性的不同装饰标点。
5. 移动端海报在正文上方，页面只有纵向滚动。
6. 图片和视频详情继续使用原媒体舞台；竖图、视频的 `contain` 行为不受影响。
7. 语音、文件与富文本文章保持当前详情布局。
8. 公开信息流与个人资产中的同一纯文字记录使用相同海报规则。
9. 编辑正文后重新渲染详情时，海报直接反映新的 `contentText`，不需要同步额外资产。

## 10. 首版决策建议

建议首版直接采用以下组合：

1. 所有真正的纯文字记录都启用海报，长文本用摘要解决，不再增加“仅短文本启用”的配置。
2. 只提供一套项目自有的固定纸张主题，不做主题选择和随机样式。
3. 不做自动关键词高亮，保留原文语义和实现确定性。
4. 海报只用于 Web 详情展示，不生成真实图片，不回写 Telegram。

这组决策能以最小前端改动解决纯文字详情缺少视觉主体的问题，也给以后增加“显式选择模板并导出图片”留下独立扩展空间，而不让首版承担那条资产链路。
