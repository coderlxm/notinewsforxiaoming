# Journal 部署性能优化报告

## 结论

本轮已完成 Journal Docker 构建缓存和健康检查调度优化。缓存命中后的 Journal 部署从优化前的 3 分 36 秒降至 2 分 53 秒；仅部署 Journal 的同版本复测为 2 分 28 秒。

当前主要耗时已经从构建和健康检查转移到完整镜像的打包、SSH 上传与服务器加载。后续若继续优化，应优先改造镜像传输方式。

## 已完成优化

### Docker 构建缓存

GitHub Actions 已改用 Docker Buildx：

- 使用 `docker/setup-buildx-action@v4` 初始化构建器。
- 使用 `docker/build-push-action@v7` 构建并加载本地镜像。
- 使用独立的 `journal` scope 读写 GitHub Actions cache。
- 使用 `mode=max` 保存中间构建层，使依赖安装、前端构建和运行时系统包层能够复用。
- 保留现有不可变 commit SHA 镜像标签及后续 `docker save` 发布路径。

首次建立缓存时构建步骤耗时 2 分 45 秒，其中包含完整构建、镜像导入和首次缓存导出成本。缓存命中后构建步骤为 60 至 61 秒。优化前最近一次构建为 1 分 23 秒，因此稳定命中后该步骤减少约 22 至 23 秒。

### 健康检查调度

Journal 容器健康检查间隔已从 30 秒调整为 5 秒，检查内容、超时、失败次数和启动保护期保持不变。

部署日志中的容器健康等待时间：

- 优化前：约 30.5 秒。
- 优化后：约 11 秒。
- 实际减少：约 19.5 秒。

同时修复了 Compose 配置未进入主机发布包的问题。现在 `deploy/journal/compose.yaml` 会随 host assets 上传，由发布脚本安装到 `/opt/journal/compose.yaml`，因此后续 Compose 配置变更能够通过既有发布主路径生效。

服务器运行时最终值已确认：

- `Interval`: 5 秒
- `Timeout`: 5 秒
- `StartPeriod`: 20 秒
- `Retries`: 1

## 仍可优化的内容

### 1. 改为分层镜像传输

当前每次都会把完整镜像保存成 tar，经 SSH 上传后再执行 `docker image load`。上传曾在不同运行中出现 32 秒、35 秒、40 秒、2 分 11 秒和接近 4 分钟的明显波动，是当前最不稳定的阶段。

优先方案是将镜像推送至容器镜像仓库，由服务器按 Docker layer 拉取。未变化的 Node、系统工具和依赖层无需重复传输及加载，可同时降低网络波动和服务器完整解包成本。

### 2. 缩小运行时镜像

运行时镜像包含 `ffmpeg`、`libheif-examples`、完整 `node_modules` 和 TypeScript 运行环境。可以根据 Journal 服务实际运行依赖继续拆分生产依赖或媒体处理能力，减少镜像体积。该项应以实际依赖边界为依据，不宜只为追求镜像数字进行复杂拆分。

### 3. 降低缓存导出和镜像导入成本

缓存命中后仍需约 60 秒，其中不仅包含构建，还包含从 BuildKit 导出可供 `docker save` 使用的本地镜像，以及更新 GitHub Actions cache。改为直接推送镜像仓库后，可以一并取消本地导入、完整打包和缓存重复导出的部分成本。

### 4. 分离工作流变更的部署范围

当前 `.github/workflows/deploy.yml` 同时属于 Journal 和 Bot 的变更范围，因此修改任一部署流程都会顺序部署两个服务。本轮 push 因此额外执行了 26 秒 Bot job。可以将两个服务的工作流拆开，或让手动发布明确选择服务；普通 Journal/Web 代码变更目前已经能够正确跳过 Bot。

## 优先顺序

1. 使用容器镜像仓库替代完整 tar 的 SSH 传输。
2. 在镜像分层发布完成后重新测量构建、推送、拉取和激活耗时。
3. 若镜像体积仍是主要瓶颈，再按 Journal 的真实运行依赖缩小运行时镜像。
4. 最后处理部署工作流自身的服务范围拆分。
