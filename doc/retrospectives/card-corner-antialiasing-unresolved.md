# 卡片折角白边问题复盘

日期：2026-08-10

## 结论

本次 AI 协作未能解决卡片右上角三角折纸角标的白边问题。

用户在正常页面和放大截图中均能持续看到折角边缘存在浅色毛边，颜色明显来自角标下方的图片。多轮修改没有达到用户要求的视觉结果，最终决定放弃当前三角折纸方案，改用不包含斜边的角标结构。

这份记录描述的是本项目中的实际失败结果，不将其扩大为“所有浏览器或所有实现都无法解决”的普遍技术结论。

## 原始目标

在瀑布流卡片右上角展示状态角标：

- 置顶内容显示置顶图标。
- 加密内容根据状态显示加密或已解密图标。
- 角标应像折纸一样紧贴右上角，而不是独立悬浮的徽章。
- 颜色应适配文字画报模板、图片、视频和文章卡片。
- 保留卡片原有圆角。
- 角标边缘不能出现可察觉的浅色毛边、阴影或额外分隔线。

## 实际问题

三角折角覆盖在浅色图片上时，斜边和右上圆弧会出现一条细微但可见的浅色边缘。放大后可以看到边缘像素混入了底图颜色。

用户以实际视觉结果为验收标准。即使样式声明、计算尺寸或局部截图显示某项技术措施已经生效，只要页面上仍能看到白边，就不能认定问题已经解决。

## 为什么这些修改始终无效

### 不同 API 最终生成的是同一种边缘

`clip-path`、硬切渐变、SVG 多边形和 CSS 边框三角形看起来是四种实现，进入浏览器绘制阶段后却都需要完成同一件事：把一条连续的斜线映射到由方形像素组成的屏幕上。

斜线会穿过部分像素。为了让它看起来平滑，浏览器会为这些像素计算一个介于 0 和 1 之间的覆盖率。最终颜色可以简化理解为：

```text
最终像素 = 角标颜色 × 覆盖率 + 底图颜色 × (1 - 覆盖率)
```

因此，浅色图片位于角标下方时，斜边必然会出现一列同时包含角标色和图片色的过渡像素。更换绘制 API 没有改变这条颜色计算，只是让浏览器通过另一条代码路径重新生成同一类过渡像素。

### 同色描边和向外扩展只会移动边界

给角标增加同色描边，或者把路径向图片方向扩展 0.5px 至数个像素，可以覆盖原来的混色边。但扩展后的图形仍然需要在新的最外侧位置结束，于是浏览器会在那里生成一条新的抗锯齿边。

这类修改能够把白边移动几个像素、改变宽度或降低显眼程度，却不能让“角标色与图片色的交界”消失。此前增加 4px SVG 同色描边仍然失败，就是因为新描边本身产生了新的外边缘。

### `shape-rendering` 不能提供确定保证

`crispEdges` 和 `optimizeSpeed` 只是向浏览器表达渲染偏好的提示。浏览器可以关闭部分抗锯齿，也可以只处理接近水平或垂直的线条，并不保证对任意斜线关闭插值。

即使 SVG 内部选择了更锐利的绘制方式，SVG 元素作为一个图层参与页面的最终缩放和合成时，浏览器仍可能重新采样其边缘。因此源码中已经出现对应属性，并不能证明最终屏幕像素不会混色。

### 整数尺寸不能保证整条斜线像素对齐

把折角宽高改成 44px 或 40px，只解决了图形尺寸本身的小数问题，没有解决以下因素：

- 瀑布流布局可能把整张卡片放在小数坐标上。
- 页面缩放比例和设备像素比会再次换算坐标。
- 即使起点和终点都位于整数像素，连接两点的斜线仍会穿过中间像素。

所以整数尺寸可以减少额外的模糊，却无法消除斜线本身的覆盖率计算。`translate3d` 只会改变合成方式，也不会自动把坐标取整。

### 像素阶梯消除了斜线，也破坏了斜线

用大量水平和垂直小线段模拟斜边，可以让每一段更容易对齐设备像素。但这相当于主动选择没有颜色混合的锯齿边缘。

它满足“没有半透明过渡像素”，却不再满足“折角斜边应当平滑”。这不是同时解决两个要求，而是在清晰毛边和可见锯齿之间换了一种瑕疵。

### 阴影和混合模式只是在视觉上遮盖

深色描边或阴影可以压住浅色过渡像素，但会引入新的视觉语义。用户已经明确认为阴影破坏了角标效果，因此不能把“白边不再显眼”当作“白边已被解决”。

`mix-blend-mode: multiply` 会改变角标覆盖区域与照片的颜色运算，使亮色更暗，但不会改变图形最外侧仍然存在部分覆盖像素的事实。它还会使同一个角标在不同照片上呈现不同颜色，破坏既定的模板配色和状态识别。

### 圆角和斜边是两个独立的抗锯齿边界

卡片原有右上圆角负责裁切整张卡片，三角折角又在卡片内部形成一条斜边。两者都可能生成部分覆盖像素。

取消右上圆角确实可以移除圆弧上的合成边，但会直接破坏已确认的卡片轮廓，因此不是有效修复。保留圆角时，也不能把圆弧边和三角斜边误认为同一个问题后统一覆盖。

### Canvas 也不能同时满足全部条件

把照片和角标绘制进同一个 Canvas，可以消除两个独立 DOM 图层之间的透明合成接缝，但只要仍要求一条平滑斜线，Canvas 也需要在角标色和照片色之间生成抗锯齿过渡像素。

如果关闭 Canvas 抗锯齿或逐像素写入二值颜色，可以做到没有混色，但边缘会成为像素阶梯。它仍然无法同时满足“平滑斜边”和“零颜色混合”，同时还会破坏当前图片、视频和响应式媒体的原生渲染路径。

### 根本约束冲突

本次反复修改无效的根本原因不是某个 CSS 属性没有写对，而是同时提出了以下三个约束：

1. 折角必须使用平滑的斜边。
2. 斜边必须直接覆盖任意高反差图片。
3. 放大后边缘不能包含任何底图混色像素，也不能用描边、阴影或其他过渡遮盖。

在栅格屏幕上，平滑斜边依赖部分覆盖像素；零混色要求每个像素只能完全属于角标或完全属于图片。前者需要抗锯齿，后者要求二值硬边，两者不能同时成立。

因此后续需要改变的不是绘制 API，而是至少放开一个视觉约束：接受极细的抗锯齿过渡、接受明确的分隔边、接受像素锯齿，或者取消角标与图片直接相交的斜边结构。

## 已尝试的实现

### CSS 裁切与渐变

- 使用 `clip-path` 绘制三角形。
- 使用硬切线性渐变代替裁切。
- 移除人为绘制的折痕线。
- 扩大三角区域并尝试覆盖斜边。

结果：浅色边缘仍然存在。

### SVG 绘制

- 使用 SVG `polygon` 绘制折角。
- 尝试 `shape-rendering="crispEdges"`。
- 尝试 `shape-rendering="optimizeSpeed"`。
- 增加同色描边，并沿圆角增加同色内描边。

结果：浏览器仍然会在最终合成结果中产生可见的底图混色像素。

### 像素和定位处理

- 将折角尺寸调整为桌面端 44px、移动端 40px。
- 检查瀑布流布局中的实际坐标和设备像素比。
- 尝试以水平、垂直的小台阶模拟斜线。

结果：没有达到视觉验收要求。瀑布流卡片的位置仍可能落在亚像素坐标，且最终画面仍能看到浅色边缘。

### 视觉遮盖

- 增加同色扩展和边线。
- 增加窄幅深色阴影模拟折痕。
- 尝试 `mix-blend-mode: multiply` 抑制亮色混合。

结果：边线和混合模式没有消除问题；阴影虽然能够弱化白边，但视觉效果被用户明确否决。

### 其他绘制路径

- 使用原生 CSS 边框三角形替代 SVG 和裁切。

结果：绘制路径发生变化，但实际视觉问题仍然存在。

## 未采用的方案

### Canvas 同层合成

将原图片和角标绘制到同一个 Canvas，属于与上述方案原理明显不同的路线，但会改变当前媒体渲染主路径：

- 静态图片需要重新处理加载、缩放和清晰度。
- 视频需要持续同步画面，复杂度明显扩大。
- 多图卡片、响应式尺寸和深浅色模式都需要额外处理。
- 会牺牲现有原生图片和视频元素的行为。

相对于一个状态角标，这个改造范围不合理，因此没有实施。

## 权威资料能够确认的范围

SVG 的 `shape-rendering` 是给浏览器的渲染提示，不保证对所有斜线关闭抗锯齿。规范也说明裁切路径通常会进行抗锯齿处理。

- [MDN：shape-rendering](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/shape-rendering)
- [W3C：SVG Rendering Model](https://www.w3.org/TR/SVG11/render.html)

这些资料可以解释为什么更换 SVG 渲染提示不能保证消除毛边，但不能单独证明所有可能的前端实现都无法解决。

## 本次协作的问题

AI 在已经出现连续失败后，仍多次围绕同一种“斜边覆盖底图”结构追加局部补丁，包括改裁切方式、描边、尺寸、阴影和混合模式。虽然每次修改都有局部技术理由，但没有及时识别出用户的视觉约束与浏览器栅格化结果之间的冲突。

主要失误：

- 过早把源码和计算样式正确等同于视觉问题已解决。
- 多次以理论推断替代用户的实际视觉验收。
- 在根本结构没有变化时反复更换绘制 API。
- 一度通过取消右上圆角规避问题，破坏了已确认的卡片设计。
- 没有在连续失败后及时停止，并明确说明可接受结果之间的取舍。

## 后续决策

放弃三角折纸角标，改为不使用斜边的右上贴边状态页签：

- 继续紧贴卡片顶部和右侧。
- 保留卡片原有圆角。
- 使用水平和垂直边界，避免角标斜边直接覆盖高反差图片。
- 继续保留置顶、加密和已解密三种状态图标。
- 继续根据画报模板、媒体和文章类型适配颜色。

新的视觉结构需要单独确认后再实施，不能把本次失败方案中的补丁继续叠加到新方案中。

## 一句话经验

当用户验收的是可见像素时，连续的理论修补不能替代视觉结果；同一结构多次失败后，应停止追加补丁，明确约束冲突并更换结构。
