# 卡片折角白边问题复盘与结构性解决

日期：2026-08-10

## 结论

卡片右上角三角折纸角标的白边问题最终已经解决，并通过用户的实际视觉验收。

前期多轮修改始终让“角标的抗锯齿斜边”直接覆盖在照片上，因此无论使用 `clip-path`、SVG、渐变、边框三角形、描边还是混合模式，边缘像素都会混入照片颜色。最终方案没有继续更换角标绘制 API，而是改变图层之间的接触关系：媒体内容提前结束，露出比折角稍大的确定背景安全区，再把较小的折纸角标放入安全区内。

最终结构中，照片与角标斜边不再直接接触。媒体裁切边缘只与确定背景混合，角标斜边也只与确定背景混合，两条边缘之间保留 2px 安全距离，因此照片颜色无法进入角标的抗锯齿像素。用户确认此前可见的浅色毛边已经消失。

这份记录描述的是本项目从失败到解决的实际过程，不将早期失败扩大为“所有浏览器或所有实现都无法解决”的普遍技术结论。

## 原始目标

在瀑布流卡片右上角展示状态角标：

- 置顶内容显示置顶图标。
- 加密内容根据状态显示加密或已解密图标。
- 角标应像折纸一样紧贴右上角，而不是独立悬浮的徽章。
- 颜色应适配文字画报模板、图片、视频和文章卡片。
- 保留卡片原有圆角。
- 角标边缘不能出现可察觉的浅色毛边、阴影或额外分隔线。

## 实际问题

三角折角覆盖在浅色图片上时，斜边和右上圆弧会出现一条细微但可见的浅色边缘。放大后可以看到边缘像素混入了底图颜色。

用户以实际视觉结果为验收标准。即使样式声明、计算尺寸或局部截图显示某项技术措施已经生效，只要页面上仍能看到白边，就不能认定问题已经解决。

## 为什么这些修改始终无效

### 不同 API 最终生成的是同一种边缘

`clip-path`、硬切渐变、SVG 多边形和 CSS 边框三角形看起来是四种实现，进入浏览器绘制阶段后却都需要完成同一件事：把一条连续的斜线映射到由方形像素组成的屏幕上。

斜线会穿过部分像素。为了让它看起来平滑，浏览器会为这些像素计算一个介于 0 和 1 之间的覆盖率。最终颜色可以简化理解为：

```text
最终像素 = 角标颜色 × 覆盖率 + 底图颜色 × (1 - 覆盖率)
```

因此，浅色图片位于角标下方时，斜边必然会出现一列同时包含角标色和图片色的过渡像素。更换绘制 API 没有改变这条颜色计算，只是让浏览器通过另一条代码路径重新生成同一类过渡像素。

### 同色描边和向外扩展只会移动边界

给角标增加同色描边，或者把路径向图片方向扩展 0.5px 至数个像素，可以覆盖原来的混色边。但扩展后的图形仍然需要在新的最外侧位置结束，于是浏览器会在那里生成一条新的抗锯齿边。

这类修改能够把白边移动几个像素、改变宽度或降低显眼程度，却不能让“角标色与图片色的交界”消失。此前增加 4px SVG 同色描边仍然失败，就是因为新描边本身产生了新的外边缘。

### `shape-rendering` 不能提供确定保证

`crispEdges` 和 `optimizeSpeed` 只是向浏览器表达渲染偏好的提示。浏览器可以关闭部分抗锯齿，也可以只处理接近水平或垂直的线条，并不保证对任意斜线关闭插值。

即使 SVG 内部选择了更锐利的绘制方式，SVG 元素作为一个图层参与页面的最终缩放和合成时，浏览器仍可能重新采样其边缘。因此源码中已经出现对应属性，并不能证明最终屏幕像素不会混色。

### 整数尺寸不能保证整条斜线像素对齐

把折角宽高改成 44px 或 40px，只解决了图形尺寸本身的小数问题，没有解决以下因素：

- 瀑布流布局可能把整张卡片放在小数坐标上。
- 页面缩放比例和设备像素比会再次换算坐标。
- 即使起点和终点都位于整数像素，连接两点的斜线仍会穿过中间像素。

所以整数尺寸可以减少额外的模糊，却无法消除斜线本身的覆盖率计算。`translate3d` 只会改变合成方式，也不会自动把坐标取整。

### 像素阶梯消除了斜线，也破坏了斜线

用大量水平和垂直小线段模拟斜边，可以让每一段更容易对齐设备像素。但这相当于主动选择没有颜色混合的锯齿边缘。

它满足“没有半透明过渡像素”，却不再满足“折角斜边应当平滑”。这不是同时解决两个要求，而是在清晰毛边和可见锯齿之间换了一种瑕疵。

### 阴影和混合模式只是在视觉上遮盖

深色描边或阴影可以压住浅色过渡像素，但会引入新的视觉语义。用户已经明确认为阴影破坏了角标效果，因此不能把“白边不再显眼”当作“白边已被解决”。

`mix-blend-mode: multiply` 会改变角标覆盖区域与照片的颜色运算，使亮色更暗，但不会改变图形最外侧仍然存在部分覆盖像素的事实。它还会使同一个角标在不同照片上呈现不同颜色，破坏既定的模板配色和状态识别。

### 圆角和斜边是两个独立的抗锯齿边界

卡片原有右上圆角负责裁切整张卡片，三角折角又在卡片内部形成一条斜边。两者都可能生成部分覆盖像素。

取消右上圆角确实可以移除圆弧上的合成边，但会直接破坏已确认的卡片轮廓，因此不是有效修复。保留圆角时，也不能把圆弧边和三角斜边误认为同一个问题后统一覆盖。

### Canvas 也不能解决原结构的约束冲突

把照片和角标绘制进同一个 Canvas，可以消除两个独立 DOM 图层之间的透明合成接缝，但只要平滑斜线仍然直接分隔角标色和照片色，Canvas 也需要在两种颜色之间生成抗锯齿过渡像素。

如果关闭 Canvas 抗锯齿或逐像素写入二值颜色，可以做到没有混色，但边缘会成为像素阶梯。它仍然无法同时满足“平滑斜边”和“零颜色混合”，同时还会破坏当前图片、视频和响应式媒体的原生渲染路径。

### 原结构中的根本约束冲突

本次反复修改无效的根本原因不是某个 CSS 属性没有写对，而是同时提出了以下三个约束：

1. 折角必须使用平滑的斜边。
2. 斜边必须直接覆盖任意高反差图片。
3. 放大后边缘不能包含任何底图混色像素，也不能用描边、阴影或其他过渡遮盖。

在栅格屏幕上，平滑斜边依赖部分覆盖像素；零混色要求每个像素只能完全属于角标或完全属于图片。前者需要抗锯齿，后者要求二值硬边，两者不能同时成立。

因此需要改变的不是绘制 API，而是图层结构。最终实现选择了最后一种方向：取消角标斜边与图片的直接相交，同时保留平滑折角、卡片圆角和既有视觉语言。

## 最终解决方案

### 核心结构

旧结构只有两个直接接触的区域：

```text
照片 | 平滑斜边 | 折角
```

最终结构插入了一个确定背景安全区：

```text
照片 | 媒体裁切边 | 确定背景安全区 | 折角斜边 | 折角
```

具体处理如下：

1. 媒体层的右上角通过裁切提前结束。
2. 媒体裁切尺寸比实际折角尺寸大 2px。
3. 被裁去的区域下方只铺确定的深色背景。
4. 折纸角标保持原尺寸，完全位于这个安全区域内。
5. 图片、视频封面、播放中的视频和文章封面共用这套几何关系。
6. 纯文字画报和没有状态角标的媒体不改变原有渲染。

### 为什么这次有效

关键不是 `clip-path` 这项技术突然能够消除抗锯齿，而是它的使用对象发生了变化。

此前使用 `clip-path` 绘制角标，角标边缘下面仍是照片：

```text
角标抗锯齿像素 = 角标色 + 照片色
```

最终方案使用裁切让媒体本身提前结束，媒体边缘下面是确定背景；实际角标又缩在媒体边缘以内：

```text
媒体抗锯齿像素 = 照片色 + 确定背景色
角标抗锯齿像素 = 角标色 + 确定背景色
```

两条抗锯齿边界不再重合，也不共享照片像素。浏览器仍然正常进行抗锯齿，但最敏感的角标斜边已经没有机会采样到底图颜色。

因此，早期结论“平滑斜边和零底图混色不能同时成立”只适用于“斜边直接位于照片与角标的交界处”。最终方案不是发明没有抗锯齿的斜线，而是把照片从角标抗锯齿发生的位置移走。

### 为什么没有使用服务端派生图

项目已经使用 `sharp` 生成媒体预览，从能力上可以增加带透明缺口的卡片专用派生图，但这不是本次问题的最短主路径：

- 当前图片预览只有 64px，加载后还会切换到原图，仅修改预览无法解决问题。
- 视频播放后会从封面切换到真实 `<video>`，服务端只处理封面不能覆盖完整状态。
- 同一媒体会用于单图、多图、文章封面和详情页，服务端需要维护多种比例及历史回填。
- UI 角标会反向扩大媒体存储、协议和派生资源模型。

前端在真实展示尺寸上控制裁切区、2px 安全距离和角标尺寸，可以同时覆盖响应式图片与视频，并保持原媒体不受污染。

## 已尝试的实现

### CSS 裁切与渐变

- 使用 `clip-path` 绘制三角形。
- 使用硬切线性渐变代替裁切。
- 移除人为绘制的折痕线。
- 扩大三角区域并尝试覆盖斜边。

结果：浅色边缘仍然存在。

### SVG 绘制

- 使用 SVG `polygon` 绘制折角。
- 尝试 `shape-rendering="crispEdges"`。
- 尝试 `shape-rendering="optimizeSpeed"`。
- 增加同色描边，并沿圆角增加同色内描边。

结果：浏览器仍然会在最终合成结果中产生可见的底图混色像素。

### 像素和定位处理

- 将折角尺寸调整为桌面端 44px、移动端 40px。
- 检查瀑布流布局中的实际坐标和设备像素比。
- 尝试以水平、垂直的小台阶模拟斜线。

结果：没有达到视觉验收要求。瀑布流卡片的位置仍可能落在亚像素坐标，且最终画面仍能看到浅色边缘。

### 视觉遮盖

- 增加同色扩展和边线。
- 增加窄幅深色阴影模拟折痕。
- 尝试 `mix-blend-mode: multiply` 抑制亮色混合。

结果：边线和混合模式没有消除问题；阴影虽然能够弱化白边，但视觉效果被用户明确否决。

### 其他绘制路径

- 使用原生 CSS 边框三角形替代 SVG 和裁切。

结果：绘制路径发生变化，但实际视觉问题仍然存在。

## 未采用的方案

### Canvas 同层合成

将原图片和角标绘制到同一个 Canvas，属于与上述方案原理明显不同的路线，但会改变当前媒体渲染主路径：

- 静态图片需要重新处理加载、缩放和清晰度。
- 视频需要持续同步画面，复杂度明显扩大。
- 多图卡片、响应式尺寸和深浅色模式都需要额外处理。
- 会牺牲现有原生图片和视频元素的行为。

相对于一个状态角标，这个改造范围不合理，因此没有实施。

## 权威资料能够确认的范围

SVG 的 `shape-rendering` 是给浏览器的渲染提示，不保证对所有斜线关闭抗锯齿。规范也说明裁切路径通常会进行抗锯齿处理。

- [MDN：shape-rendering](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/shape-rendering)
- [W3C：SVG Rendering Model](https://www.w3.org/TR/SVG11/render.html)

这些资料可以解释为什么更换 SVG 渲染提示不能保证消除毛边，但不能单独证明所有可能的前端实现都无法解决。

## 本次协作的问题

AI 在前期已经出现连续失败后，仍多次围绕同一种“斜边覆盖底图”结构追加局部补丁，包括改裁切方式、描边、尺寸、阴影和混合模式。虽然每次修改都有局部技术理由，但没有及时识别出用户的视觉约束与浏览器栅格化结果之间的冲突。最终能够解决，是因为后续讨论停止了 API 层面的替换，重新审视了媒体、背景和角标之间的几何关系。

主要失误：

- 过早把源码和计算样式正确等同于视觉问题已解决。
- 多次以理论推断替代用户的实际视觉验收。
- 在根本结构没有变化时反复更换绘制 API。
- 一度通过取消右上圆角规避问题，破坏了已确认的卡片设计。
- 没有在连续失败后及时停止，并明确说明可接受结果之间的取舍。

## 最终决策

保留三角折纸角标，并采用媒体安全区结构：

- 角标继续紧贴卡片顶部和右侧。
- 保留卡片原有圆角。
- 媒体比角标提前 2px 结束，避免角标斜边直接覆盖高反差图片。
- 安全区使用确定的深色背景，角标只与该背景接触。
- 继续保留置顶、加密和已解密三种状态图标。
- 继续根据画报模板、媒体和文章类型适配颜色。
- 不新增服务端派生图，不改变原始媒体、详情页和数据协议。

实现后，用户在原先能够稳定看到毛边的页面中确认白边已经消失。

## 面试表达

### 30 秒版本

> 我做过一个很小但很典型的浏览器渲染问题：在瀑布流图片右上角叠加折纸状态角标时，斜边总会混入照片颜色，出现一条浅色毛边。最开始尝试过 SVG、`clip-path`、渐变、描边和混合模式，但它们都没有改变“抗锯齿斜边直接覆盖照片”这个根约束。最终我没有继续换绘制 API，而是让媒体提前 2px 结束，下面露出确定背景，再把角标缩进这个安全区。这样媒体边缘和角标边缘分别只与确定背景混合，照片不再参与角标抗锯齿，既保留了平滑折角，也消除了毛边。

### 2 分钟版本

> 这个问题出现在一个带图片、视频和纯文字画报的瀑布流里。需求是在卡片右上角显示置顶、加密和已解锁状态，并保留折纸斜边和卡片圆角。视觉验收时发现，浅色图片会沿折角斜边露出一条很细的毛边。
>
> 我先后验证了 CSS `clip-path`、SVG 多边形、硬切渐变、边框三角形、同色描边、像素对齐和混合模式。这些方案源码层面都成立，但实际视觉始终失败。后来重新抽象问题，发现它们虽然 API 不同，最终都让浏览器计算同一个像素公式：角标颜色乘覆盖率，再加照片颜色乘剩余覆盖率。所以只要照片直接位于平滑斜边下方，照片颜色就必然参与边缘像素。
>
> 最终解法是改变相邻关系，而不是关闭抗锯齿。我先把图片或视频容器的右上角裁掉，裁切区域比折角大 2px；裁切下方铺一层固定深色背景，再把实际折角放在更小的内部区域。媒体的抗锯齿边只接触固定背景，角标的抗锯齿边也只接触固定背景，两条边不会重合，照片颜色自然无法渗入角标边缘。
>
> 这个方案只修改了前端卡片和媒体组件，播放中的视频也能共用，没有引入服务端图片派生、历史资源回填或新的媒体协议。对我来说，这个案例的价值在于：遇到连续失败时，不应该继续堆属性，而要判断不同实现是不是仍在解决同一个错误的问题模型。

### 面试官可能追问

**为什么不直接关闭抗锯齿？**

关闭抗锯齿会把浅色毛边换成明显的像素锯齿，无法同时满足平滑折角的视觉要求，而且浏览器的 SVG 渲染提示也不能保证最终合成阶段完全不采样。

**为什么服务端生成图片不是首选？**

服务端派生图对静态图片可行，但卡片还包含视频播放、多图布局、不同宽高比和响应式尺寸。把 UI 状态或裁切烘焙进媒体会扩大存储、回填和协议范围。前端安全区直接作用于最终展示容器，范围更小且覆盖所有媒体状态。

**为什么仍然用了 `clip-path`，而之前它无效？**

之前裁的是角标，角标的半透明边缘下面仍然是照片；最终裁的是媒体，让照片提前离场。技术 API 没有神奇变化，变化的是裁切对象和图层邻接关系。

**2px 是怎么确定的？**

它不是用来掩盖原边缘的描边，而是让媒体裁切边和角标斜边在 CSS 几何上明确分离。尺寸由同一组卡片规则控制，并随移动端角标尺寸同步，避免两条独立边界因为缩放重新重合。

**这个案例体现了什么工程判断？**

先用实际像素结果否定无效方案，再区分“换实现工具”和“改变问题结构”；同时拒绝为了一个 UI 装饰扩大服务端媒体模型，选择能够覆盖图片、视频和响应式布局的最小主路径。

## 一句话经验

当用户验收的是可见像素时，连续更换绘制 API 不能替代视觉结果；同一结构多次失败后，应重新检查元素之间的接触关系，通过改变问题结构消除冲突。
